## 1. Peripheral Modular Grid Layout
* **Decision**: Snaps mirror modules into 9 distinct grid regions (`top_left`, `top_center`, `top_right`, `middle_left`, `middle_center`, `middle_right`, `bottom_left`, `bottom_center`, `bottom_right`), each an absolutely positioned anchor (a flex column pinned to an edge or the centre), keeping the center void clear.
* **Rationale**: Designed for ambient heads-up display (HUD) observation through semi-reflective glass. Centering information is restricted to maintain the primary reflective function of the mirror.

## 2. Server-Side Rendering (SSR) via Jinja2 & WebSocket Push
* **Decision**: Modules run their own event loops on the Python backend, render their HTML templates using Jinja2, and push the fully formed HTML payload to the client via WebSockets.
* **Rationale**: Keeps the kiosk client extremely thin, lightweight, and framework-agnostic. The client only needs to mount and transition raw HTML strings into designated container divs, eliminating complex client-side state managers or rendering libraries.

## 3. Dynamic Module Discovery via Python Entry Points
* **Decision**: Rather than hardcoding modules in the loader, the system automatically discovers installed module packages dynamically using Python `importlib.metadata` entry points (group: `mirrordash.modules`).
* **Rationale**: Allows third-party modules to be developed, packaged, and installed completely independently as standard Python wheels or editable packages. The core platform discovers them implicitly on startup.

## 4. Config-Driven Lifespan & Hot Reloading
* **Decision**: System configurations stored in `config.json` dictate module coordinates, custom properties, and enabled states. The config has been expanded to support multiple instances of the same module type. Each instance is indexed by a unique `instance_id` and contains a `"module"` property to identify the module type. Changes to the config trigger a soft reload: stopping, cancelling, and garbage-collecting running loops, and then spinning up newly configured instances. The reload restarts the modules only: the system settings (screen, time zone, SSH, Matter, the pi password) are applied once at startup (`start_system()` in the loader, called from the lifespan) and otherwise by each setting's own save. A `run_loop` must be `async def` (a thread can't be stopped on a reload), and one that returns or crashes starts again after a delay that doubles each time, up to 5 minutes.
* **Rationale**: Users can run multiple instances of modules (e.g. clocks in different timezones or positions) and customize their mirror layouts and parameters dynamically without restarting the Uvicorn web server or causing full browser disconnects.

## 5. Read-Only Squashfs Root via overlayroot
* **Decision**: The root filesystem is a zstd squashfs under `overlayroot=tmpfs:recurse=0`: `/` is a RAM overlay over the read-only card, and everything that must survive a reboot (settings, module data, the venvs, Wi-Fi profiles, SSH host keys) lives on the separate `/storage` partition, reached through symlinks (`~/.mirrordash`, `~/mirrordash/.venv`), one bind mount (NetworkManager's `system-connections`) and `HostKey` lines. `recurse=0` keeps `/storage` a real mount instead of a second RAM overlay. The build packs the root and writes both kernel parameters (`rootfstype=squashfs`, `overlayroot=`), so a mirror is locked from its first boot. That boot can't leave anything on the root either: the build sets up the `pi` user (not Pi OS's `userconf.txt`), and since the image's machine-id is `uninitialized`, systemd would treat every boot as the first one: it would enable every unit Debian's presets name (SSH, systemd-networkd, Cog without its path unit) and rerun the first-boot units (new SSH keys). `systemd.condition_first_boot=false` turns the first boot off; cloud-init, which sees a new machine every boot, is disabled. The repartition finds the card through `root=` and runs on every boot (a no-op once `/storage` is there). The app writes straight to `/storage` and never remounts anything.
* **Rationale**: The SD card is the part that wears out, and a power cut can't corrupt a filesystem that is never written. A squashfs root is a quarter of the ext4 size (757 MB instead of 3.2 GB for v0.6.2), which leaves room for a second root (A/B OS updates) on an 8 GB card, and the squashfs is what such an update would write. Writing the parameter ourselves instead of `raspi-config enable_overlayfs` is what lets us add `recurse=0`; raspi-config's version made `/storage` a RAM overlay that lost everything at reboot. The initramfs (with overlayroot and squashfs in it) is built in the image, for its own kernels. A run of `configure_image.sh` straight on a Pi stays ext4 and unlocked.

## 6. Hybrid Template Loader Resolution
* **Decision**: Implemented a `ChoiceLoader` combining standard Jinja2 `PackageLoader` with a fallback `FileSystemLoader` that resolves physical package paths on disk using `importlib.util.find_spec`.
* **Rationale**: Resolves `TemplateNotFound` errors on PEP 660 editable installations (common in local dev/testing environments like Hatch/uv) where zipped virtual package paths can hide standard template subdirectories.

## 7. Scope Isolation for Dynamic Module Helpers
* **Decision**: Auto-injected helpers (such as `render_template` and `translate`) are bound to their module instance by `_inject_module_helpers` in `features/modules/loader.py`, called once per instance after the constructor, so they are not available inside `__init__`.
* **Rationale**: Solves Python's loop lexical closure late-binding behavior. Defined inside the loader loop instead, nested helper definitions reference the loop variable by name, resulting in all module instances executing translations and templates using the scope of whichever module loaded last.

## 8. Skeletal Loading UI & Transition Flow
* **Decision**: Added a public unauthenticated `/api/active-modules` API to retrieve active modules list. On startup/refresh, the client fetches this metadata, pre-renders placeholder loading skeletons with visual spinners, and transitions them smoothly using a fade-in animation (`.module-enter`) once the first WebSocket frame for that module arrives.
* **Rationale**: Eliminates the flash of a blank screen on startup/page refresh. It provides immediate, responsive feedback ("Loading Swedish Name Day...", "Loading Clock...") while the backend modules fetch remote API data or perform slow initialization loops.

## 9. WebSocket State Caching for Instant Updates
* **Decision**: Implemented an in-memory frame cache (`latest_messages`) inside the WebSocket `ConnectionManager` ([ws.py](mirrordash_core/features/kiosk/ws.py)). Every time a module broadcasts an HTML payload, it is cached. Upon a new connection, the manager immediately pushes all cached HTML frames to the newly connected client. The cache is automatically cleared when modules reload or stop.
* **Rationale**: Resolves the delay on page refresh where modules (especially those with long update intervals like the 60-second name day module or hourly updates) would remain as skeletons until their sleep intervals completed and they triggered a new broadcast. Now, refreshed screens load the last rendered frames instantly.

## 10. Carousel Groups for Layout Regions
* **Decision**: Implemented a client-side carousel grouping system (`.carousel-group-container` and `.carousel-slide`). When multiple modules in the same region share the same `carousel_group` string in the configuration, they are rendered inside a single grid container and cycle visibility on a set timer, while ungrouped modules stack normally.
* **Rationale**: Provides users with fine-grained control over which modules cycle and which ones remain static in a region, avoiding rigid full-screen transitions. By using CSS Grid overlaying (`grid-area: 1 / 1 / 2 / 2`), all slides occupy the exact same space, preventing visual layout jumping or shifting during cross-fade transitions, keeping the ambient mirror clean.

## 11. Display Power Automation Strategies
* **Decision**: Integrated a central `DisplayPowerManager` daemon executing alongside the module loader lifespan. It supports time schedules, presence sensors and push buttons, read from kernel input devices (see #19 and #20). The Time of Day Schedule mode respects the global timezone configuration (e.g. `Europe/Stockholm`) when fetching the current time, ensuring timezone-aware scheduling.
* **Rationale**: Smart mirrors require automated power conservation. Supporting time scheduling, presence sensors, and buttons allows different hardware setups to save energy automatically. Timezone awareness prevents schedule misalignment if the host machine (e.g., Raspberry Pi) is configured to UTC or another local time.

## 12. User Data Outside the Package
* **Decision**: `config.json` and custom local modules live in the user's home directory, not in the package installation directory (which is replaced on every update).
* **Rationale**: Lets the core be installed and updated as a standard PyPI package without losing settings, while developers can still run from a cloned workspace.
* **Decision (never lose it)**: Files on `/storage` are written with `config.write_atomic` (a temp file, `fsync`, `os.replace`, `fsync` of the folder), so a power cut leaves the old or the new file, never an empty one. Before each save the current `config.json` is kept as `config.json.bak`, but only when it reads. A `config.json` that doesn't read is moved aside as `config.json.broken-<UTC time>` and the backup is used; only without one does the mirror start with defaults. *Rationale*: a broken file used to be overwritten with the defaults at the next start, so one bad write lost every setting. One backup generation (ponytail): enough to survive one bad write, not a history.
* **Decision (no /storage)**: `/storage` has `nofail` in fstab, so a filesystem check that wants a person lets the boot go on without it. The hydrate script then runs `e2fsck -p` (`-y` if that isn't enough), mounts it and saves a `storage-repair` log. If it still isn't mounted on an image, it stops, so the app (which `Requires=` it) doesn't start and the loading page says so after 4 minutes. *Rationale*: on the RAM overlay (#5) the folders would have been made in RAM: the mirror looked new, copied `base_venv` into a Pi 3's 1 GB of RAM, and forgot everything at the next restart.

## 13. Directory Contract
* **Decision**: Everything lives under `~/.mirrordash/` (on the mirror a link to `/storage/mirrordash/data`): the config in `data/config.json`, each module instance's data in `data/<instance-id>/` and its cache (such as `fetch_json`'s last good answers) in `cache/<instance-id>/`. Both are on `/storage`, so a cache survives a reboot.
* **Rationale**: One directory is all a backup or a reflash has to care about, and it is the one place a read-only root leaves writable (#5). Separate paths per instance ID keep two instances of the same module from clobbering each other's data.

* **Decision (resetting)**: **Reset Mirror** (Settings, type RESET) runs `mirrordash-factory-reset --yes` through its own sudo rule: it deletes everything in `/storage/mirrordash` but `logs/`, and restarts; hydrate then seeds it as on a first boot (venv, Python, SSH host keys, a new hotspot password). `/storage/rauc` stays, since it says which A/B slot is the good one. *Rationale*: everything of the owner's is on `/storage` by this contract, so deleting that folder is the whole reset; giving a mirror away used to mean reflashing it.

## 14. WiFi Fallback / Captive Portal State Machine
* **Decision**: Implemented an automated fallback WiFi captive portal setup state machine. If network connectivity is not verified within 30 seconds of system boot, NetworkManager shifts `wlan0` to an autonomous Access Point (AP) setup hotspot. Phones get a real captive portal: the OS image makes the hotspot's dnsmasq (`/etc/NetworkManager/dnsmasq-shared.d/`, used only for shared connections) answer every DNS name with `10.42.0.1`, so the phone's HTTP connectivity check (`captive.apple.com/hotspot-detect.html`, `connectivitycheck.gstatic.com/generate_204`, ...) reaches the app, whose middleware answers anything but the setup page with a redirect to `http://mirrordash.setup/wifi-setup`; the unexpected answer makes the phone show "Sign in to network". Submitting credentials saves the new NetworkManager profile (on `/storage`) and joins it without a restart; if joining fails, the hotspot comes back with the same password (a reboot only if even that fails). The check service is `Type=oneshot` and ordered `Before=mirrordash.service`, so the app (and therefore the kiosk's first page) only starts after the client-vs-hotspot decision; the app's hotspot check uses a short TTL cache, never a permanent one, so a state change is picked up within seconds. The hotspot password is unique per mirror: the check script generates it when it creates the `MirrorDash-Setup` profile (with `autoconnect no`), and the profile is only taken down after setup, never deleted, so it lives on `/storage` (the bind-mounted `system-connections`) until the card is reflashed. Any connection counts at boot, so a cable keeps the hotspot off; one plugged in while it runs takes it down (NetworkManager dispatcher `40-mirrordash-cable`), since the periodic watch only retries saved Wi-Fi. The app reads the password back with `nmcli -s` (allowed for pi by a polkit rule, no sudo) and shows it, with a Wi-Fi QR code, only to a loopback client (the mirror's own screen); phones on the hotspot can spoof the Host header but not their address.
* **Decision (the watch)**: The same script with `--watch` runs every 3 minutes from `mirrordash-wifi-watch.timer`. On the hotspot it tries the saved Wi-Fi again (a scan, then `nmcli connection up id` for each saved Wi-Fi, the last one used first, which also brings back a profile NetworkManager stopped retrying) and brings the hotspot back if that fails; it skips this while a phone is on the hotspot (a REACHABLE/DELAY/PROBE neighbour on `wlan0`; `iw` isn't in the image) or when no Wi-Fi was ever saved. Off the hotspot it does the boot check with a 60 s wait, so a Wi-Fi gone for good starts the hotspot without a restart, and a Wi-Fi change from the admin page (seconds without a connection) never does. Only NetworkManager's own state counts, so a lost internet behind a working router changes nothing. After a switch the script posts `/api/wifi/changed` (loopback only), and the app reloads the mirror's screen into the setup prompt or the mirror.
* **Decision (by name, after a scan)**: Not `nmcli device connect wlan0`, which the watch used first: right after the hotspot the Pi 3's chip rejects the first scan (`Reject scan trigger since one is already pending`), so NetworkManager saw no saved Wi-Fi and brought the hotspot itself back up, the only profile available without a scan, and `nm-online` took that for being online. Every round logged "Back on the saved Wi-Fi" while the mirror stayed on the hotspot until its power was cut; found with developer logging on a Pi 3B. The traffic check's rejoin uses the same `join_saved_wifi`.
* **Rationale (the watch)**: After a power cut the mirror is up in ~30 s and the router in 1–3 minutes, so the boot check started the hotspot, which (with `autoconnect no` and the radio busy as an AP) never looked for the home network again: the mirror stayed on `MirrorDash-Setup` until someone restarted it. A systemd timer instead of a loop in the app or the script: no long-running process, and the radio is only touched every few minutes.
* **Decision (no traffic)**: When NetworkManager says the Wi-Fi is joined, the watch also pings the router (or 1.1.1.1, for routers that don't answer ping). Two rounds in a row without an answer (about 6 minutes) save the log as `wifi-lost` under **Logs → Saved Logs** (once per outage) and join the Wi-Fi again (`nmcli device disconnect` + `connect`); the next rounds keep trying. *Rationale*: a Pi 3 stayed joined for over 20 minutes while nothing got through, so NetworkManager saw nothing wrong and the hotspot never came; only a power cut brought it back, and with the log in RAM nothing showed why. Two rounds, so a router that restarts isn't taken for it. The failure count lives in `/run` (RAM), like the rest of the watch.
* **Decision (a Wi-Fi chip that didn't start)**: The watch also checks first that the Wi-Fi chip is there: `brcmfmac` (the driver of every Pi with built-in Wi-Fi) loaded but no `wlan0` means the chip's firmware didn't load at boot (seen on a Pi 3: "Downloaded RAM image is corrupted"; it then had no Wi-Fi and no hotspot until restarted). It saves a `wifi-chip` log (once per start), loads the driver again (all `brcmfmac*` modules out, `brcmfmac` in, `udevadm wait` for `wlan0`), and only if `wlan0` still doesn't come and there's no network at all (no cable either) restarts the mirror, at most once an hour (a stamp on `/storage`). *Rationale*: it acts on the symptom, not the model, so it covers every Pi with that chip family and does nothing on one without built-in Wi-Fi or with working Wi-Fi; a driver reload is harmless, and the restart is limited so a broken chip can't make the mirror restart over and over.
* **Decision (from the admin page)**: *Settings → Wi-Fi* changes the network: the route answers first and switches a second later (the phone loses the mirror the moment it changes network). If the mirror can't join, it deletes the profile that attempt created and brings the previous one back up; the card then shows why.
* **Rationale (setup)**: Minimizes appliance maintenance and makes the device plug-and-play across different network environments without requiring terminal access or physical disassembly.

## 15. Hardware Watchdog
* **Decision**: Kept the kernel hardware watchdog that Raspberry Pi OS enables (`RuntimeWatchdogSec=1m`, its drop-in `40-rpi-enable-watchdog.conf`; our earlier 14 s edit of `system.conf` never applied, the drop-in overrides it). `mirrordash.service` starts after `network.target` and the storage hydration, and the Wi-Fi check (#14) runs before it; it doesn't wait for time sync.
* **Decision (the app and the screen)**: `Restart=always` only helps a process that dies. `mirrordash-app-watch` (a timer every 3 minutes, like the Wi-Fi watch #14) restarts `mirrordash.service` when `/health` doesn't answer two rounds in a row, and `cog-kiosk.service` when the mirror's own screen has been silent for over 5 minutes two rounds in a row: the kiosk page sends `alive` on its WebSocket every minute, and the setup prompts poll `/admin/auth/status`; only loopback clients count (`ConnectionManager.saw`), and `/health` reports `screen_seen_seconds_ago` (null while the screen is off). It retries every second round while the fault stays, but saves the `app-hung`/`screen-lost` log once, so it can't push the other saved logs out. *Rationale*: a WebKit renderer that crashes or freezes keeps Cog's window (and can keep the socket open), and a hung event loop keeps the process; both left a dead screen until the power was cut. A timer, not `WatchdogSec` + sd_notify: no change to `launch.sh` or the unit type; the price is ~6 minutes instead of seconds.
* **Decision (the clock)**: The Pi has no clock battery and the root forgets, so every start began at the image's build date until NTP answered. `mirrordash-clock.service` (`/usr/local/lib/mirrordash/clock`) moves the clock forward to the time saved on `/storage/mirrordash/clock` at start, before the network, never back; the time is saved hourly and at shutdown, only once NTP has set it. Not Debian's fake-hwclock: it loads before `/storage` is mounted. Not a bind mount for timesyncd's own clock file: timesyncd starts before `sysinit.target`, hydrate after it, and a missing mount would keep timesyncd from starting at all.
* **Rationale**: The mirror restarts by itself if the kernel or systemd hangs, with the vendor's tested default. The Pi has no clock battery, so the first minute can run on an old time; modules fetch again on their next interval, and `fetch_json` returns the last good answer meanwhile, which beats a screen that waits for NTP.

## 16. Failsafe A/B Virtual Environment Updates
* **Decision**: Redirected the virtual environment `.venv` from the read-only root partition to the persistent writeable `/storage` partition via a symlink. When the core's packages change (an update, a rebuild), the change is staged in a cloned alternative directory (`venv_a` or `venv_b`). The modules aren't in it: they live in the module site, which the module host switches the same way (#41). Once successful, the symlink is atomically updated and the previous environment is kept as `venv_old`. A core update that didn't install a newer version (PyPI's index can lag a few minutes; uv runs with `--refresh-package mirrordash`) is reverted with a 409 instead of switched in, so a no-op never replaces the real fallback in `venv_old`. *Rebuild environment* (*Reinstall MirrorDash*) starts from an empty venv with this MirrorDash version; the modules, in the module site, stay as they are.
* **Decision (the app's Python)**: The Python the venvs run lives on `/storage/mirrordash/python`, with the app, not in the root: `mirrordash.service` sets `UV_PYTHON_INSTALL_DIR` there (and `venv.run` passes it on), and the hydrate script gives a venv that still uses the root's Python (one seeded from `base_venv`, or from an older image) a copy of it, once, and points it there (its `bin/python` link and `pyvenv.cfg`'s `home`, the only places that name it). Only `base_venv` (Safe mode) uses the root's Python. A MirrorDash whose PyPI `requires_python` asks for a newer minor (`needed_python`, ">=3.N" only) is an app update like any other: `uv python install 3.N` next to the running one, an empty venv with it and the new MirrorDash, an empty module site with every module built for it by the module host (the pinned version, then the newest for a PyPI module), and each module loaded once from there. Only when all of them work is it switched in; otherwise nothing has changed, the update card lists the modules and why, and **Install Anyway** installs without them and turns their instances off (`disabled_reason`, settings kept). *Rationale*: the venvs used to link into the root, so an OS update with another Python left them unable to start; hydrate then deleted them on the trial boot, before the update was proven, the modules were gone for good (Reinstall read the list from the running, empty venv), and a failed trial lost the app update too. A new Python is seldom a breaking change for a module, so none is dropped up front, and the admin, not the mirror, decides whether losing one is worth it. *Order*: the first image with this must keep the root's Python (3.14), since that is what is copied; only a later image may change it. After every swap, `remove_unused_pythons` deletes the Pythons on `/storage` that none of `venv_a`, `venv_b` and `venv_old` (the launcher's fallback, which must still start) uses, about 90 MB each; `venv_failed` needs none, only its files are read. Only where `UV_PYTHON_INSTALL_DIR` is set, so never a developer's own uv Pythons. *Patches*: every app update first runs `uv python upgrade 3.N` (same guard); the venvs point at uv's minor link, so all of them get the newest 3.N.x, and the old patch is removed after the swap.
* **Rationale**: Prevents package upgrades from bricking the system in the event of an update failure (network drops, syntax errors, or incompatible package versions). The boot-time hydration script only seeds `venv_a` and the link when the link is missing or dangling; it never resets a valid link, otherwise every reboot would silently revert A/B updates to the factory `base_venv`.

## 17. Boot Fallback Launcher and Settings Restoration
* **Decision**: Implemented a boot launcher script (`launch.sh`) that monitors the startup lifespan of the application. If the primary virtual environment fails to boot successfully within 10 seconds, it automatically rolls back to the previous stable state (`venv_old`) or fallback boots the Golden Copy (`base_venv`, the version the image shipped with, on the read-only root, so no update or power cut can touch it) in Safe Mode, alerting the user via UI status banners. Additionally, user configurations (SSH state, timezone, and shadow-crypt password hash) are programmatically re-applied on boot.
* **Rationale**: Maintains a high standard of consumer appliance resilience and security under OverlayFS, ensuring the device remains accessible and self-healing.

## 18. Background Jobs and Restart Detection in the Admin UI
* **Decision**: Long package operations (module install/upgrade/uninstall, core update, venv rebuild, backup restore) run as a single in-memory background job (`start_job` in `admin.py`). The HTMX request returns immediately with a script that opens the progress overlay; the UI then polls the authenticated `/admin/jobs/current`. Every process start gets a random `BOOT_ID`, reported by `/health` and the job endpoint, and a restart counts as finished only when that id changes. All `hx-confirm` prompts go through the app's own `showConfirm()` dialog via one `htmx:confirm` handler, and button spinners use HTMX's `.htmx-request` state (`.htmx-indicator` / `.htmx-normal`, `hx-disabled-elt`) instead of being set in `onclick`.
* **Rationale**: On a Pi 3 these operations take minutes, longer than nginx's 60 s proxy timeout, so a synchronous request could fail while the work continued silently. Inferring a restart from timings ("down after 5 s, then up") broke on flaky Wi-Fi and left the overlay spinning. Spinners set in `onclick` started before the confirm dialog and were never reset, even when the user cancelled. One job at a time matches the A/B venv swap, which cannot run concurrently, and a restart ends every job, so no persistence is needed.

## 19. Sensors and Inputs via Kernel Device-Tree Overlays
* **Decision**: Everything on the GPIO header is a list of devices (`system.devices`, at most one per type: `button` (and `button_2`–`button_4` for up to four buttons, `KEY_MACRO1`–`KEY_MACRO3`), `pir`, `mmwave`, `dht11`, `light`, and one of `fan` (`gpio-fan`, on/off) or `pwm_fan` (`pwm-gpio-fan`, four speed steps)), and every device is a Raspberry Pi kernel driver instead of a Python GPIO library. A root-owned helper (`mirrordash-gpio-overlays`, allowed in sudoers) takes typed arguments (`button:17`, `light:0x23`), validates them against a fixed vocabulary and writes the matching overlays into a managed `[all]` block of `config.txt`; the firmware applies them at the next boot. `gpio-key` overlays turn the button, PIR and mmWave sensor into input devices (`KEY_PROG1`–`KEY_PROG3`) that `hardware.GpioInputs` reads as raw evdev events; `PressClassifier` turns button down/up times into single/double/triple/long presses. The DHT11 (`dht11` overlay) and the BH1750 light sensor (`i2c-sensor` overlay, enables I²C) are read by one generic IIO reader from `/sys/bus/iio/devices`, cached for 30 s. `hardware.sync_gpio_overlays()` validates the list (pins, I²C reserving GPIO 2/3) and only calls the helper when the overlay arguments change; the change is marked pending with the kernel boot id until the mirror restarts. A failure there never blocks saving other settings. Modules get the hardware through the event bus: `hardware.button` `{"press", "action", "button"}` (each button has its own `PressClassifier` and `long_press` time, 1.5 s by default), `hardware.motion` `{"motion", "sensor"}` on every change (`motion` is true while any presence sensor sees someone), `hardware.climate` `{"temperature_c", "humidity"}`, `hardware.light` `{"lux"}` and `hardware.fan` `{"level", "max_level", "cpu_temperature_c"}` every 30 s. The fan itself is run by the kernel's thermal framework; the app only reads its state from `/sys/class/thermal`. Module subscriptions are cleared whenever the modules are reloaded, since the reload creates new instances.
* **Rationale**: The app runs on uv's Python 3.14, where `gpiozero`/`RPi.GPIO` are not installed and `lgpio` cannot be built on the device, so the previous GPIO code silently did nothing. The kernel debounces inputs and handles sensor timing far more reliably than Python polling, with no extra dependency. One device list, one IIO reader and one input reader mean a new sensor type is mostly one entry in `DEVICE_TYPES` plus one line in the helper. Changes only happen at boot because overlays applied by the firmware can't be removed at runtime. Only a fixed set of types is accepted by the root helper, so the app can never write arbitrary content into `config.txt`.

## 20. Screen Wake Timer
* **Decision**: `DisplayPowerManager` combines a base mode (`manual` = always on, `interval` = schedule, `wake` = off until woken) with one wake timer. Presence sensors (if enabled), the push button, the admin page and the open `POST /admin/screen` endpoint wake the screen for `timeout_minutes` (or a per-call `timeout_minutes`). With `extend` the countdown restarts on every wake and stands still while someone is present; without it the screen goes off a fixed time after the first wake. An explicit "off" wins until the next wake or base-mode change. The decision is a single method (`desired_state`) that gets the time and presence passed in, and commands wake the loop through an `asyncio.Event` instead of waiting for the next tick.
* **Rationale**: The PIR mode was a hard-coded special case of the same idea. One timer covers presence, buttons and home automation calls the same way, and the two counting strategies cover both "stay on while I'm here" and "show it briefly". An API call without a timeout gets the default time, so the screen can never be left on by mistake.

## 21. Module Scripts Receive Their Shadow Root
* **Decision**: The kiosk wraps every inline `<script>` in a module's HTML as `(function (root) { … })(…)`, where `root` is that module instance's shadow root. The root is kept across re-renders, so a script keeps per-instance state such as a timer on it (`clearInterval(root._timer); root._timer = setInterval(…)`).
* **Rationale**: Module HTML lives in a shadow root, and the HTML spec makes `document.currentScript` null there, so scripts had no reliable way to find their own markup; looking themselves up by `data-module` broke whenever the instance id differed from the package name, and globals made two instances of a module share one timer. One wrapper in the core gives every module the same answer without a client-side API.

## 22. Releases Are Made From What Was Tested
* **Decision**: One local script, `scripts/release.py`, makes every release, and each real release follows a test. The app is first published as a PyPI pre-release (`X.Y.ZrcN`) that only mirrors with `system.prerelease` ("Test versions") are offered and install (`uv pip install --prerelease=allow`); the release then bumps to `X.Y.Z`. The OS image is built only on request and published as a test version (the GitHub pre-release `vX.Y.Z-osN`), which only mirrors with Test versions are offered as a system update, or flashed from its download; the release turns that same pre-release into the release, so nothing is rebuilt. `publish.yml` refuses a tag that isn't `v` + the `pyproject.toml` version. Versions are compared with `config.version_key`, which orders a release above its own pre-releases.
* **Rationale**: Releases were made by hand in the GitHub UI, nothing tied the tag to the published version, an OS image was rebuilt at tagging so the shipped file was never the tested one, and there was no way to try an app version on one mirror before all of them got it. The script keeps the GitHub CLI as its only extra tool and the mirror gains no dependency (`packaging` isn't installed there).

* **Decision (automatic updates)**: On unless *Install updates automatically* is off (`system.auto_update`, missing = on). `mirrordash-auto-update.timer` (03:30, spread over an hour) asks the app (`POST /admin/auto-update`, loopback only), and `auto_update()` does what the Updates card's buttons would, the system first, as its own job. It doesn't choose for the owner: a system build whose trial boot failed is remembered (`system.auto_update_skip_build`) and not tried again by itself, and a newer Python some modules don't work with waits for **Install Anyway**. *Rationale*: an update only by button never reaches a mirror nobody looks after, which is most of them, security fixes included; the safety is already in the updates themselves (A/B, the trial boot, the module check).

## 23. Shared Building Blocks for Modules: Layout Classes and fetch_json
* **Decision**: Everything a module may use for its look lives in one stylesheet, `static/modules.css` (typography, `.text-*`, `.flex-*`, icons, data lists, forecast and agenda lists, gauges, stats, callouts, `.module-message`). `style.css` imports it for the page, and the kiosk loads it once and puts it into every module's shadow root next to the design tokens (`static/js/kiosk/design-tokens.js`). `/design` is the library of exactly these components, with markup to copy; a test keeps every class in its markup present in `modules.css`, and the mirror's own UI is marked there as not for modules. The module loader also gives every module `self.fetch_json(url, …)` and `self.fetch(url, …)` (raw bytes, for RSS, ICS and other non-JSON answers) next to `render_template`. Both take `headers`, `params`, `method`, `json`, `data`, `timeout` and `max_age` (reuse a saved answer younger than that, so a restart of the modules makes no call), the names `requests` uses, so a module never needs its own HTTP client, whatever API it talks to; `mirrordash-sdk validate` warns about one. They return `(data, error)`: on any failure the last good answer for the same method, URL and body (kept in the module's `cache_dir`) and one of `rejected`, `offline`, `http <code>`, `invalid`. They log only method, host and path. Module templates in `mirrordash-sdk` build on both.
* **Rationale**: The module guide recommended classes that only existed in the global stylesheet, which a shadow root never sees, so every module wrote its own CSS. Five modules each had their own fetch, JSON, timeout and error code, with different bugs (an error branch that could never run, a network error read as "nothing today", an API key in the log). One helper in the core fixes that once, needs no dependency (urllib in a thread), and keeps modules free of imports from the core.

## 24. An API for Other Systems, With Its Own Description
* **Decision**: `/api/v1` (`features/api/api.py`) answers only to `Authorization: Bearer <token>`, a 256-bit token from the Settings tab's *API* card. Only its sha256 is stored (`config["api_token"]`), so it is shown once; a new token replaces the old one. It can read `/status` (version, uptime, CPU temperature, screen, brightness, modules, cached sensor readings) and set `/screen` and `/brightness`, which reuse the admin's own `update_screen_state` and `update_system_settings`. The admin password (`X-API-Key`) is not accepted there. It is its own FastAPI app mounted at `/api/v1`, with Pydantic models for every body and answer, so `/api/v1/docs` (Swagger UI) and `/api/v1/openapi.json` describe it; they are open, the calls are not. Home Assistant is one client: its `rest`, `rest_command`, template `switch` and template `number`, with the YAML in the user guide.
* **Rationale**: Before, the only key was the admin password, which Home Assistant would have had to keep. A separate token can be removed without changing the password, can't install modules or restore backups, and survives a backup restore (the hash is in `config.json`; `admin_auth` is not). MQTT discovery or an own integration would mean a broker or a second repo for what a few REST calls do. The older open `POST /admin/screen` stays for existing automations. Only this API gets a description: the rest of the app has one client, the admin page, so a description there would only be attack surface (#27).

## 25. The Screen Reloads After a Restart of the Core, Not on a Reconnect
* **Decision**: On every WebSocket connection the server first sends `{"type": "hello", "version": …, "boot_id": …}`; the boot id is new each time the core process starts (`admin.BOOT_ID`). The kiosk page remembers both from the first hello and reloads itself when a later one carries a different version or boot id: the core was updated, or restarted (a module installed or removed, a backup restored). Anything else (a module's settings changed, a settings change) arrives as rendered HTML over the open socket. The admin's Power tab has a *Reload Screen* button that broadcasts `{"action": "reload"}` for everything else.
* **Rationale**: Cog keeps one page open for weeks, so after a core update it would run the old `core.js` and CSS against the new server, and after a restart that removed a module it kept that module's last HTML on screen. Reloading on every reconnect would flash the screen at each Wi-Fi blip; a reconnect to the same process keeps its boot id, so the page reloads exactly when it is stale. The button covers the rare case nothing detects, without SSH.

## 26. Discover: One Search Request, the Release Tag Pinned at Install
* **Decision**: The module list under *Modules → Add modules* makes one GitHub search request (repositories named `mirrordash-*`, up to 100) and keeps the previous list if it fails. Only at install is the module's latest release looked up; its tag is appended (`…@v1.2.0`), a repository without releases is refused, and a rate-limit or network error asks the user to try again later.
* **Rationale**: Unauthenticated GitHub allows 60 requests an hour per IP, shared by the whole home network, so one request per repository ran out after a few scans and silently showed only the first module. Pinning the tag installs a published release instead of whatever is on the default branch, and the update check compares that recorded revision with the latest release.

## 27. The Core in Vertical Slices
* **Decision**: The core is organised by feature, not by layer. `mirrordash_core/features/<feature>/` (api, auth, backup, dashboard, hardware, kiosk, logs, matter, modules, power, settings, updates, video, wifi) holds a feature's routes, logic and templates; one Jinja environment reads every `features/*/templates`. Code two or more features use stays at the package root: `admin.py` (page shell, login, jobs, page events), `config.py`, `forms.py` (forms from a JSON schema), `venv.py` (the A/B swap and uv), `host.py` (OS commands), `fetch.py`, `system_settings.py` and `event_bus.py`. `app.py` only composes. The admin panels call feature functions directly, so a feature only has HTTP routes something requests; the JSON routes nothing called were removed, and so were FastAPI's `/docs` and `/openapi.json`.
* **Rationale**: A feature was spread over a JSON file, a panels file, `system/`, `templates/` and a root module, so a change touched five places and copies drifted apart (the A/B swap five times, backup validation twice, the form flattening three times). Measured before and after: no function above grade C (from one F, three E and five D), average complexity A (4.3, from B 5.6), the largest Python file 513 lines (from 592), `admin.html` 245 lines (from 1763), routes 96 → 74.

## 28. A Forgotten Admin Password: a Recovery Code From Setup
* **Decision**: Setting up the admin password also creates a recovery code (12 characters, `XXXX-XXXX-XXXX`), shown once and stored only as a PBKDF2 hash next to the password. With it, *Forgot password?* sets a new password; the code is then used up and a new one is shown. Changing the password keeps the code. Without the code, the password is reset by removing `admin_auth` from `config.json` over SSH or on the SD card (USER_GUIDE §1), after which the admin page asks for a new password.
* **Rationale**: The earlier recovery (a PIN on the mirror's screen) needed no login to start and wiped the password at once, so anyone on the network could lock the owner out, and the 6-digit PIN had no attempt limit; anyone in front of the mirror could take over. A reset e-mail would need an SMTP account on every mirror or a MirrorDash mail service, against a mirror that works on its own at home. A code the owner saves works offline and can't be guessed (~59 bits behind PBKDF2), and whoever can reach the SD card owns the mirror anyway.

* **Decision (logging in)**: The admin page sends the password once, to `/admin/auth/login`, and gets a random session token as a cookie (`HttpOnly`, `SameSite=Strict`, 30 days); `require_api_key` accepts that cookie (one sha256 lookup) or, for scripts and tests, the password in `X-API-Key`. Only the token's sha256 is kept, in `sessions.json` next to `config.json`, so the restart after an update doesn't log anyone out. A new password (changed, or reset with the recovery code) ends every session. Five wrong passwords or recovery codes from one address in a minute lock it out for a minute (in memory). A cookie request that changes something is refused when its `Origin` is another site, and the server sends no CORS headers. *Rationale*: the page kept the password itself in `localStorage` and sent it, over HTTP, with every request; any script on the page could read it, every request ran 100 000 PBKDF2 rounds on the Pi, and nothing stopped guessing. The CORS setting (any origin, with credentials) would have let any web page use a logged-in session.

## 29. Modules Sleep While the Screen Is Off
* **Decision**: While the screen is off, a module's `fetch`/`fetch_json` waits until it is on again (`DisplayPowerManager.awake`). The module's loop stands still at the fetch, so a fetch that fell due in the dark goes out once on waking, and one that didn't waits for its own interval. A module that must run in the dark (a data logger) sets `keep_running = True` on its class. Modules that use their own HTTP client are not held.
* **Rationale**: A dark mirror shouldn't spend paid API calls or rate limits. Cancelling and restarting the modules' tasks would fetch on every wake, so a mirror woken by presence could call an hourly API many times an hour; holding the one shared fetch keeps each module's own schedule without the core knowing it, and needs no setting. Home Assistant already turns the screen off when nobody is home, so that sleeps the modules too.

## 30. Modules Keep Their Own Schedule; the Core Stops Redraws of the Same Content
* **Decision**: There is no scheduler in the core. A module loops in `run_loop` with its own `interval` (a convention from the SDK templates, not a core field) and passes `max_age=self.interval` to `fetch`/`fetch_json`, so restarting the modules (every saved setting, an update, a reboot) reuses a young saved answer instead of calling the API again. The websocket manager (`kiosk/ws.py`) doesn't send a module the same message twice, so the screen doesn't redraw a module whose HTML and settings didn't change; a reload clears that memory.
* **Rationale**: A scheduler would be a second way to do what `run_loop` does, and `run_loop` stays anyway for push updates, clocks and carousels; the core would also have to own a retry policy (a fetch at 10:30 that fails: retry when?) and time of day around a boot without a clock battery. MagicMirror² works the same way: an `updateInterval` convention per module and a check in the core that skips a redraw of unchanged content. Redrawing identical HTML restarts a module's icons, scripts and scrolling, which shows as a flicker. `max_age` is explicit rather than taken from `interval`, since `interval` means different things in different modules (namnsdag checks for a new day every minute but fetches once a day).

## 31. A/B OS Updates: RAUC and the Pi Firmware's tryboot
* **Decision**: The OS updates without reflashing. The card has two slots (boot p2 + root p5 = A, boot p3 + root p6 = B), a small p1 with the Pi 3 firmware files and `autoboot.txt` (which boot partition the firmware starts), and `/storage` (p7) shared by both; the image holds p1–p5 and the first boot adds p6 and p7 (`mirrordash-repart.sh`). A release carries a signed RAUC bundle (the same boot and root images as the card image); **Settings → Check for Updates** downloads it to `/storage` and has RAUC write it into the slot that isn't running. Our own bootloader backend (`rauc-bootloader`, about 140 lines of bash, `scripts/image/rootfs/usr/local/lib/mirrordash/rauc-bootloader`) then points the new boot partition at its own root, carries over the Wi-Fi country and the GPIO block, and sets the firmware's one-time tryboot flag. On that trial boot (only when the slot running is the one RAUC activated last, by RAUC's own `activated.timestamp` in `/storage/rauc/central.raucs`, so a trial started by hand with `reboot "0 tryboot"` never keeps an older slot, and it holds also when an older system installed the update) `mirrordash-mark-good.service` waits for the internet (`https://github.com`, where the next update comes from; not `nm-online`, which counts the setup hotspot as online, so an OS whose Wi-Fi can't join the home network would be kept and the mirror could never be updated again) and the app's `/health`, then swaps the partitions in `autoboot.txt`; if either fails it restarts the mirror, which then boots the old slot. `/boot/firmware` is mounted by a systemd generator from the partition the firmware reports, since the shared root's fstab can't know it. `rootdelay=20` keeps the fallback after a missing root to about half a minute. The build stamp (`/etc/mirrordash-os-build`, and the end of the bundle's file name) says which OS is newer. Images only: a Pi set up by hand has one root.
* **Rationale**: Reflashing loses the setup and needs a computer; mirror owners shouldn't have to. The Pi firmware's own A/B switch (`autoboot.txt`, `tryboot_a_b`) needs no U-Boot, and was tested on a Pi 3B before this was built: it boots the tried slot once, and any restart, power cut or kernel panic before mark-good brings back the old one. RAUC brings signature checks and the slot handling; Mender would have meant U-Boot and a server. Rtone's RAUC backend for the same firmware feature was the model, but it is 500 lines for many layouts, and it has to be changed anyway (`sync` around the `autoboot.txt` swap, the boot partition setup), so ours is written for one layout. The root fix lives in `set-primary` rather than a post-install handler because RAUC ignores a failing post-install handler: a boot partition pointing at the wrong root must fail the install. The bundle is downloaded to `/storage` before installing instead of streamed: then sudo allows `rauc install` on one fixed path only, and a Wi-Fi drop stops the download before anything is written rather than failing the install halfway (it costs about 800 MB on `/storage` while it runs). Only one file path is allowed to `rauc install` through sudo, and RAUC refuses bundles not signed with the key behind `scripts/rauc/cert.pem`.
* **Limits**: The mirror boots from the SD card only (`/dev/mmcblk0` is fixed in `system.conf` and the backend), not USB or NVMe. Slot sizes can't change on cards that are out there: root 1.5 GiB (757 MB used), boot 256 MiB (about 90 MB used); the build stops when a root doesn't fit. Tested on a Pi 3B; Pi 4 and 5 read `autoboot.txt` from their EEPROM and should work the same, but haven't been tried. p1 (the Pi 3 firmware and `autoboot.txt`) is renewed by `update-p1`, the last step of `mirrordash-mark-good`: on a Pi 3 it is p1's `start.elf` that boots a slot, so the slots' own firmware files are never used there, and without it a Pi 3 would keep the firmware it was flashed with while each system update brings a newer kernel (Pi OS ships them as a pair). When the running, just proven slot's `bootcode.bin`, `start.elf` or `fixup.dat` differ from p1's, the script builds a new p1 in the 32 MiB left empty after it (a loop device over that half: `mkfs.vfat`, the firmware, and `autoboot.txt` as it is now), checks it file by file, and moves the MBR's p1 entry over in one 512-byte write (`sfdisk -N 1`). A power cut before that write leaves the old p1, after it the new one; the old half stays as a way back by hand. A failure there never undoes the system update (the unit's `-`), it only leaves a `p1-update` saved log. Not RAUC's `boot-mbr-switch`: it writes p1 from the bundle, `autoboot.txt` included, and so forgets which slot is the good one. What remains: a new `start.elf` can't be tried before it's used (tryboot is p1's own feature), the same as on every Pi running Raspberry Pi OS, where it is overwritten in place.
* **An app crash on a trial boot**: `launch.sh` doesn't roll MirrorDash back when `rauc-bootloader is-update-trial` says this is the trial boot of a new OS: it keeps failing, `/health` never answers, mark-good gives up and the mirror goes back to the old OS with the app as it was. *Rationale*: on a trial boot the crash is the new OS's doing; the rollback downgraded the app for good, and when that failed too, Safe mode answered `/health` and got the broken OS kept.
* **Frozen in every image**: how a mirror installs an OS update can't change once an image is out: the sudo rule for `rauc install /storage/mirrordash/os-update.raucb`, `compatible=mirrordash-rpi`, the `verity` bundle format, the slot classes `rootfs` and `boot`, the certificate in the keyring, and the bundle name `mirrordash-os-v<version>-<YYYYMMDD-HHMM>.raucb` the app looks for. Changing one leaves the mirrors out there unable to install the update that would change it on them, so only reflashing helps; if one must change, the old way keeps working next to the new one until no older image is left. `tests/test_ab_updates.py::test_the_os_update_interface_stays_the_same` holds them.
* **Logs of failed updates**: The system log stays in RAM, so nothing is written to the SD card all day and it doesn't wear out (a journal kept on the card would write every few minutes, and a small write can cost a whole erase block). The price is that the log is gone after a restart, which is exactly when an update has failed. So `save-log` keeps a copy at that moment: a trial boot that fails (`mirrordash-save-trial-log`, before it restarts into the old slot), a failed `rauc install`, and an app update that `launch.sh` rolls back. The newest 5 are kept under `/storage/mirrordash/logs/`, listed under **Logs → Saved Logs**, and can be downloaded and deleted there. A kernel that doesn't start or finds no root runs no program, so nothing can be saved then; the admin page says the update didn't start.
* **Log times are UTC**: The app's log (ISO 8601 with `Z`, `main.py`), the system log in the Logs tab and the saved logs (`journalctl --utc -o short-iso`) and saved log file names all use UTC, so lines from different logs line up without a time zone or summer time in the way. Times written for people in the admin page (when a log was saved, until when developer logging is on) are local. A Pi has no clock battery: until NTP has set the time, every time is wrong whatever the zone.
* **Developer logging**: For working on a mirror, **Settings → Developer → Developer logging** keeps the whole system log on `/storage` across restarts: a drop-in in `/run` sets journald to `Storage=persistent` (after Pi OS's own `Storage=volatile`) and `/var/log/journal` is bind-mounted from `/storage/mirrordash/journal` (`mirrordash-dev-logging`, at boot and hourly). Off by default and off by itself after 7 days, so a forgotten switch doesn't wear the card for years; capped at 64 MB. The image's machine-id is `uninitialized`, so every start gets a new one and its own journal folder, which journald alone doesn't trim: the script deletes the oldest starts' folders beyond the cap, and the Logs tab reads them merged (`journalctl -m`). Whether it's on is a file on `/storage` holding when it turns off, so it works at boot before the app runs.

## 32. Sound and Hardware Video: a Lean GStreamer in the Image, Played Outside the Browser
* **Decision**: The image carries GStreamer's base, ALSA and GL plugins and `gst-launch-1.0`. From the good and bad sets it carries only the plugins for radio, TV and camera streams (`step_media` in `configure_image.sh`): `video4linux2` (the Pi's H.264 decoder, `/dev/video10`), `adaptivedemux2` (HLS), `isomp4`, `audioparsers`, `mpg123`, `soup` (HTTP), `icydemux` (Icecast radio), `videoparsersbad` (`h264parse`), `waylandsink` and `faad` (AAC). They are copied out of the .debs, with the libraries they need installed by name. The build fails if any of them doesn't load. A module plays media by starting `gst-launch-1.0` (for example `playbin3 uri=…`) as user pi, with `WAYLAND_DISPLAY=wayland-0` and `waylandsink fullscreen=true` for video and `alsasink` for sound; the video covers the mirror while it plays.
* **Rationale**: Modules can't bring system packages: a module is a Python package on `/storage`, and the root is read-only and replaced on every OS update. So what modules need for media has to be in the image, and it has to be small, since every MB is in every OS update. The full good and bad sets plus libav came to 277 MB, mostly unrelated libraries: plugins-bad pulls in ONNX runtime, oneDNN, LAPACK and GTK 3, and libav pulls in x265 and libavfilter. The chosen set is about 12 MB (13 packages and 2.4 MB of plugins), and `faad` decodes AAC instead of libav. Tested on a Pi 3B (2026-10-19), with only these plugins, an SVT live stream played on the hardware decoder at 50 fps, 1080p included (fullscreen, below), at 30–50 % CPU; Sveriges Radio played at about 8 %. In Cog the same stream ran at 3–5 fps with both cores full. WebKit decoded it in software: its web process runs in a bwrap sandbox that most likely hides `/dev/video10` (unproven; the sandbox stays, it guards the mirror against harmful pages). WebKit also blocks sound that starts without a tap, and a mirror has no one to tap.
* **Video must be fullscreen**: only then does wlroots put the decoded frames straight on a display plane (the Pi's hardware scaler does the scaling, as in Kodi) instead of compositing them with the mirror's page on the GPU. Measured on the Pi 3B: SVT 540p, 720p and 1080p at 50 fps, 0 dropped, fullscreen (the plane shows `YU12` in `/sys/kernel/debug/dri/0/state`); in a window, 540p dropped about one frame a second and 720p reached 35–40 fps. Decoding alone (`fakesink`) holds 50 fps at 720p, so the decoder was never the limit. A 50 fps stream on a 60 Hz screen still jerks every fifth frame: switch the screen to 50 Hz while playing (`wlr-randr --mode …@50Hz`, only a mode the screen lists, and back afterwards).
* **Video in a window** is composited by labwc on the GPU, and that holds 50 fps only while the page behind is still: a blank page dropped 2 frames in 40 s, but a page that changes one number a second drops about one frame per change (39–55 in 40 s, the clock's seconds on the mirror page gave 26). Every repaint of the page takes the Pi 3's GPU long enough for labwc to miss a video frame. Painting the page on the CPU (`WEBKIT_SKIA_ENABLE_CPU_RENDERING=1`) brought it to 15–21; WebKit's damage features (`--features=+PropagateDamagingInformation,+UnifyDamagedRegions`) made no clear difference. labwc doesn't put windows on display planes (wlroots' `wlr_output_layer` is unstable and unused), so a smooth window needs the page to hold still while a video plays. Weston 14.0.2 (Trixie) does put windows on planes: tested in RAM on the mirror (2026-10-20), with the desktop shell, the video window (`YU12`, 960×540) and Cog's page each got their own plane, and the ticking page cost 6–8 dropped frames in 35 s instead of 39–55. Its desktop shell crashed at once in the plane code (`drm_output_find_plane_for_view: Assertion 'fb' failed`) with a plain background colour, and ran with a background image. Weston has no `wlr-randr` (rotation, resolution and screen off at runtime) and lets no client place its own window. What decides it under labwc is how much of the page the GPU redraws, and at what resolution. Measured on 2026-10-21 with the real mirror page (only the clock, with seconds), SVT1 at 360p in a quarter-width window in the bottom right corner, 90 s each: 1920×1080@50 dropped 67 frames (1.5 %), 1280×720@50 (the monitor scales up) dropped 5, and 1920×1080@50 with the clock's seconds off dropped 11 (0.25 %). The whole Pi used 8–15 % CPU and stayed at 60–62 °C in all three, so the limit is the GPU's time, not the CPU. The window is placed with a labwc window rule on its app id, which is the program's name (`gst-launch-1.0` for gst-launch; `g_set_prgname` sets it in a player of our own), not a GStreamer name; without a matching rule labwc centres the window at the video's own size. A player must take only the video and audio from SVT's playlist: with the subtitle rendition left unlinked, `uridecodebin3` sometimes hung in preroll.
* **Video inside the page** works once WebKit can reach the decoder. Tested with the sandbox off (`WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1`, a few minutes, our own page; 2026-10-20): `<video>` with hls.js used `v4l2h264dec` and dropped 0 frames at 540p, 720p and SVT1 1080p, also with a number ticking on the page. The web process used 60–80 % CPU (120 % at 1080p) and the Pi reached 75 °C. SVT2 at 1080p dropped 31 %, so 720p is the safe level. With the sandbox on, the decoder isn't visible and WebKit decodes in software. The reason: WebKit 2.48 (Trixie) binds only `/dev/video0`–`video2` and `/dev/media0` into the sandbox, and the Pi's decoder is `/dev/video10`. WebKit binds every V4L2 node from 2.52 on ([bug 311007](https://bugs.webkit.org/show_bug.cgi?id=311007); 2.54 is in forky, not in Trixie or its backports). Loading the decoder as `/dev/video0` (`bcm2835_codec decode_video_nr=0`) is enough: tested with the sandbox on, WebKit then used `v4l2h264dec`. The frames that come late show only with `requestVideoFrameCallback` (`getVideoPlaybackQuality` said 0 dropped while a viewer saw the hitches): at 720p, gaps over 45 ms came about every two seconds with a still page and about once a second with a number ticking each second. Putting the number on its own layer, changing it right after a video frame, or painting on the CPU didn't remove them. The web process used 75–88 % CPU at 720p, most of it the hls.js/MSE path (75 °C). WebKit's own HLS (no hls.js) is off in 2.48 unless `WEBKIT_GST_ENABLE_HLS_SUPPORT=1`, and then takes only the old `hlsdemux` (plugins-bad), not `hlsdemux2`, also with `WEBKIT_GST_USE_PLAYBIN3=1`. With it, and with `deinterlace`, `videofilter` and `audiofx` added (`Missing element 'deinterlace'` otherwise), SVT played at about 8 % CPU on `v4l2h264dec`, but the picture stayed on its first frame while the time ran on; without the audio and subtitle renditions too. That path is a dead end on 2.48. Sound still needs a tap: WebKit pauses video that unmutes by itself.
* **Sources and sound**: SVT's channels come from `https://api.svt.se/video/ch-svt1` (`svt2`, …): HLS without DRM, geo-blocked to Sweden, every variant from 252p to 1080p at 50 fps, with audio and subtitles as separate renditions. Sveriges Radio is a plain MP3/AAC stream (`https://www.sverigesradio.se/topsy/direkt/srapi/132.mp3` redirects to `live1.sr.se`; about 8 % CPU). Set the volume on the hearing scale (`amixer -M -c Headphones sset PCM 35%`): the raw scale's 20 % is −81 dB, silent. The volume lives in the RAM root and is lost at a restart. The Pi 3's 3.5 mm output is PWM and a little noisy.
* **Other compositors and strategies**: Set-top boxes running WPE (RDK, Metrological) use hole punch: the page draws a transparent hole at the `<video>` and a platform sink (`westerossink` under the Westeros compositor) puts the picture on a plane under it, at the rectangle WebKit passes it. Trixie's WPE 2.48 has it built in (`WEBKIT_GST_HOLE_PUNCH_QUIRK=westeros`), but Westeros isn't in Debian (not tried). Kodi owns DRM itself and puts its menus and the video on separate planes, which is why it plays smoothly. Cage is wlroots like labwc, so it costs the same, and it shows one client at a time. Pure DRM (`cog -P drm` beside `mpv --vo=drm`) can't work: only one process can be DRM master, and the screen can then only be turned off over CEC. vc4 rotates planes only 0°/180°, so on a portrait mirror (90°) video always goes through the GPU, whatever the compositor (not measured).
* **Where this leaves video (2026-10-20)**: a TV module should play fullscreen in its own GStreamer process, with the screen switched to 50 Hz while it plays. Optionally it plays in a window over the module's card (a labwc window rule), with the screen at 1920×1080@50 and the other modules holding still while it plays (or the screen switched to 1280×720@50). A window that stays smooth while the rest of the mirror updates needs WebKit 2.52+ (video in the page, the decoder in the sandbox) or a Pi 4/5. A heatsink is cheap headroom behind the glass: the Pi 3B idles at about 51 °C.
* **Limits**: Streams with DRM (TV4, Netflix) can't play. Copied files aren't in dpkg's database: they are refreshed when an image is built, not by apt, which never runs on a mirror anyway.

## 33. Modules Update Once a Minute While a Video Plays
* **Decision**: A module that plays a video wraps the playback in `async with self.video_is_playing():` (injected like `fetch`). While any module plays, the websocket manager (`kiosk/ws.py`) holds the other modules' updates and sends the latest of each on every whole minute, and at once when the last video stops; the playing module's own updates go out as usual. The page (`js/kiosk/core.js`) hears `{"type": "video_is_playing"}` (and the state in `hello`), puts `data-video-is-playing` on `<html>` and on every module's host, fires the `mirrordash:video_is_playing` event, steps the carousels on the minute without their fade (one a minute at most; a slower one keeps its pace), and `modules.css` pauses every animation and transition inside the modules. A module's own timers are its own: while the attribute is set, nothing on its card should change more than once a minute, on the minute (the clock hides its seconds and ticks on the minute).
* **Rationale**: Under labwc, every redraw of the page costs the Pi 3's GPU about one frame of a video window (#32): the clock's seconds alone dropped 67 frames in 90 s at 1080p50, 11 without them. Gathering every change on the same moment gives one short hitch a minute, which the owner accepted, without switching the screen to 720p. The name says when and why a module should adapt, so it means nothing else (not the screen being off, which #29 covers). Rewriting the page's `setInterval` and `requestAnimationFrame` for the modules was rejected: hidden, and it breaks modules in ways their authors can't see. Modules that ignore the signal cost a few frames, not a broken page.

## 34. A Module's Video Window: the Core Places It, the Module Plays It
* **Decision**: The core only gives a video its place; the player and what it plays belong to the module. A module wraps its own player in `async with self.video_window(fullscreen=False, hz=None) as window:` (injected like `fetch`). The card marks where the video goes with an element carrying `data-video-window`; the core asks the mirror's own page for its place (`{"type": "video_window"}` over the websocket; only a loopback client's answer counts), writes a labwc window rule for the app id `window.app_id` (`mirrordash-video`) into `~/.config/labwc/rc.xml` at that place, reloads labwc (`SIGHUP`), switches the screen to `hz` when the current resolution has that rate (50 for European TV), and holds `video_is_playing` (#33). When the block ends, also by an error or a cancel, everything is put back. One video window at a time; a second waits. The OS image gives the libraries: the lean GStreamer of #32 and its Python bindings (`python3-gi` and the GStreamer typelibs, about 3 MB), so a player runs on the system's Python (`/usr/bin/python3 -I`), which has them; the app's own Python (uv's, in the venv) doesn't.
* **Rationale**: Only the core may write the system's files and change the screen's mode, and only the page knows where the card is, so the place follows the layout like any module's. What to play and how (sources, playlists, YouTube) changes with the sources and ships with the module that knows them. A first version played the video in the core too (`play_video`, commit 776ceb4) and was split this way on the owner's call: the core stays small, and a second video module brings its own player.
* **For a module's player** (measured 2026-10-21 on the Pi 3 with SVT1): `gst-launch-1.0` doesn't do: its window's app id is its own name, and with SVT's subtitle renditions it hung in preroll (`uridecodebin3`) or waited about 20 s before the first frame (`playbin3`). A small GStreamer player in Python works: `GLib.set_prgname(window.app_id)` for the app id, `playbin3` with `waylandsink` (`fullscreen` from `window.fullscreen`) and `flags` video+audio. hlsdemux2 holds the first frame some 18 s when the master playlist has a subtitle rendition, whatever streams are selected; with the subtitle renditions removed from the playlist (and its addresses made absolute) SVT1 starts in about 1.5 s. The player from commit 776ceb4 (`mirrordash_core/features/video/play.py`) does all of this and is the starting point for a TV module.
* **Limits**: The window's place is taken when the block starts; a card that moves while it plays leaves the video where it was. A carousel that hides the card doesn't hide the video. vc4 rotates planes only 0°/180°, so on a portrait mirror the window is composited like any other (#32).

## 35. Matter: a Node.js Sidecar That Runs the Screen Through /api/v1
* **Decision**: The mirror is a Matter device: its screen is an on/off light (`OnOffLightDevice`), nothing else. The node is `matter/index.mjs`, a small matter.js program installed in the image at `/opt/mirrordash-matter` (`step_matter`, Debian's `nodejs`, `npm ci` from the pinned lock file, then npm removed) and run as `mirrordash-matter.service` (user pi). It only talks to `/api/v1` (#24) on localhost: `GET /status` every 2 s for the screen's state, `POST /screen` when a home app turns it on or off. It is paired over the network (mDNS, the mirror is already on Wi-Fi), without Bluetooth. The core runs it from `features/matter`: turning Matter on makes the pairing codes once per mirror (random passcode outside the spec's forbidden ones, random discriminator, and the serial number and UniqueID `mirrordash-<8 hex>`, which a pairing reset makes anew as the spec asks, in `config["matter"]`), and on every start a new token, of which only the hash is kept (`config["matter"]["token_hash"]`, accepted by `require_api_token` beside the API card's), written with the codes to `~/.mirrordash/matter.env` (0600) for the unit's `EnvironmentFile`; then `sudo systemctl restart mirrordash-matter`. The unit isn't enabled: `/etc` is a RAM overlay (#5), so the core starts it at its own start when the config says so, like SSH. The node keeps its fabrics in `~/.mirrordash/matter/` and writes `pairing.json` (QR payload, manual code, commissioned) there, which the admin page's Matter card shows (QR drawn by the same `qrcode.js` as the Wi-Fi setup).
* **Rationale**: matter.js was the only library that can be a device (not only a controller) and complete pairing over IP with Apple, Google, Alexa, SmartThings and Home Assistant; the Python ones couldn't (CircuitMatter doesn't finish commissioning, `chip-core` only controls). A sidecar on the public API keeps Node out of the core and gives it no more power than a Home Assistant token. Its own token means a new API token doesn't unpair anything, and a token made anew at each start never has to survive a restore. The files sit next to `data/`, not in it, so a backup carries neither the pairing keys nor the token.
* **Limits**: Uncertified (test vendor `0xFFF1`, product `0x8000`): the apps warn, and Google Home needs a Developer Console project with those IDs (user guide). A change on the mirror reaches the apps up to 2 s late (polling; a push from the event bus is the upgrade). It costs about 90 MB in the image (Node.js about 70, matter.js trimmed to its ES modules about 20) and about 100 MB of RAM while on (measured on the Pi 3B, 2026-10-12). The node is updated with the OS image, not with app updates. Brightness and the sensors (occupancy, temperature, lux) would be more endpoints on the same node; left out until asked for.

## 36. The App's Root Rights: Fixed Commands, a udev Rule and polkit
* **Decision**: The app runs as `pi`, and every root action it needs is either a sudo rule for one fixed command (`scripts/image/rootfs/etc/sudoers.d/`), a file the `video` group may write (the backlight, `90-mirrordash-backlight.rules`), or a polkit rule (NetworkManager, `50-mirrordash-networkmanager.rules`, so `nmcli` runs as pi). Where a command needs input, a root-owned helper takes it and checks it: `mirrordash-pi-password` reads one crypt hash on stdin and sets only pi's password; `mirrordash-gpio-overlays` takes a fixed vocabulary. A `*` may only end a sudo rule (`tests/test_configure_image.py::test_sudo_rules_give_no_way_to_root`).
* **Rationale**: Modules run in the app's process, so whatever the app may do as root, any installed module may too. A bare `chpasswd` let it set root's password, and the `*` in `tee /sys/class/backlight/*/brightness` matches spaces, so tee could be handed any file; `sudo nmcli *` could read any file as root (an import, a certificate path). The fixed rules make the sudo list the real boundary it looks like.
* **Limits**: A module still has everything pi has: the owner's settings, the network, the admin password's hash. The admin page marks official modules and warns before others (#26). The build removes Pi OS's own `010_pi-nopasswd` (`pi ALL=(ALL) NOPASSWD: ALL`) and takes pi out of the `sudo` group; with them left in, every rule here was moot. Where a sandbox would have to go: #38.

## 37. The Mirror Stands Still Between Updates; a Dark Screen Draws Nothing
* **Decision**: Nothing on the mirror moves forever. A list that doesn't fit steps: one item slides up (a short `transition`), then it stands still for a few seconds (the news module since 1.2.1). `mirrordash-sdk validate` warns hard about an `infinite` CSS animation or a `requestAnimationFrame` loop, and mildly about `infinite` with `steps()`. The core has no pause for a dark screen: it isn't needed.
* **Rationale**: Measured on a Pi 3B at 1080p (2026-10-23): the news module's endless scroll (`linear infinite`, under a `mask-image` fade) made WebKit draw 60 frames a second all day. The compositor thread took 17 % of a core, labwc 13 %, cog 6 %, a kernel thread waited on page flips (load ~1.6 on an idle CPU), the CPU stayed at full clock and the Pi sat at 66 °C; with the scroll stepping instead, 54 °C. A smooth scroll with `steps(N)`, one whole pixel per step, no mask (the fades as still gradients on top) and `will-change: transform` drew only when it had moved a pixel: 28 flips a second at 28 px/s, about a quarter of the cost (WebKit 7 %, labwc 2 %, cog 3 %), but never free. A still page draws nothing. With the screen off the output is disabled (`wlr-randr --off`), labwc asks for no frames and WebKit drew nothing even under the endless scroll (0 % and 0 flips), so pausing animations for a dark screen would save nothing; a module's own timers keep running, at no measurable cost.

## 38. Locking Modules Down: Where the Boundary Has to Be
The analysis (2026-10-24). Built since: step 0, step 1 and the screen, in #41; "Today" below is how it was.

* **Today**: A module is Python in the core's own process, as `pi`, in the core's venv (`features/modules/loader.py`). It can import and patch `mirrordash_core`, read `config.json` (every module's API keys, the admin password's hash, the API token's hash), `matter.env` (the Matter node's token in plain text) and the session store, start a login session itself, run every sudo rule of #36 (reboot, factory reset), change the network through polkit, and read GPIO, I²C and input devices. Its build backend already runs as `pi` when it is installed. Nothing limits its network: no firewall (uvicorn listened on `0.0.0.0:8000` too, until step 0). Its HTML and JS run on the screen as a global script (the shadow root scopes only CSS and DOM, #21) on the same origin as `/admin`, `/api/v1` and `/ws`, with no Content-Security-Policy, so it can call the routes that trust loopback (`/admin/auto-update`, `/api/wifi/changed`, the hotspot password on the index page) and reach every device on the home network from the browser.
* **The boundary has to be a process and a user**: In the core's process every limit is voluntary: a module can undo any check written in Python next to it. Only the kernel can hold a line, so a sandbox means the module runs in another process, as another user.
* **Steps, cheapest first** (a Pi 3 has 1 GB; one more Python process is ~30–40 MB):
  * **0. Hygiene, independent of a sandbox**: no root shortcuts for `pi` (done: #36); uvicorn on `127.0.0.1` only, behind nginx (done); a token besides "from loopback" for the routes the OS calls (done with step 1, #41: in the core's process a module could read any token the core can).
  * **1. One module host**: all modules in `mirrordash-modules.service`, as its own user (`mirrordash-mod`), talking to the core over a unix socket: the core sends each module its own settings and forwards the events it may see; the host sends back HTML and events. systemd does the rest: `ProtectSystem=strict`, `ProtectHome=yes`, `ReadWritePaths=` the module data only, `PrivateDevices=yes`, `NoNewPrivileges=yes`, `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`, `IPAddressDeny=localnet` with `IPAddressAllow=` for what a module declares. This keeps the core, the secrets, the hardware and the home network away from modules, but not modules from each other. A video module needs the Wayland socket: a declared permission.
  * **2. A process per module**: a template unit `mirrordash-module@.service` with `DynamicUser=yes`, `StateDirectory=`, and the network rules from what the module declares in its `pyproject.toml` (`network = ["internet"]`, `["lan:192.168.1.10"]`, `hardware`, `video`), shown to the owner at install like a phone shows an app's permissions. N × ~30 MB: heavy on a Pi 3, unless forked from one preloaded process (#41's limits: ~2 MB each).
  * **The screen**: the admin page and the API on their own origin (another port), and a CSP on the kiosk page whose `connect-src` comes from the modules' declared hosts. An iframe per module would isolate its JS fully but breaks the shadow-root design (#21) and costs a document each.
  * **Install**: require built wheels (`uv pip install --no-build`), or build as the module user, so installing runs no module code as `pi`.
* **Recommendation**: step 0 now; step 1 when modules by others are in real use; step 2 only if the permission model is wanted. The big cost is the SDK: `broadcast_func` and the injected helpers become calls over the socket. The host can inject the same helpers, so modules keep their source.

## 39. Backups: Encrypted Ones Carry the Logins, and a New Mirror Can Start From One
* **Decision**: A backup is a zip. Without a password it holds no secrets: the config without `admin_auth`, no `pi_password.hash`, no Wi-Fi. With a password the whole file is encrypted with `openssl enc -aes-256-cbc -pbkdf2 -iter 600000` (the password in the environment, never on the command line) and also holds the admin password, the pi password and the saved Wi-Fi networks with their passwords (`wifi.json`, read with `nmcli -s`, which polkit's `settings.modify.system` allows). A restore takes the backup's admin password when it has one. Never in a backup, either way: `sessions.json` (a login cookie must not work on another mirror), `config.json.bak` and `config.json.broken-*` (they hold what a plain backup leaves out). Modules are restored into the next A/B venv (#16). The Wi-Fi setup page restores an encrypted backup too, while the mirror has no admin password (the same rule as the rest of that page): it joins a network from the backup first, since the modules come from GitHub, then restores.
* **Rationale**: Setting a mirror up again (a new card, a second mirror) should be one step. ZIP's own encryption (ZipCrypto) breaks with a known-plaintext attack, and a backup's layout is known, so it couldn't carry Wi-Fi passwords in plain text. openssl is in the image already, so no dependency. Before an admin password exists, anyone near the mirror could set it up anyway, so restoring from the setup page opens nothing new.
* **Limits**: CBC without a MAC: a changed file fails as a broken zip rather than being detected (upgrade: openssl's AEAD modes). Backups from before this (ZipCrypto) can't be read; no compatibility before 1.0.

## 40. A Module's Own Routes: Under /api/modules/<instance>, Nowhere Else
* **Decision**: A module that sets `self.router` (a FastAPI `APIRouter`) is served at `/api/modules/<instance>/...` by one ASGI app mounted there (`module_routes` in `features/modules/loader.py`), which looks the running instance up on every request. The module gets the path as `config["api_path"]`. The core puts no login in front: the module checks its callers itself.
* **Rationale**: Modules talk to devices on the home network (an ESP32 posting a reading, a phone shortcut flipping a relay), and a fixed prefix means a module can't add or shadow a route of the core, the way `app.add_api_route` from inside the process could. Looking the instance up per request needs nothing on a reload, and a disabled module is a 404. An `APIRouter` is what the module host of #38 step 1 can serve over its socket too, so modules keep their source when the sandbox comes.
* **Limits**: The routes run in the module host (#41): the core sends each call over its socket and the host runs it through a FastAPI app around the router. HTTP only (no WebSockets), 1 MB in, 4 MB out, 30 s. GPIO: the host's user may open `/dev/gpiochip*`, I²C and SPI (#41); the pins the core's overlays hold (buttons, PIR) stay busy in the kernel.

## 41. Modules Run Apart From the Core, Each as a User of Its Own
* **Decision**: Every module instance runs in the module host (`features/modules/host.py`, `forkserver.py`, `mirrordash-modules.service`), in a process of its own as a user of its own (uid 70100 and up), never in the core's process. The unit's main process is a forkserver; its first fork, the control process (the unit's user `mirrordash-mod`), answers the core's connection on the unix socket (`/run/mirrordash-modules/host.sock`, through the group `mirrordash-mod`, which pi is in): the users, the site's steps and the sandbox's checks. To start an instance the core (`client.py`) makes two socket pairs and passes one end of each over the second connection (`host.sock.fds`); the forkserver gives them to the instance's new process, so **its connection is who it is**: the core sends it its own settings only (`config["modules"][instance]` and `globals`, never the rest of config.json), the screen going on or off, hardware events and calls to `/api/modules/<instance>/`, and takes from it its HTML (placed by the core: position, carousel), its GPIO requests, its public events (`event_bus.publish(..., public=True)`: the core passes them to every instance, never to its own subscribers, only named `<its package>.…`, 64 kB and 20 a second at most; a plain publish stays in the instance's process) and its log lines (under `mirrordash.modules.<instance>`, whatever name it gives), checked as input from outside, whatever instance a message names. A changed setting restarts that instance alone (a move on the screen none); the cards of the others are sent again to the reloaded screen. The protocol is in host.py's docstring. The core never imports a module: schema, icon and translations are read as files (`package_dir`, which finds a package without running it), and the upgrade check imports the modules in the host. When the core goes (a restart, an update) the instances' connections close and they stop, the control process exits and with it the forkserver; systemd starts it again with the venv there is now. Off a mirror (development, the SDK's `start`) the core starts the host as its own child: the same processes, as the developer's user, without the sandbox.
* **The sandbox** (the unit): the system read-only, its own folder writable (`/storage/mirrordash/modules`: data_dir and cache_dir), the core's data dir (0700 and InaccessiblePaths), its logs and the SSH and Wi-Fi keys out of sight, no D-Bus, NoNewPrivileges, only the system calls of `@system-service`, and of the capabilities only `CAP_SETUID CAP_SETGID CAP_CHOWN` (ambient), which only the forkserver keeps (below). Devices: I²C and SPI only (DevicePolicy=closed; the unit's user is in i2c and spi, and the instances' processes keep those two groups), and of the I²C buses only the header's, `i2c-1` (a udev rule gives the others to root: one is the screen's DDC/CI, brightness and power; ddcutil runs through sudo). No GPIO chip and no gpiomem: a chip is every one of its lines, the SD card's and the core's too, since the Pi's pin control isn't strict and a line can be taken from I²C or the SD card, and gpiomem maps the registers (the Pi kernels have no gpio-aggregator to give out a part of a chip). A module asks for pins instead (`await self.gpio([27], output=True)`, `features/hardware/gpio.py`): the core requests exactly those lines with the kernel's v2 ioctl, if they are free header pins (GPIO 2–27, not a Hardware tab device's, not I²C's while an I²C device is set up), and sends the request's file descriptor over the instance's own descriptor socket (SOCK_SEQPACKET, SCM_RIGHTS: a stream drops it). That descriptor drives those lines and no other; the instance releases them when its run_loop ends. Network (written as addresses and systemd's own names only: it skips a word it doesn't know, like `localnet`, with a mere warning, and the first image left the home network and loopback open that way; `test_ip_filters_name_only_what_systemd_knows`): IPAddressDeny of the home network, of the mirror itself (127.0.0.0/8: the core's routes that trust loopback) and of IPv6 (a device at home can have a global address); IPAddressAllow of systemd-resolved's stub (127.0.0.53: why resolved is in the image, as the router is usually the DNS server) and of the addresses the owner typed in settings marked `"format": "lan-url"`, each to its own instance's user: the core runs `mirrordash-module-network <uid>=<address> ...` through sudo at every start and every 10 minutes; it lets through only the modules' users and home-network addresses, opens their union to the unit (IPAddressAllow) and keeps each to its user with nftables (`meta skuid <uid> ip daddr <address> accept`, then those addresses refused to the host's other users `with icmpx admin-prohibited`: a plain reject reads as "refused", which the self-check counts as reached). Never the mirror itself, whatever was typed (its own LAN address or `mirrordash.local` would open nginx, SSH and Matter to the module): a first rule refuses the modules' users every address the kernel calls local (`fib daddr type local`, every interface, a DHCP change included) but resolved's stub, checked in a network namespace. MemoryMax (30 %, no swap) and CPUWeight, so a runaway module can't take the core and the screen with it; the Pi's firmware turns the memory controller off (`cgroup_disable=memory`), so the image's cmdline.txt turns it on again (`cgroup_enable=memory`). At the limit the kernel kills one process (`OOMPolicy=continue`), an instance's first (`oom_score_adj` 500); the core starts it again and, after `CRASH_LIMIT` (3) deaths in a row each within `CRASH_WINDOW` (5 min) of its start, leaves it off with the Dashboard's *Start Modules Again*, naming it, while the others run on. Fixed uids (960, 70000 and up): `/storage` outlives the OS image. The core (pi) reads and writes the host's folder only for backups, and follows no symlink there: one the host put in would have pi copy the core's data into the backup, or delete and write in it on a restore.
* **The screen**: Cog may reach the mirror and the internet, not the home network. The page gets a CSP: pictures and video from anywhere, but `connect-src 'self'` (no fetch or WebSocket elsewhere), no frames, forms or plugins, and only scripts with the page's nonce (new each load). core.js gives it to a card's `<script>`s only if its module may run them (`scripts_allowed`: one in the core's venv, the image's clock or a developer's, or one whose site folder's name is in config's `module_scripts`: put there when it is installed from `OFFICIAL_OWNER`'s GitHub, taken out when one of that name comes from anywhere else or it is uninstalled, and switched by the owner in its settings); another card's scripts are removed, and its `onerror=`, `javascript:` or `<iframe srcdoc>` don't run (tested in WebKit). *Rationale*: a script in the page reaches every card (a closed shadow root doesn't stop it: it can patch `attachShadow` or read the WebSocket), so it could send what the calendar or Home Assistant shows to the internet; `frame-src 'none'` because a frame of a page of this site's runs its scripts with the page in reach. Iframes per card would have isolated even the allowed ones, for about 2 MB a card on the Pi 3B (measured, nine cards) and a layout that has to measure each card; the owner's yes was chosen instead. Whether a module is MirrorDash's own comes from the install target, never from where its folder says it came from (`direct_url.json`, Project-URL): those are the module's own to write. The routes the OS calls (`/admin/auto-update`, `/api/wifi/changed`) want the core's `local-token` (in its data dir, new at every start) besides loopback: a module's card runs JS on loopback too. The page and its WebSocket are the mirror's own (`on_screen`: loopback, which the kiosk reaches without nginx; through nginx uvicorn sees the real address, the rightmost of `X-Forwarded-For`); another browser gets a redirect to the admin page. So a card's script never runs in a browser logged in to the admin page, and the two keep one origin without a port or hostname of their own: the kiosk has no admin session to use, and the token covers the loopback routes. Off a mirror the developer's browser is loopback too.
* **The admin page**: what a module supplies is its author's text. Schema titles, descriptions and option labels are escaped; keys and names that reach ids and JS are only `[A-Za-z0-9_-]` (`SAFE_NAME`, `SAFE_KEY`; an entry point or instance with another name is left out); icon.svg becomes a `data:` URL drawn as a CSS mask. All three ran a module's script in the logged-in admin page before. A module route's answer gets `Content-Security-Policy: sandbox` and no `Set-Cookie`, `Service-Worker-Allowed` (a service worker over the screen's whole site) or `Clear-Site-Data`, and the call reaches it without the owner's `Cookie`.
* **Rationale**: In one process every limit is voluntary (#38); a process and a user let the kernel hold the line, between the core and the modules and between the modules. Not a Python of its own per module (34 MB and 4 s each on a Pi 3B, measured) nor a systemd unit each, least of all on a 512 MB Pi 3 A+: the forkserver has the core's code, fastapi and the venv imported and `gc.freeze()`d, so a fork shares it (about 9 MB of its own in the real unit, against 34 MB, so three to four times less: the nine instances on the test mirror use 92 MB more than one process, see Limits; a fork in the experiment before, which used little of what it inherited, had 2 MB). Keeping the module API as it was (the instance's process injects the same helpers) means no module had to change, except Home Assistant marking its URL `lan-url`.
* **The module site**: modules aren't installed in the core's venv. They live in `/storage/mirrordash/modules/site`, a link the host switches between `site_a` and `site_b` like the core's venv (#16). Each of those holds only links, one per module (`site_b/mirrordash-news → ../pkgs/mirrordash-news_3`), written by the control process alone; each module is installed in a new folder of its own in `pkgs` with its dependencies (`uv pip install --target pkgs/<name>_<n>`, `--no-cache`, then `compileall`), in a process of its own as that module's user (one per module, 70002–70099, kept in `package_uids.json`; the folder is that user's, readable by all, and its `HOME`, with uv's `--no-config`: uv and git read their config from `HOME`, and in the unit's shared `/tmp` another module had planted an index and a git `insteadOf` for the next install, `scripts/sandbox-check`). So a package's build backend, the files its wheel holds and its `.pth` reach that module's folder and process only: never another module's code, the links, the core, the forkserver or another module's process. The core asks for each step (`ModuleHost.packages`: prepare the next site with the active one's links or none, `pip` one module at a time (install into a new folder, linked in only if uv succeeded and the module claims no name another module has; uninstall takes the link out), `check` the modules import from their folders, each as its user, commit or revert); a folder no site links to any more (an older version, an uninstalled module, a failed install) is emptied by its user and removed at the next prepare. The core only reads the modules' files, and only those that really lie in a module's folder or on sys.path (`module_file`: a link put there to the core's data isn't followed): entry points through `importlib.metadata.distributions(path=…)`, a package's folder through `PathFinder`, in the entry point's own folder first (neither runs a `.pth`). An instance's process adds its module's folder alone, after the core's own packages (`site.addsitedir` in `ModuleLoader.start_modules`, only there: it runs the folder's `.pth` files), since `--target` installs every dependency again and a module's copy mustn't shadow the core's. *Rationale*: in one shared site (until 0.9.4) any module's install could change the others' code, its `.pth` ran in every module's process, and a package of a name another module imported replaced that one's for both; `--only-binary` would only have stopped the builds (a wheel's files and `.pth` go where they like) and ruled out modules whose dependencies have no wheel for the Pi. The price: a dependency two modules share is on the card twice (`babel`, about 30 MB), and a mirror from before had to install its modules again (no migration before 1.0). A new Python (#16) gets an empty site built for it in the same step as its venv, and both are switched in together; launch.sh's fallback to venv_old switches back to the old site when the two venvs' Pythons differ (the old site is untouched until the next module change). Local modules restored from a backup go to `modules/local`, where the host can build them. Off a mirror the same, with the site in the developer's `~/.mirrordash/module-data` (a module installed into the venv by hand is found there too). The host checks its own limits when the core connects (`sandbox_checks`, as the self-check's user: what systemd only warns about when the kernel can't filter: the mirror's ports 80 and 8000, the router, the folders it mustn't read, the devices besides the header's I2C bus; and what a user per instance needs: another module's data, writing the site, capabilities left over) and logs an error that shows under Logs when one is open. *Logs → Diagnostics* asks it again (`diagnose`), with what systemd knows of it (memory, restarts, lan-url addresses) and each instance's GPIO lines, and offers it all with the logs, versions, `rauc status` and `systemd-analyze security` as one download, to find a fault without SSH. It needs no right the app doesn't have; the settings aren't in the download. The host answers for itself, so it finds a kernel, unit or mode that doesn't hold, not a module that took the control process over. A `lan-url` setting's default is only a placeholder in the form: saving it unchanged opens nothing.
* **A user per instance** (built and checked 2026-10-25 after an analysis by experiment: a container running it as systemd would with `setpriv`, measured on the Pi, then the real unit under systemd in a container, `scripts/sandbox-check`). The forkserver (`forkserver.py`) runs one thread, imports only the core's code (never the module site's: a package there would run with its capabilities), `gc.freeze()`s it, sets `PR_SET_DUMPABLE` 0 and only forks, on a request from the control process it checks (a kind, a uid of that kind's range, an instance's safe name). A child: every descriptor but stdio and its own sockets closed (a fork inherits the forkserver's), `setgroups` to the unit's groups but `mirrordash-mod` (i2c and spi stay), `setresgid`/`setresuid` to its uid, **its capabilities cleared by hand** (`PR_CAP_AMBIENT_CLEAR_ALL` and `capset` to zero, then checked in `/proc/self/status`: changing from one non-root uid to another keeps them, and without the clearing a module became uid 0 again in the experiment), `PR_SET_PDEATHSIG` after the change (which clears it), dumpable again (non-dumpable, its own `/proc` files are root's) to raise its `oom_score_adj` to 500, no `pycache_prefix` and no bytecode written (the unit's prefix is the forkserver's own; the site's process compiles the site), `HOME` its data folder and `TMPDIR` its cache folder. The forkserver can't signal it (another uid, EPERM without `CAP_KILL`): an instance stops when the core closes its connection, and a thread in it ends the process `STOP_GRACE` (5 s) later, for a loop that never lets it read the close. Its users: one per installed module (70002–70099, uv and its build in its own folder: the module site, above), the self-check's (70001, `probe_main`, which looks at the sandbox as a module would: also another module's data, writing the site or a module's folder and capabilities left over), and one per instance from 70100, kept in `uids.json` in the host's folder and never given to another instance (its data may still be there). Files: the host's folder and its `data` and `cache` 2771 (others may pass, not list; set by mirrordash-hydrate.sh as root, as the sandbox refuses a setgid mode), the site's folders of links and `pkgs` the unit's user's and readable by all (`own_site` at the forkserver's start, which takes back what an older shared site left in them), a module's folder its user's and readable by all (made by the forkserver before that user's first step in it, `o+rX` set while it still owns it: after the `chown` it would need `CAP_FOWNER`), an instance's data and cache folders its uid's in the group mirrordash-mod (setgid from their parent), so pi still reads and restores them through the group and other modules can't; what pi restored belongs to pi, so the forkserver gives the folder back to the instance (by file descriptor: `O_NOFOLLOW`, no link followed, a hard-linked file left alone) before it starts it. Checked under the real unit: uids 70100 and 70101 with all capability sets 0 and `setuid(0)` refused, neither reading the other's data, listing the host's folder, writing the site or `uids.json`, or seeing the forkserver's `/proc`; the self-check 0 of 46 open; a module leaking memory killed by the kernel alone, three times, then paused, the others in the same processes and the unit active; uv installing as the site user. Again with a folder per module (2026-10-26): `six` installed as 70003 into a folder of its own, the links the unit's user's, an instance unable to write its own module's code, and a build backend made to attack (`scripts/sandbox-check/evil`, as 70004) refused writing another module's code, a `.pth` into its folder, a link in either site and a folder in `pkgs`; what an older shared site left (70000's) taken back and removed at the next change; the self-check 0 of 49 open. On an OS image without the capabilities no module runs (they would run as the unit's user beside the forkserver), and the host says to install the system update. The other way round, the unit starts `forkserver` rather than `host`: an app from before it doesn't start at all, where it would have run its modules with the unit's capabilities (seen on the test mirror between the OS update and the app's). Checked on the Pi 3B (v0.9.3-os2): the nine instances as 70100–70108 with no capabilities, the self-check 43 of 43 closed (another module's data included: the control process tells the self-check's user the folders it can't list), both Home Assistant instances reaching 192.168.1.85 through their own nftables rules, and a module taking 400 MB killed by the kernel alone (`CONSTRAINT_MEMCG`, its uid, `oom_score_adj` 500) three times, then paused and named on the Dashboard, the other eleven processes untouched.
* **Limits**: Modules still share the unit: its memory limit (one can use it up before the kernel picks it), its `/tmp` (sticky, each user's own files), the internet and their pins (one can take a line another wanted, first come). `/tmp` and `/dev/shm` are RAM (tmpfs; the root's overlay is tmpfs too) and, with no swap, a file there can't be reclaimed: measured under systemd (2026-10-26), a module that left 130 MB in `/tmp` of a 150 MB unit and exited had the next module that wanted 40 MB killed instead, until the unit restarts (PrivateTmp goes with it); a file in `/dev/shm` (the host's, outside PrivateTmp, and RemoveIPC removes only the unit's own user's) outlived the unit, its memory moved to `system.slice`, outside MemoryMax, until a reboot. ponytail: upgrade path, not built: `TemporaryFileSystem=/tmp:mode=1777,size=…` and the same for `/dev/shm` (private to the unit and capped), with the site's `TMPDIR` on disk for uv's builds. What a module sends the core is bounded, so a bad one can't take the core's memory or its log: a card over 512 kB isn't shown and a card reaches the screen at most every 0.5 s (the last one), log lines past 100 in 10 s are counted, not logged, and a module file the core reads (schema, translations, icon.svg) over 1 MB isn't read. Each module's user may have 256 processes and threads (`RLIMIT_NPROC`, forkserver `TASKS`, only where it has a uid of its own), so a fork bomb stops there. A module's install can change its own folder (its earlier version too) and nothing else; all instances of a module run its one folder's code. What a module reads it can still send to the internet; the owner's choice of modules is the line there. The control process sees every instance's settings, as the core does. Memory, measured on the Pi 3B test mirror with its nine instances (v0.9.3-os2, each process's `smaps_rollup` in a copy of the host run as pi): 167 MB of anonymous memory in the unit, against about 75 MB in one process. Of the 92 MB more: about 50 MB is each process's own copy of the forkserver's pages it touches (an instance with no module dirties 4.7 MB, all of it pymalloc's arenas and the heap it inherited, none in new mappings: reference counts are written whenever a shared object is used, which `gc.freeze()` doesn't stop; ten processes with the control process); about 10 MB the second clock and Home Assistant instance loading their package again; 9 MB `babel` loaded by both calendar and weather (9.3 MB a process); the rest other imports each process makes of its own. Preloading the standard library's modules every instance imports, `gc.disable()` in the instances and `MALLOC_ARENA_MAX=2` each changed the total by less than the run-to-run spread (about 9 MB). Within the 278 MB `MemoryMax` of a Pi 3B; on a 512 MB Pi 3 A+ (30 %: 154 MB) about five instances fit. ponytail: the measured way down is a process per module package instead of per instance (here about 20 MB; instances of one package would share a user). Preloading `babel` (now the core's, for the language list) in the forkserver, its import and the mirror's language before the instances fork, made it 3 MB worse, not 9 MB better (three runs each on the Pi 3B, 156 against 159 MB): a forked instance alone had 0.5 MB of babel of its own instead of 7.8, but most likely every instance copies pages of the larger heap it inherits (not measured); the 50 MB of copied pages has no supported fix (making the forkserver's objects immortal is CPython's internals). **Backups**: unchanged by the users per instance, pi reaching the data through the group (above). The core walks the folder by file descriptors (backup/service.py `copy_out`, `_replace_in_module_folder`: `os.fwalk`, `O_NOFOLLOW` with `dir_fd`, `shutil.rmtree(dir_fd=)`), so a link swapped in while pi copies is never followed. Landlock (a process locking itself to its own folder without a user each) isn't in the Pi's kernel (rpi-v8 and rpi-2712 6.18, checked); nor Yama, which doesn't matter as the syscall filter already blocks ptrace (though not `/proc/<pid>/mem` between processes of one user, hence `PR_SET_DUMPABLE`). A module's card runs in the screen's page, so it can forge what the page reports (`video_window` places for other modules, the heartbeat app-watch reads); it can't reach more than the page itself does. A module can't use gpiod, gpiozero or RPi.GPIO; a change is one ioctl from the module's own process (microseconds), so a slow software PWM works with Python's jitter, but no fast protocol (WS2812). Real dimming would be a Hardware tab device on the kernel's pwm overlay. /storage has no quota, but ext4's reserve (5 %) is pi's too (`resgid=` in fstab), not the modules' user's: a module filling the card leaves the core room to save settings, though not for an OS update's download on a 16 GB card. The modules' folder is a file system of its own, in a sparse file on /storage (`modules.img`, made by mirrordash-hydrate.sh at the first start of an image: `mkfs.ext4` on the file, a quarter of /storage up to 8 GB, with what the folder held moved in; mounted over the folder with `loop,discard,nosuid,nodev` before the core and the host start, `discard` giving back what is deleted in it; growable later with `resize2fs`): a module that fills it gets "No space left" and the card keeps its room. The path stays, so backups don't change, and it works on mirrors that exist. When it doesn't mount, the modules run in the folder below it, without the limit. Not ext4 project quotas: they need `mkfs -O quota,project` (new cards only), a tool to set the limit (`quota` isn't in the image), and the files' owner can most likely move them to another project (`FS_IOC_FSSETXATTR`, allowed to the owner outside a user namespace; unverified), which a syscall filter can't tell apart from other ioctls. Nor a partition of its own: fixed for good, and only on new cards. Video players (#34) need Wayland, sound and the decoder: not in the sandbox, a permission to add with the first video module. A camera at home shows on a card through the module's own route, not from the page. Safe mode runs no modules (the host starts from the active venv), so a module can't be installed or updated there. The IP and device filters, the memory limit and the device groups hold on a Pi 3B (tested 2026-10-25). `ProcSubset=pid` hides the machine's `/proc` files (cpuinfo, meminfo, the kernel's settings) from the host; the host reads its route from `/proc/self/net`, which stays.
