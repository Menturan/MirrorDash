## 1. Peripheral Modular Grid Layout
> **In short:** The screen has nine areas along its edges and the middle stays empty, so the mirror still works as a mirror; two full-screen layers lie under and over them.

* **Decision**: Snaps mirror modules into 9 distinct grid regions (`top_left`, `top_center`, `top_right`, `middle_left`, `middle_center`, `middle_right`, `bottom_left`, `bottom_center`, `bottom_right`), each an absolutely positioned anchor (a flex column pinned to an edge or the centre), keeping the center void clear.
* **Rationale**: Designed for ambient heads-up display (HUD) observation through semi-reflective glass. Centering information is restricted to maintain the primary reflective function of the mirror.
* **Layers** (2026-11-03): two more regions cover the whole screen, `background` (z-index 0, under the nine at 1) and `foreground` (2, `pointer-events: none`, under the connection and offline indicators at 1000 and up). Their cards drop the anchors' near-black card background and padding, which would black out the mirror, and fill the layer; several modules or a carousel overlay (one grid cell). Each layer is its own compositing layer (`will-change: transform`), so a card that changes above a photo shouldn't repaint it (to measure on a Pi 3 with the photo module). The admin map shows a layer as a band of its own only when a module is there. While the background holds a module (`:root:has(#background [data-module])`), the anchors' cards follow the owner's `globals.cards_over_photo` (in the screen message of #45, set on `<html>` by core.js): see-through with a text shadow (default), a soft dark radial glow, half dark, or the usual near-black; without one they stay near-black, so overlapping cards still cover each other. A hard dark card over a photo is a rectangle of glass in it on the mirror. A card in a layer carries `--md-layer-size: 100%`, inherited into its shadow root, so the module's CSS fills the screen there and keeps its box elsewhere (WebKit has no `:host-context`). *Rationale*: a photo behind the clock and seasonal decoration over it are what owners put on a mirror; a region is the core's existing way to place a card, so no module API or permission is new, and the owner chooses it like any position. A module taking the screen with `position: fixed` from an anchor would fight the layout and the other modules.

## 2. Server-Side Rendering (SSR) via Jinja2 & WebSocket Push
> **In short:** Modules make their HTML on the server and the core pushes it to the screen over a WebSocket; the screen only puts it in place.

* **Decision**: Modules run their own event loops on the Python backend, render their HTML templates using Jinja2, and push the fully formed HTML payload to the client via WebSockets.
* **Rationale**: Keeps the kiosk client extremely thin, lightweight, and framework-agnostic. The client only needs to mount and transition raw HTML strings into designated container divs, eliminating complex client-side state managers or rendering libraries.

## 3. Dynamic Module Discovery via Python Entry Points
> **In short:** The core finds installed modules by their Python entry points (`mirrordash.modules`), so a module is an ordinary package, made and installed on its own.

* **Decision**: Rather than hardcoding modules in the loader, the system automatically discovers installed module packages dynamically using Python `importlib.metadata` entry points (group: `mirrordash.modules`).
* **Rationale**: Allows third-party modules to be developed, packaged, and installed completely independently as standard Python wheels or editable packages. The core platform discovers them implicitly on startup.

## 4. Config-Driven Lifespan & Hot Reloading
> **In short:** `config.json` says which module instances run, where and with which settings; saving a change restarts the modules whose settings changed, never the system settings.

* **Decision**: System configurations stored in `config.json` dictate module coordinates, custom properties, and enabled states. The config has been expanded to support multiple instances of the same module type. Each instance is indexed by a unique `instance_id` and contains a `"module"` property to identify the module type. Changes to the config trigger a soft reload: stopping, cancelling, and garbage-collecting running loops, and then spinning up newly configured instances. The reload restarts the modules only: the system settings (screen, time zone, SSH, Matter, the pi password) are applied once at startup (`apply_saved_system_settings_at_startup()` in `features/settings/system_settings.py`, called from the lifespan) and otherwise by each setting's own save. A `run_loop` must be `async def` (a thread can't be stopped on a reload), and one that returns or crashes starts again after a delay that doubles each time, up to 5 minutes.
* **Rationale**: Users can run multiple instances of modules (e.g. clocks in different timezones or positions) and customize their mirror layouts and parameters dynamically without restarting the Uvicorn web server or causing full browser disconnects.

## 5. Read-Only Squashfs Root via overlayroot
> **In short:** The system's disk is read-only and changes to it last until the next boot; everything that must survive a reboot lives on the `/storage` partition.

* **Decision**: The root filesystem is a zstd squashfs under `overlayroot=tmpfs:recurse=0`: `/` is a RAM overlay over the read-only card, and everything that must survive a reboot (settings, module data, the venvs, Wi-Fi profiles, SSH host keys) lives on the separate `/storage` partition, reached through symlinks (`~/.mirrordash`, `~/mirrordash/.venv`), one bind mount (NetworkManager's `system-connections`) and `HostKey` lines. `recurse=0` keeps `/storage` a real mount instead of a second RAM overlay. The build packs the root and writes both kernel parameters (`rootfstype=squashfs`, `overlayroot=`), so a mirror is locked from its first boot. That boot can't leave anything on the root either: the build sets up the `pi` user (not Pi OS's `userconf.txt`), and since the image's machine-id is `uninitialized`, systemd would treat every boot as the first one: it would enable every unit Debian's presets name (SSH, systemd-networkd, Cog without its path unit) and rerun the first-boot units (new SSH keys). `systemd.condition_first_boot=false` turns the first boot off; cloud-init, which sees a new machine every boot, is disabled. The repartition finds the card through `root=` and runs on every boot (a no-op once `/storage` is there). The app writes straight to `/storage` and never remounts anything.
* **Rationale**: The SD card is the part that wears out, and a power cut can't corrupt a filesystem that is never written. A squashfs root is a quarter of the ext4 size (757 MB instead of 3.2 GB for v0.6.2), which leaves room for a second root (A/B OS updates) on an 8 GB card, and the squashfs is what such an update would write. Writing the parameter ourselves instead of `raspi-config enable_overlayfs` is what lets us add `recurse=0`; raspi-config's version made `/storage` a RAM overlay that lost everything at reboot. The initramfs (with overlayroot and squashfs in it) is built in the image, for its own kernels. A run of `configure_image.sh` straight on a Pi stays ext4 and unlocked.

## 6. Hybrid Template Loader Resolution
> **In short:** A module's templates are found inside its package and on disk, so a module installed for development finds them too.

* **Decision**: Implemented a `ChoiceLoader` combining standard Jinja2 `PackageLoader` with a fallback `FileSystemLoader` that resolves physical package paths on disk using `importlib.util.find_spec`.
* **Rationale**: Resolves `TemplateNotFound` errors on PEP 660 editable installations (common in local dev/testing environments like Hatch/uv) where zipped virtual package paths can hide standard template subdirectories.

## 7. Scope Isolation for Dynamic Module Helpers
> **In short:** The helpers a module gets (`translate`, `render_template`, ...) are made for each instance after its constructor, so each belongs to the right instance; they don't exist yet in `__init__`.

* **Decision**: Auto-injected helpers (such as `render_template` and `translate`) are bound to their module instance by `_inject_module_helpers` in `features/modules/loader.py`, called once per instance after the constructor, so they are not available inside `__init__`.
* **Rationale**: Solves Python's loop lexical closure late-binding behavior. Defined inside the loader loop instead, nested helper definitions reference the loop variable by name, resulting in all module instances executing translations and templates using the scope of whichever module loaded last.

## 8. Skeletal Loading UI & Transition Flow
> **In short:** While the screen starts, each module's place shows a placeholder until its first card arrives, instead of a blank screen.

* **Decision**: Added a public unauthenticated `/api/active-modules` API to retrieve active modules list. On startup/refresh, the client fetches this metadata, pre-renders placeholder loading skeletons with visual spinners, and transitions them smoothly using a fade-in animation (`.module-enter`) once the first WebSocket frame for that module arrives.
* **Rationale**: Eliminates the flash of a blank screen on startup/page refresh. It shows at once what is coming while the modules fetch their data.

## 9. WebSocket State Caching for Instant Updates
> **In short:** The core keeps each module's last card and sends them all to a screen that connects, so a reload shows everything at once.

* **Decision**: Implemented an in-memory frame cache (`latest_messages`) inside the WebSocket `ConnectionManager` ([screen.py](mirrordash_core/screen.py)). Every time a module broadcasts an HTML payload, it is cached. Upon a new connection, the manager immediately pushes all cached HTML frames to the newly connected client. The cache is automatically cleared when modules reload or stop.
* **Rationale**: Resolves the delay on page refresh where modules (especially those with long update intervals like the 60-second name day module or hourly updates) would remain as skeletons until their sleep intervals completed and they triggered a new broadcast. Now, refreshed screens load the last rendered frames instantly.

## 10. Carousel Groups for Layout Regions
> **In short:** Modules in one area with the same `carousel_group` take turns in one place on a timer; the others stack.

* **Decision**: Implemented a client-side carousel grouping system (`.carousel-group-container` and `.carousel-slide`). When multiple modules in the same region share the same `carousel_group` string in the configuration, they are rendered inside a single grid container and cycle visibility on a set timer, while ungrouped modules stack normally.
* **Rationale**: Provides users with fine-grained control over which modules cycle and which ones remain static in a region, avoiding rigid full-screen transitions. By using CSS Grid overlaying (`grid-area: 1 / 1 / 2 / 2`), all slides occupy the exact same space, preventing visual layout jumping or shifting during cross-fade transitions, keeping the ambient mirror clean.

## 11. Display Power Automation Strategies
> **In short:** One manager turns the screen on and off: a base mode (always on, a schedule, or off until woken) on the owner's time zone, and one wake timer that sensors, buttons and the admin page start again.

* **Decision**: Integrated a central `DisplayPowerManager` daemon executing alongside the module loader lifespan. It supports time schedules, presence sensors and push buttons, read from kernel input devices (#19), with one wake timer (below). A TV on the cable follows over HDMI-CEC (#55). The Time of Day Schedule mode respects the global timezone configuration (e.g. `Europe/Stockholm`) when fetching the current time, ensuring timezone-aware scheduling.
* **Rationale**: Smart mirrors require automated power conservation. Supporting time scheduling, presence sensors, and buttons allows different hardware setups to save energy automatically. Timezone awareness prevents schedule misalignment if the host machine (e.g., Raspberry Pi) is configured to UTC or another local time.
* **Decision (the wake timer)**: `DisplayPowerManager` combines a base mode (`manual` = always on, `interval` = schedule, `wake` = off until woken) with one wake timer. Presence sensors (if enabled), the push button, the admin page and the open `POST /admin/screen` endpoint wake the screen for `timeout_minutes` (or a per-call `timeout_minutes`). With `extend` the countdown restarts on every wake and stands still while someone is present; without it the screen goes off a fixed time after the first wake. An explicit "off" wins until the next wake or base-mode change. The decision is a single method (`desired_state`) that gets the time and presence passed in, and commands wake the loop through an `asyncio.Event` instead of waiting for the next tick.
* **Rationale (the wake timer)**: The PIR mode was a hard-coded special case of the same idea. One timer covers presence, buttons and home automation calls the same way, and the two counting strategies cover both "stay on while I'm here" and "show it briefly". An API call without a timeout gets the default time, so the screen can never be left on by mistake.

## 12. User Data Outside the Package
> **In short:** Settings live outside the installed package, on `/storage`, so an update never loses them; every write is all or nothing and keeps the last good copy; *Reset Mirror* empties it all.

* **Decision**: `config.json` and custom local modules live in the user's home directory, not in the package installation directory (which is replaced on every update).
* **Rationale**: Lets the core be installed and updated as a standard PyPI package without losing settings, while developers can still run from a cloned workspace.
* **Decision (never lose it)**: Files on `/storage` are written with `config.write_atomic` (a temp file, `fsync`, `os.replace`, `fsync` of the folder), so a power cut leaves the old or the new file, never an empty one. Before each save the current `config.json` is kept as `config.json.bak`, but only when it reads. A `config.json` that doesn't read is moved aside as `config.json.broken-<UTC time>` and the backup is used; only without one does the mirror start with defaults. *Rationale*: a broken file used to be overwritten with the defaults at the next start, so one bad write lost every setting. One backup generation (ponytail): enough to survive one bad write, not a history. Backup files (`.mirror`) go in place the same way (`config.replace_durably`, which `write_atomic` uses too), the encrypted ones included: openssl writes beside the final name, never to it. A storage partition lost as a whole is #58.
* **Decision (no /storage)**: `/storage` has `nofail` in fstab, so a filesystem check that wants a person lets the boot go on without it. The hydrate script then runs `e2fsck -p` (`-y` if that isn't enough), mounts it and saves a `storage-repair` log. If it still isn't mounted on an image, it stops, so the app (which `Requires=` it) doesn't start and the loading page says so after 4 minutes. *Rationale*: on the RAM overlay (#5) the folders would have been made in RAM: the mirror looked new, copied `base_venv` into a Pi 3's 1 GB of RAM, and forgot everything at the next restart.
* **Decision (the folders)**: The core's files live under `~/.mirrordash/` (on the mirror a link to `/storage/mirrordash/data`), the config in `data/config.json`. Each module instance's data is in `data/<instance-id>/` and its cache (such as `fetch_json`'s last good answers) in `cache/<instance-id>/`, under the module host's folder (`get_module_dir`: `/storage/mirrordash/modules` on a mirror, which the core's data dir is closed to, #41; `~/.mirrordash/module-data` off one). All of it is on `/storage`, so a cache survives a reboot.
* **Rationale (the folders)**: `/storage` is all a backup or a reflash has to care about, and it is the one place a read-only root leaves writable (#5). Separate paths per instance ID keep two instances of the same module from clobbering each other's data.
* **Decision (resetting)**: **Reset Mirror** (Settings, type RESET) runs `mirrordash-factory-reset --yes` through its own sudo rule: it deletes everything in `/storage/mirrordash` but `logs/`, and restarts; hydrate then seeds it as on a first boot (venv, Python, SSH host keys, a new hotspot password). `/storage/rauc` stays, since it says which A/B slot is the good one. *Rationale*: everything of the owner's is on `/storage` by this contract, so deleting that folder is the whole reset; giving a mirror away used to mean reflashing it.

## 14. WiFi Fallback / Captive Portal State Machine
> **In short:** Without a network 30 s after boot, the mirror opens a Wi-Fi hotspot of its own, where the owner picks a network on the phone.

* **Decision**: Implemented an automated fallback WiFi captive portal setup state machine. If network connectivity is not verified within 30 seconds of system boot, NetworkManager shifts `wlan0` to an autonomous Access Point (AP) setup hotspot. Phones get a real captive portal: the OS image makes the hotspot's dnsmasq (`/etc/NetworkManager/dnsmasq-shared.d/`, used only for shared connections) answer every DNS name with `10.42.0.1`, so the phone's HTTP connectivity check (`captive.apple.com/hotspot-detect.html`, `connectivitycheck.gstatic.com/generate_204`, ...) reaches the app, whose middleware answers anything but the setup page with a redirect to `http://mirrordash.setup/wifi-setup`; the unexpected answer makes the phone show "Sign in to network". Submitting credentials saves the new NetworkManager profile (on `/storage`) and joins it without a restart; if joining fails, the hotspot comes back with the same password (a reboot only if even that fails). The check service is `Type=oneshot` and ordered `Before=mirrordash.service`, so the app (and therefore the kiosk's first page) only starts after the client-vs-hotspot decision; the app's hotspot check uses a short TTL cache, never a permanent one, so a state change is picked up within seconds. The hotspot password is unique per mirror: the check script generates it when it creates the `MirrorDash-Setup` profile (with `autoconnect no`), and the profile is only taken down after setup, never deleted, so it lives on `/storage` (the bind-mounted `system-connections`) until the card is reflashed. Any connection counts at boot, so a cable keeps the hotspot off; one plugged in while it runs takes it down (NetworkManager dispatcher `40-mirrordash-cable`), since the periodic watch only retries saved Wi-Fi. The app reads the password back with `nmcli -s` (allowed for pi by a polkit rule, no sudo) and shows it, with a Wi-Fi QR code, only to a loopback client (the mirror's own screen); phones on the hotspot can spoof the Host header but not their address.
* **Decision (the watch)**: The same script with `--watch` runs every 3 minutes from `mirrordash-wifi-watch.timer`. On the hotspot it tries the saved Wi-Fi again (a scan, then `nmcli connection up id` for each saved Wi-Fi, the last one used first, which also brings back a profile NetworkManager stopped retrying) and brings the hotspot back if that fails; it skips this while a phone is on the hotspot (a REACHABLE/DELAY/PROBE neighbour on `wlan0`; `iw` isn't in the image) or when no Wi-Fi was ever saved. Off the hotspot it does the boot check with a 60 s wait, so a Wi-Fi gone for good starts the hotspot without a restart, and a Wi-Fi change from the admin page (seconds without a connection) never does. Only NetworkManager's own state counts, so a lost internet behind a working router changes nothing. After a switch the script posts `/api/wifi/changed` (loopback only), and the app reloads the mirror's screen into the setup prompt or the mirror.
* **Decision (by name, after a scan)**: Not `nmcli device connect wlan0`, which the watch used first: right after the hotspot the Pi 3's chip rejects the first scan (`Reject scan trigger since one is already pending`), so NetworkManager saw no saved Wi-Fi and brought the hotspot itself back up, the only profile available without a scan, and `nm-online` took that for being online. Every round logged "Back on the saved Wi-Fi" while the mirror stayed on the hotspot until its power was cut; found with developer logging on a Pi 3B. The traffic check's rejoin uses the same `join_saved_wifi`.
* **Rationale (the watch)**: After a power cut the mirror is up in ~30 s and the router in 1–3 minutes, so the boot check started the hotspot, which (with `autoconnect no` and the radio busy as an AP) never looked for the home network again: the mirror stayed on `MirrorDash-Setup` until someone restarted it. A systemd timer instead of a loop in the app or the script: no long-running process, and the radio is only touched every few minutes.
* **Decision (no traffic)**: When NetworkManager says the Wi-Fi is joined, the watch also pings the router (or 1.1.1.1, for routers that don't answer ping). Two rounds in a row without an answer (about 6 minutes) save the log as `wifi-lost` under **Logs → Saved Logs** (once per outage) and join the Wi-Fi again (`nmcli device disconnect`, then `join_saved_wifi`); the next rounds keep trying. *Rationale*: a Pi 3 stayed joined for over 20 minutes while nothing got through, so NetworkManager saw nothing wrong and the hotspot never came; only a power cut brought it back, and with the log in RAM nothing showed why. Two rounds, so a router that restarts isn't taken for it. The failure count lives in `/run` (RAM), like the rest of the watch.
* **Decision (a Wi-Fi chip that hangs)**: When there's no traffic and the kernel log of the last 30 minutes shows the Pi 3's Wi-Fi bus locked up (`failed backplane access` or `brcmf_proto_bcdc_msg failed w/status -110`, after `mmc1: Controller never released inhibit bit(s)`), the watch doesn't join again but takes one step a round, each stronger, from the first round on (the kernel log already says what is wrong, so there is no router restart to wait out): round 1 loads `brcmfmac` again, round 2 restarts the chip's bus controller (unbind/bind of the controller behind `mmc1`, `3f300000.mmcnr` on a Pi 3) and, while it is unbound, takes the chip's power line low for a second (`gpioset -t 1s,0 WL_ON=0`), round 3 restarts the mirror (the same once-an-hour stamp as above), and round 4 starts over, so a chip that hangs again within that hour still gets the lighter steps. Each step is logged, and the round that finds traffic again logs which step was enough. The log is saved three times at most: `wifi-lost` at the first step, `wifi-restart` right before the restart, and `wifi-back` when traffic is back, the one that holds the answer. *Why the power line by hand*: the Pi 3's device tree gives the bus no power switch for the chip (no `mmc-pwrseq`; `WL_ON` is a line on the firmware's GPIO expander that no driver holds), so restarting the bus alone leaves a hung chip powered. *Why `mmc1` and not `wlan0`*: loading the driver again on a hung chip often leaves no `wlan0`; for the same reason the watch looks for a hung chip before it looks for a chip that didn't start (below), which would load the driver once more and then restart. *Rationale*: a kernel bug without a fix ([raspberrypi/linux#5770](https://github.com/raspberrypi/linux/issues/5770)) locks the bus under long heavy traffic; on the test mirror the bus hiccuped every few minutes of full-speed download (more often while writing to the SD card) and one hiccup in about 45 was fatal (once in some 30 downloads of 900 MB), and with `wlan0` still there the mirror stayed offline until unplugged. Nothing prevents it (overvolting, lower clocks and a 32-bit kernel were all tried upstream), so the watch recovers; the log line tells whether the lighter steps are ever enough or the restart is all that's needed. The chip's hang often takes the connection down with it (NetworkManager loses the Wi-Fi, `nm-online` fails), so the watch looks for a hung chip before it looks at NetworkManager: on a Pi 3 (2026-11-11, a long 1080p stream) the watch took that for a network gone for good, tried the hotspot every round (which can't start on a hung chip) and never started the chip again; it stayed offline 64 minutes until the chip woke by itself. *Not verified on a real hang*: the steps are tested against a fake `/sys`, and `pi` has no root to run them by hand.
* **Decision (a Wi-Fi chip that didn't start)**: The watch also checks that the Wi-Fi chip is there: `brcmfmac` (the driver of every Pi with built-in Wi-Fi) loaded but no `wlan0` means the chip's firmware didn't load at boot (seen on a Pi 3: "Downloaded RAM image is corrupted"; it then had no Wi-Fi and no hotspot until restarted). It saves a `wifi-chip` log (once per start), loads the driver again (all `brcmfmac*` modules out, `brcmfmac` in, `udevadm wait` for `wlan0`), and only if `wlan0` still doesn't come and there's no network at all (no cable either) restarts the mirror, at most once an hour (a stamp on `/storage`). *Rationale*: it acts on the symptom, not the model, so it covers every Pi with that chip family and does nothing on one without built-in Wi-Fi or with working Wi-Fi; a driver reload is harmless, and the restart is limited so a broken chip can't make the mirror restart over and over.
* **Decision (from the admin page)**: *Settings → Wi-Fi* changes the network: the route answers first and switches a second later (the phone loses the mirror the moment it changes network). If the mirror can't join, it deletes the profile that attempt created and brings the previous one back up; the card then shows why.
* **Rationale (setup)**: Minimizes appliance maintenance and makes the device plug-and-play across different network environments without requiring terminal access or physical disassembly.

## 15. Hardware Watchdog
> **In short:** The kernel's watchdog restarts a frozen Pi, and a timer restarts the app or the screen's browser when they stop answering.

* **Decision**: Kept the kernel hardware watchdog that Raspberry Pi OS enables (`RuntimeWatchdogSec=1m`, its drop-in `40-rpi-enable-watchdog.conf`; our earlier 14 s edit of `system.conf` never applied, the drop-in overrides it). `mirrordash.service` starts after `network.target` and the storage hydration, and the Wi-Fi check (#14) runs before it; it doesn't wait for time sync.
* **Decision (the app and the screen)**: `Restart=always` only helps a process that dies. A renderer that crashes makes the screen's launcher exit (`mirrordash-screen` on `web-process-terminated`, `screen-kiosk.service`; before #56, Cog's `--webprocess-failure=exit`) and systemd starts a new one in 2 s: a browser's default shows a white "The renderer process crashed" page and stays on it, and only a new process gets the crashed renderer's GPU memory back (2026-11-04: a foreground module ran the Pi 3 out of CMA, the page reloaded in the same Cog never reconnected). `mirrordash-app-watch` (a timer every minute) covers what hangs without dying: it restarts `mirrordash.service` when `/health` doesn't answer four rounds in a row (an app starting after an update takes minutes on a Pi 3), and `screen-kiosk.service` when the mirror's own screen has been silent for over 150 s two rounds in a row: the kiosk page sends `alive` on its WebSocket every minute, and the setup prompts poll `/admin/auth/status`; only loopback clients count (`ConnectionManager.saw`), and `/health` reports `screen_seen_seconds_ago` (null while the screen is off). It retries every fourth (app) or second (screen) round while the fault stays, but saves the `app-hung`/`screen-lost` log once, so it can't push the other saved logs out. *Rationale*: a WebKit renderer that freezes keeps the launcher's window (and can keep the socket open), and a hung event loop keeps the process; both left a dead screen until the power was cut. A timer, not `WatchdogSec` + sd_notify: no change to `launch.sh` or the unit type; a frozen page costs about 3 minutes, a crashed one seconds.
* **Decision (the clock)**: The Pi has no clock battery and the root forgets, so every start began at the image's build date until NTP answered. `mirrordash-clock.service` (`/usr/local/lib/mirrordash/clock`) moves the clock forward to the time saved on `/storage/mirrordash/clock` at start, before the network, never back; the time is saved hourly and at shutdown, only once NTP has set it. Not Debian's fake-hwclock: it loads before `/storage` is mounted. Not a bind mount for timesyncd's own clock file: timesyncd starts before `sysinit.target`, hydrate after it, and a missing mount would keep timesyncd from starting at all.
* **Rationale**: The mirror restarts by itself if the kernel or systemd hangs, with the vendor's tested default. The Pi has no clock battery, so the first minute can run on an old time; modules fetch again on their next interval, and `fetch_json` returns the last good answer meanwhile, which beats a screen that waits for NTP.

## 16. Failsafe A/B Virtual Environment Updates
> **In short:** The app's Python environment is changed in a copy (venv A/B) and switched to only when it works; when it doesn't start, `launch.sh` goes back to the one before, or to the image's own copy in Safe Mode.

* **Decision**: Redirected the virtual environment `.venv` from the read-only root partition to the persistent writeable `/storage` partition via a symlink. When the core's packages change (an update, a rebuild), the change is staged in a cloned alternative directory (`venv_a` or `venv_b`). The modules aren't in it: they live in the module site, which the module host switches the same way (#41). Once successful, the symlink is atomically updated and the previous environment is kept as `venv_old`. A core update that didn't install a newer version (PyPI's index can lag a few minutes; uv runs with `--refresh-package mirrordash`) is reverted with a 409 instead of switched in, so a no-op never replaces the real fallback in `venv_old`. *Rebuild environment* (*Reinstall MirrorDash*) starts from an empty venv with this MirrorDash version; the modules, in the module site, stay as they are.
* **Decision (the app's Python)**: The Python the venvs run lives on `/storage/mirrordash/python`, with the app, not in the root: `mirrordash.service` sets `UV_PYTHON_INSTALL_DIR` there (and `venv.run` passes it on), and the hydrate script gives a venv that still uses the root's Python (one seeded from `base_venv`, or from an older image) a copy of it, once, and points it there (its `bin/python` link and `pyvenv.cfg`'s `home`, the only places that name it). Only `base_venv` (Safe mode) uses the root's Python. A MirrorDash whose PyPI `requires_python` asks for a newer minor (`needed_python`, ">=3.N" only) is an app update like any other: `uv python install 3.N` next to the running one, an empty venv with it and the new MirrorDash, an empty module site with every module built for it by the module host (the pinned version, then the newest for a PyPI module), and each module loaded once from there. Only when all of them work is it switched in; otherwise nothing has changed, the update card lists the modules and why, and **Install Anyway** installs without them and turns their instances off (`disabled_reason`, settings kept). *Rationale*: the venvs used to link into the root, so an OS update with another Python left them unable to start; hydrate then deleted them on the trial boot, before the update was proven, the modules were gone for good (Reinstall read the list from the running, empty venv), and a failed trial lost the app update too. A new Python is seldom a breaking change for a module, so none is dropped up front, and the admin, not the mirror, decides whether losing one is worth it. *Order*: the first image with this must keep the root's Python (3.14), since that is what is copied; only a later image may change it. After every swap, `remove_unused_pythons` deletes the Pythons on `/storage` that none of `venv_a`, `venv_b` and `venv_old` (the launcher's fallback, which must still start) uses, about 90 MB each; `venv_failed` needs none, only its files are read. Only where `UV_PYTHON_INSTALL_DIR` is set, so never a developer's own uv Pythons. *Patches*: every app update first runs `uv python upgrade 3.N` (same guard); the venvs point at uv's minor link, so all of them get the newest 3.N.x, and the old patch is removed after the swap.
* **Decision (when the link moves)**: `prepare_venv_next` builds the next venv by its path and leaves the link alone; `commit_venv_next` points the link at it, after everything installed, and `revert_venv_next` only deletes the next venv. *Rationale*: the link used to move before uv ran, for the minutes an install takes on a Pi 3. A restart in that time (a power cut, an out-of-memory kill, the Restart button) started the half-installed venv, and `launch.sh` then went back to `venv_old`, the version *before* the current one, deleting the intact current venv on the way (Safe mode when there was no `venv_old`); the module host, which starts through the same link, could start on half a venv too. The module site always switched at commit (#41). The Python patch (`upgrade_python_patch`) is outside the swap, since every venv follows uv's minor link: the new patch is started once (`import ssl, sqlite3`) and the link put back on the old patch if it doesn't run.
* **Rationale**: Prevents package upgrades from bricking the system in the event of an update failure (network drops, syntax errors, or incompatible package versions). The boot-time hydration script only seeds `venv_a` and the link when the link is missing or dangling; it never resets a valid link, otherwise every reboot would silently revert A/B updates to the factory `base_venv`.
* **Decision (the launcher)**: Implemented a boot launcher script (`launch.sh`) that monitors the startup lifespan of the application. If the primary virtual environment fails to boot successfully within 10 seconds, it automatically rolls back to the previous stable state (`venv_old`) or fallback boots the Golden Copy (`base_venv`, the version the image shipped with, on the read-only root, so no update or power cut can touch it) in Safe Mode, alerting the user via UI status banners. Additionally, user configurations (SSH state, timezone, and shadow-crypt password hash) are programmatically re-applied on boot.
* **Decision (an update on trial)**: `commit_venv_next` leaves `/storage/mirrordash/venv-trial` when it switches the link, and the app removes it once a start has run for a minute after its startup finished (`confirm_venv`). While the file is there, `launch.sh` takes a crash at any time for a broken update and rolls back, then removes the file. *Rationale*: ten seconds is a guess about the hardware; a Pi 3 with a cold card can need longer just to import the app, and a version that failed after that was started again for ever (systemd's `Restart=always`), with no rollback. The file makes the limit "has it run yet", not a number of seconds. After a rollback the app also turns the modules back on that **Install Anyway** turned off for the newer Python (`turn_modules_back_on_after_rollback`).

## 18. Background Jobs and Restart Detection in the Admin UI
> **In short:** Long jobs (install, update, restore) run in the background behind a progress overlay; the admin page knows a restart is done when the app's boot id changes.

* **Decision**: Long package operations (module install/upgrade/uninstall, core update, venv rebuild, backup restore) run as a single in-memory background job (`start_job` in `admin.py`). The HTMX request returns immediately with a script that opens the progress overlay; the UI then polls the authenticated `/admin/jobs/current`. Every process start gets a random `BOOT_ID`, reported by `/health` and the job endpoint, and a restart counts as finished only when that id changes. All `hx-confirm` prompts go through the app's own `showConfirm()` dialog via one `htmx:confirm` handler, and button spinners use HTMX's `.htmx-request` state (`.htmx-indicator` / `.htmx-normal`, `hx-disabled-elt`) instead of being set in `onclick`.
* **Rationale**: On a Pi 3 these operations take minutes, longer than nginx's 60 s proxy timeout, so a synchronous request could fail while the work continued silently. Inferring a restart from timings ("down after 5 s, then up") broke on flaky Wi-Fi and left the overlay spinning. Spinners set in `onclick` started before the confirm dialog and were never reset, even when the user cancelled. One job at a time matches the A/B venv swap, which cannot run concurrently, and a restart ends every job, so no persistence is needed.

## 19. Sensors and Inputs via Kernel Device-Tree Overlays
> **In short:** Buttons, sensors and fans on the GPIO pins are kernel drivers (device-tree overlays) a root helper sets up, not a Python GPIO library; a change needs a reboot.

* **Decision**: Everything on the GPIO header is a list of devices (`system.devices`, at most one per type: `button` (and `button_2`–`button_4` for up to four buttons, `KEY_MACRO1`–`KEY_MACRO3`), `pir`, `mmwave`, `dht11`, `light`, and one of `fan` (`gpio-fan`, on/off) or `pwm_fan` (`pwm-gpio-fan`, four speed steps)), and every device is a Raspberry Pi kernel driver instead of a Python GPIO library. A root-owned helper (`mirrordash-gpio-overlays`, allowed in sudoers) takes typed arguments (`button:17`, `light:0x23`), validates them against a fixed vocabulary and writes the matching overlays into a managed `[all]` block of `config.txt`; the firmware applies them at the next boot. `gpio-key` overlays turn the button, PIR and mmWave sensor into input devices (keycodes 148–150: `KEY_PROG1`, `KEY_PROG2` and `KEY_WWW`) that `hardware.GpioInputs` reads as raw evdev events; `PressClassifier` turns button down/up times into single/double/triple/long presses. The DHT11 (`dht11` overlay) and the BH1750 light sensor (`i2c-sensor` overlay, enables I²C) are read by one generic IIO reader from `/sys/bus/iio/devices`, cached for 30 s. `hardware.sync_gpio_overlays()` validates the list (pins, I²C reserving GPIO 2/3) and only calls the helper when the overlay arguments change; the change is marked pending with the kernel boot id until the mirror restarts. A failure there never blocks saving other settings. Modules get the hardware through the event bus: `hardware.button` `{"press", "action", "button"}` (each button has its own `PressClassifier` and `long_press` time, 1.5 s by default), `hardware.motion` `{"motion", "sensor"}` on every change (`motion` is true while any presence sensor sees someone), `hardware.climate` `{"temperature_c", "humidity"}`, `hardware.light` `{"lux"}` and `hardware.fan` `{"level", "max_level", "cpu_temperature_c"}` every 30 s. The fan itself is run by the kernel's thermal framework; the app only reads its state from `/sys/class/thermal`. Module subscriptions are cleared whenever the modules are reloaded, since the reload creates new instances.
* **Rationale**: The app runs on uv's Python 3.14, where `gpiozero`/`RPi.GPIO` are not installed and `lgpio` cannot be built on the device, so the previous GPIO code silently did nothing. The kernel debounces inputs and handles sensor timing far more reliably than Python polling, with no extra dependency. One device list, one IIO reader and one input reader mean a new sensor type is mostly one entry in `DEVICE_TYPES` plus one line in the helper. Changes only happen at boot because overlays applied by the firmware can't be removed at runtime. Only a fixed set of types is accepted by the root helper, so the app can never write arbitrary content into `config.txt`.

## 21. Module Scripts Receive Their Shadow Root
> **In short:** Every script in a module's card gets that card's shadow root as `root`, to find its own markup and keep state per instance.

* **Decision**: The kiosk wraps every inline `<script>` in a module's HTML as `(function (root) { … })(…)`, where `root` is that module instance's shadow root. The root is kept across re-renders, so a script keeps per-instance state such as a timer on it (`clearInterval(root._timer); root._timer = setInterval(…)`).
* **Rationale**: Module HTML lives in a shadow root, and the HTML spec makes `document.currentScript` null there, so scripts had no reliable way to find their own markup; looking themselves up by `data-module` broke whenever the instance id differed from the package name, and globals made two instances of a module share one timer. One wrapper in the core gives every module the same answer without a client-side API.

## 22. Releases Are Made From What Was Tested
> **In short:** Every release is first published as a test version and tried on a real mirror; the release is then that same tested version.

* **Decision**: One local script, `scripts/release.py`, makes every release, and each real release follows a test. The app is first published as a PyPI pre-release (`X.Y.ZrcN`) that only mirrors with `system.prerelease` ("Test versions") are offered and install (`uv pip install --prerelease=allow`); the release then bumps to `X.Y.Z`. The OS image is built only on request and published as a test version (the GitHub pre-release `vX.Y.Z-osN`), which only mirrors with Test versions are offered as a system update, or flashed from its download; the release turns that same pre-release into the release, so nothing is rebuilt. `publish.yml` refuses a tag that isn't `v` + the `pyproject.toml` version. Versions are compared with `config.version_key`, PEP 440 through `packaging`, which orders a release above its own pre-releases.
* **Rationale**: Releases were made by hand in the GitHub UI, nothing tied the tag to the published version, an OS image was rebuilt at tagging so the shipped file was never the tested one, and there was no way to try an app version on one mirror before all of them got it. The script keeps the GitHub CLI as its only extra tool. `packaging` (PyPA's own, pure Python, no dependencies) compares the versions on the mirror and in the script, which runs itself in the dev venv: a hand-written comparison knew only the shapes MirrorDash publishes, and the Python a release needs (`requires_python`) only as `>=3.N`.

* **Decision (automatic updates)**: On unless *Install updates automatically* is off (`system.auto_update`, missing = on). `mirrordash-auto-update.timer` (03:30, spread over an hour) asks the app (`POST /admin/auto-update`, loopback only), and `auto_update()` does what the Updates card's buttons would, the system first, as its own job. It doesn't choose for the owner: a system build whose trial boot failed is counted (`system.auto_update_failed`) and tried again on the next nights until it failed three times (`OS_TRIAL_TRIES`): a passing fault, like the Pi 3's Wi-Fi chip not starting after the download, must not keep a mirror nobody looks after off updates for good, and a build that is really broken costs three nights' restarts, after which only that build waits (a newer one is tried, with its own count); and a newer Python some modules don't work with waits for **Install Anyway**. Modules come last, one job a night like the rest (one restart), only with *Update modules automatically* on (`system.auto_update_modules`, missing = off: a module is someone else's code, the owner opts in) and not the ones turned off in their settings (config's `module_auto_update_off`, site folder names like `module_scripts`); they also go while MirrorDash waits for that choice. A version of MirrorDash or a module gets the same three nights (`UPDATE_TRIES`, `system.auto_update_tries` by package name, "mirrordash" for the app), counted when the night starts it rather than when it fails: still offered the next night means it failed, whichever way (the install, the module check, or a crash launch.sh rolled back), so no failure needs telling apart. Several modules at once (here and **Update All**) stay one site change and one restart, but each must install and load on its own: one that doesn't is reinstalled as the running site has it (`installed_modules`, `module_target`), the others are checked together once more (a dependency one moved can break another) and kept; only when none works is nothing changed. *Rationale*: an update only by button never reaches a mirror nobody looks after, which is most of them, security fixes included; the safety is already in the updates themselves (A/B, the trial boot, the module check).
* **Decision (a mirror that is off at night)**: With *Catch up after a night off* on (`system.auto_update_catch_up`, missing = off), the app runs the night's round itself ten minutes after it starts, when the last round is more than 20 hours ago (`features/updates/catch_up.py`; the last round's time is the file `nightly-update-at` beside the config). Never on the trial start of a new system, and not when the clock shows a time before the last round (not set yet). *Rationale*: a mirror on a smart plug or a switch is off at 03:30 every night and never updated. systemd's `Persistent=true` can't do it: a timer's memory of its last run lies under `/var/lib/systemd/timers`, in the root's RAM overlay, which every start begins without. Off by default, since an update then restarts the mirror while someone looks at it; 20 hours rather than 24 so a mirror turned on at the same time every morning doesn't skip every other day.

## 23. Shared Building Blocks for Modules: Layout Classes and fetch_json
> **In short:** Everything a module may use for its look is in `modules.css`, shown at `/design`, and `fetch_json` gives every module the same HTTP calls with a saved answer.

* **Decision**: Everything a module may use for its look lives in one stylesheet, `static/modules.css` (typography, `.text-*`, `.flex-*`, icons, data lists, forecast and agenda lists, gauges, stats, callouts, `.module-message`). `style.css` imports it for the page, and the kiosk loads it once and puts it into every module's shadow root next to the design tokens (`static/js/kiosk/design-tokens.js`). `/design` is the library of exactly these components, with markup to copy; a test keeps every class in its markup present in `modules.css`, and the mirror's own UI is marked there as not for modules. The module loader also gives every module `self.fetch_json(url, …)` and `self.fetch(url, …)` (raw bytes, for RSS, ICS and other non-JSON answers) next to `render_template`. Both take `headers`, `params`, `method`, `json`, `data`, `timeout` and `max_age` (reuse a saved answer younger than that, so a restart of the modules makes no call), the names `requests` uses, so a module never needs its own HTTP client, whatever API it talks to; `mirrordash-sdk validate` warns about one. They return `(data, error)`: on any failure the last good answer for the same method, URL and body (kept in the module's `cache_dir`) and one of `rejected`, `offline`, `http <code>`, `invalid`. The pair also carries `.fetched_at`, when the data was downloaded (a saved answer keeps its download's time, the cache file's mtime), so a card says how old its data is, not when it was drawn; unpacking it as `data, error` works as before. And `.headers`, this call's answer's headers (an error's too: a 429's `Retry-After`, beside the last good data), empty when no call was made (a saved answer reused, the preview's samples) or none answered: the fetch runs in the module's process for its own request, so its headers hold nothing the module couldn't see with a client of its own, and like the body they are never logged. They log only method, host and path. Module templates in `mirrordash-sdk` build on both.
* **Rationale**: The module guide recommended classes that only existed in the global stylesheet, which a shadow root never sees, so every module wrote its own CSS. Five modules each had their own fetch, JSON, timeout and error code, with different bugs (an error branch that could never run, a network error read as "nothing today", an API key in the log). One helper in the core fixes that once, needs no dependency (urllib in a thread), and keeps modules free of imports from the core.

## 24. An API for Other Systems, With Its Own Description
> **In short:** `/api/v1` lets other systems (Home Assistant, scripts) read the status and set the screen with a token of its own, never the admin password.

* **Decision**: `/api/v1` (`features/api/api.py`) answers only to `Authorization: Bearer <token>`, a 256-bit token from the Settings tab's *API* card. Only its sha256 is stored (`config["api_token"]`), so it is shown once; a new token replaces the old one. It can read `/status` (version, uptime, CPU temperature, screen, brightness, modules, cached sensor readings) and set `/screen` and `/brightness`, which reuse the admin's own `update_screen_state` and `update_system_settings`. The admin password (`X-API-Key`) is not accepted there. It is its own FastAPI app mounted at `/api/v1`, with Pydantic models for every body and answer, so `/api/v1/docs` (Swagger UI) and `/api/v1/openapi.json` describe it; they are open, the calls are not. Home Assistant is one client: its `rest`, `rest_command`, template `switch` and template `number`, with the YAML in the user guide.
* **Rationale**: Before, the only key was the admin password, which Home Assistant would have had to keep. A separate token can be removed without changing the password, can't install modules or restore backups, and survives a backup restore (the hash is in `config.json`; `admin_auth` is not). MQTT discovery or an own integration would mean a broker or a second repo for what a few REST calls do. Only this API gets a description: the rest of the app has one client, the admin page, so a description there would only be attack surface (#27).

## 25. The Screen Reloads After a Restart of the Core, Not on a Reconnect
> **In short:** The screen reloads itself only when the core restarted or was updated (a new boot id or version), not when its WebSocket merely reconnects.

* **Decision**: On every WebSocket connection the server first sends `{"type": "hello", "version": …, "boot_id": …}`; the boot id is new each time the core process starts (`admin.BOOT_ID`). The kiosk page remembers both from the first hello and reloads itself when a later one carries a different version or boot id: the core was updated, or restarted (a module installed or removed, a backup restored). Anything else (a module's settings changed, a settings change) arrives as rendered HTML over the open socket. The admin's Power tab has a *Reload Screen* button that broadcasts `{"action": "reload"}` for everything else.
* **Rationale**: The screen keeps one page open for weeks, so after a core update it would run the old `core.js` and CSS against the new server, and after a restart that removed a module it kept that module's last HTML on screen. Reloading on every reconnect would flash the screen at each Wi-Fi blip; a reconnect to the same process keeps its boot id, so the page reloads exactly when it is stale. The button covers the rare case nothing detects, without SSH.

## 26. Discover: One Search Request, the Release Tag Pinned at Install
> **In short:** The list of modules to add is PyPI's `mirrordash-*` packages and one GitHub search for `mirrordash-*` repositories with the `mirrordash-module` topic; a GitHub module's latest release is looked up only when it is installed, and pinned.

* **Decision**: The module list under *Modules → Add modules* is every `mirrordash-*` package on PyPI (its simple index, then each package's JSON) plus one GitHub search request (repositories named `mirrordash-*` that have the `mirrordash-module` topic, up to 100; the SDK's `release` sets the topic, and a GitHub repository without it is not listed); a name on both is listed once, PyPI's unless the GitHub one is official (`_add_github_modules`). When the GitHub search fails the previous list is kept. Only at install is the module's latest release looked up; its tag is appended (`…@v1.2.0`), a repository without releases is refused, and a rate-limit or network error asks the user to try again later.
* **Rationale**: Unauthenticated GitHub allows 60 requests an hour per IP, shared by the whole home network, so one request per repository ran out after a few scans and silently showed only the first module. Pinning the tag installs a published release instead of whatever is on the default branch, and the update check compares that recorded revision with the latest release.

## 27. The Core in Vertical Slices
> **In short:** The code is split by feature (`features/<name>/`: its routes, logic and templates together); only what several features share sits at the package root.

* **Decision**: The core is organised by feature, not by layer. `mirrordash_core/features/<feature>/` (api, auth, backup, dashboard, hardware, kiosk, logs, matter, modules, mqtt, notifications, power, settings, updates, video, wifi) holds a feature's routes, logic and templates; one Jinja environment reads every `features/*/templates`. Code two or more features use stays at the package root: `admin.py` (page shell, login, jobs, page events), `config.py`, `forms.py` (forms from a JSON schema, its HTML in the autoescaped macros of `templates/schema_form.html`), `venv.py` (the A/B swap and uv), `host.py` (OS commands and what the mirror says about itself), `fetch.py`, `screen.py` (the screen's WebSocket hub), `notifications.py` (the store of #57) and `event_bus.py`. `app.py` only composes; which part may import which is #59. The admin panels call feature functions directly, so a feature only has HTTP routes something requests; the JSON routes nothing called were removed, and so were FastAPI's `/docs` and `/openapi.json`.
* **Rationale**: A feature was spread over a JSON file, a panels file, `system/`, `templates/` and a root module, so a change touched five places and copies drifted apart (the A/B swap five times, backup validation twice, the form flattening three times). Measured before and after: no function above grade C (from one F, three E and five D), average complexity A (4.3, from B 5.6), the largest Python file 513 lines (from 592), `admin.html` 245 lines (from 1763), routes 96 → 74.

## 28. A Forgotten Admin Password: a Recovery Code From Setup
> **In short:** Setting the admin password also gives a recovery code, shown once; without it the password is reset by editing `config.json`.

* **Decision**: Setting up the admin password also creates a recovery code (12 characters, `XXXX-XXXX-XXXX`), shown once and stored only as a PBKDF2 hash next to the password. With it, *Forgot password?* sets a new password; the code is then used up and a new one is shown. Changing the password keeps the code. Without the code, the password is reset by removing `admin_auth` from `config.json` over SSH or on the SD card (USER_GUIDE, *Lost the recovery code too?*), after which the admin page asks for a new password.
* **Rationale**: The earlier recovery (a PIN on the mirror's screen) needed no login to start and wiped the password at once, so anyone on the network could lock the owner out, and the 6-digit PIN had no attempt limit; anyone in front of the mirror could take over. A reset e-mail would need an SMTP account on every mirror or a MirrorDash mail service, against a mirror that works on its own at home. A code the owner saves works offline and can't be guessed (~59 bits behind PBKDF2), and whoever can reach the SD card owns the mirror anyway.

* **Decision (logging in)**: The admin page sends the password once, to `/admin/auth/login`, and gets a random session token as a cookie (`HttpOnly`, `SameSite=Strict`, 30 days); `require_api_key` accepts that cookie (one sha256 lookup) or, for scripts and tests, the password in `X-API-Key`. Only the token's sha256 is kept, in `sessions.json` next to `config.json`, so the restart after an update doesn't log anyone out. A new password (changed, or reset with the recovery code) ends every session. Five wrong passwords or recovery codes from one address in a minute lock it out for a minute (in memory). A cookie request that changes something is refused when its `Origin` is another site, and the server sends no CORS headers. *Rationale*: the page kept the password itself in `localStorage` and sent it, over HTTP, with every request; any script on the page could read it, every request ran 100 000 PBKDF2 rounds on the Pi, and nothing stopped guessing. The CORS setting (any origin, with credentials) would have let any web page use a logged-in session.

## 29. Modules Sleep While the Screen Is Off
> **In short:** While the screen is off, a module's `fetch` waits until it is on again, so a dark mirror spends no API calls.

* **Decision**: While the screen is off, a module's `fetch`/`fetch_json` waits until it is on again (`DisplayPowerManager.awake`). The module's loop stands still at the fetch, so a fetch that fell due in the dark goes out once on waking, and one that didn't waits for its own interval. A module that must run in the dark (a data logger) sets `keep_running = True` on its class. Modules that use their own HTTP client are not held.
* **Rationale**: A dark mirror shouldn't spend paid API calls or rate limits. Cancelling and restarting the modules' tasks would fetch on every wake, so a mirror woken by presence could call an hourly API many times an hour; holding the one shared fetch keeps each module's own schedule without the core knowing it, and needs no setting. Home Assistant already turns the screen off when nobody is home, so that sleeps the modules too.

## 30. Modules Keep Their Own Schedule; the Core Stops Redraws of the Same Content
> **In short:** The core has no scheduler: each module keeps its own interval, and the core leaves out redraws of the same content.

* **Decision**: There is no scheduler in the core. A module loops in `run_loop` with its own `interval` (a convention from the SDK templates, read by the core where it is there). A module with only `async def render()` gets the one loop nearly every module wrote: show it, wait `interval` (600 s without one) or until `self.changed` is set (the core adds that event), repeat, an error logged and tried again next turn (`_render_loop` in `loader.py`). `fetch`/`fetch_json` take `max_age` from `interval` when it isn't passed (`max_age=0` always calls), so restarting the modules (every saved setting, an update, a reboot) reuses a young saved answer instead of calling the API again, and a module that forgot it is covered too. The websocket manager (`screen.py`) doesn't send a module the same message twice, so the screen doesn't redraw a module whose HTML and settings didn't change; a reload clears that memory.
* **Rationale**: A scheduler would be a second way to do what `run_loop` does, and `run_loop` stays anyway for push updates, clocks and carousels; the core would also have to own a retry policy (a fetch at 10:30 that fails: retry when?) and time of day around a boot without a clock battery. MagicMirror² works the same way: an `updateInterval` convention per module and a check in the core that skips a redraw of unchanged content. Redrawing identical HTML restarts a module's icons, scripts and scrolling, which shows as a flicker. The default loop is that same loop, not a scheduler: a module with pushes, a time of day or a clock still writes its own `run_loop`. `max_age` defaults to `interval` because a fetch then never happens less often than the loop turns, while a module that forgot it no longer spends a paid API on every restart (every module that fetches passed it by hand). Where `interval` means something else (namnsdag checks for a new day every minute but fetches once a day) the module passes `max_age` itself. A render woken by `self.changed` within the interval gets the saved answer; a module whose *Update now* must call passes `max_age=0` then.

## 31. A/B OS Updates: RAUC and the Pi Firmware's tryboot
> **In short:** The OS updates itself into a second copy of the system (slots A and B, RAUC) and keeps it only when it boots; otherwise the Pi goes back to the one before.

* **Decision**: The OS updates without reflashing. The card has two slots (boot p2 + root p5 = A, boot p3 + root p6 = B), a small p1 with the Pi 3 firmware files and `autoboot.txt` (which boot partition the firmware starts), and `/storage` (p7) shared by both; the image holds p1–p5 and the first boot adds p6 and p7 (`mirrordash-repart.sh`). A release carries a signed RAUC bundle (the same boot and root images as the card image); **Settings → Check for Updates** downloads it to `/storage` and has RAUC write it into the slot that isn't running. Our own bootloader backend (`rauc-bootloader`, about 170 lines of bash, `scripts/image/rootfs/usr/local/lib/mirrordash/rauc-bootloader`) then points the new boot partition at its own root, carries over the Wi-Fi country and the GPIO block, and sets the firmware's one-time tryboot flag. On that trial boot (only when the slot running is the one RAUC activated last, by RAUC's own `activated.timestamp` in `/storage/rauc/central.raucs`, so a trial started by hand with `reboot "0 tryboot"` never keeps an older slot, and it holds also when an older system installed the update) `mirrordash-mark-good.service` waits for the internet (`https://github.com`, where the next update comes from; not `nm-online`, which counts the setup hotspot as online, so an OS whose Wi-Fi can't join the home network would be kept and the mirror could never be updated again) and the app's `/health`, then swaps the partitions in `autoboot.txt`; if either fails it restarts the mirror, which then boots the old slot. `/boot/firmware` is mounted by a systemd generator from the partition the firmware reports, since the shared root's fstab can't know it. `rootdelay=20` keeps the fallback after a missing root to about half a minute. The build stamp (`/etc/mirrordash-os-build`, and the end of the bundle's file name) says which OS is newer. Images only: a Pi set up by hand has one root.
* **Rationale**: Reflashing loses the setup and needs a computer; mirror owners shouldn't have to. The Pi firmware's own A/B switch (`autoboot.txt`, `tryboot_a_b`) needs no U-Boot, and was tested on a Pi 3B before this was built: it boots the tried slot once, and any restart, power cut or kernel panic before mark-good brings back the old one. RAUC brings signature checks and the slot handling; Mender would have meant U-Boot and a server. Rtone's RAUC backend for the same firmware feature was the model, but it is 500 lines for many layouts, and it has to be changed anyway (`sync` around the `autoboot.txt` swap, the boot partition setup), so ours is written for one layout. The root fix lives in `set-primary` rather than a post-install handler because RAUC ignores a failing post-install handler: a boot partition pointing at the wrong root must fail the install. The bundle is downloaded to `/storage` before installing instead of streamed: then sudo allows `rauc install` on one fixed path only, and a Wi-Fi drop stops the download before anything is written rather than failing the install halfway (it costs about 800 MB on `/storage` while it runs). Only one file path is allowed to `rauc install` through sudo, and RAUC refuses bundles not signed with the key behind `scripts/rauc/cert.pem`.
* **Limits**: The mirror boots from the SD card only (`/dev/mmcblk0` is fixed in `system.conf` and the backend), not USB or NVMe. Slot sizes can't change on cards that are out there: root 1.5 GiB (757 MB used), boot 256 MiB (about 90 MB used); the build stops when a root doesn't fit. Tested on a Pi 3B; Pi 4 and 5 read `autoboot.txt` from their EEPROM and should work the same, but haven't been tried. p1 (the Pi 3 firmware and `autoboot.txt`) is renewed by `update-p1`, the last step of `mirrordash-mark-good`: on a Pi 3 it is p1's `start.elf` that boots a slot, so the slots' own firmware files are never used there, and without it a Pi 3 would keep the firmware it was flashed with while each system update brings a newer kernel (Pi OS ships them as a pair). When the running, just proven slot's `bootcode.bin`, `start.elf` or `fixup.dat` differ from p1's, the script builds a new p1 in the 32 MiB left empty after it (a loop device over that half: `mkfs.vfat`, the firmware, and `autoboot.txt` as it is now), checks it file by file, and moves the MBR's p1 entry over in one 512-byte write (`sfdisk -N 1`). A power cut before that write leaves the old p1, after it the new one; the old half stays as a way back by hand. A failure there never undoes the system update (the unit's `-`), it only leaves a `p1-update` saved log. Not RAUC's `boot-mbr-switch`: it writes p1 from the bundle, `autoboot.txt` included, and so forgets which slot is the good one. What remains: a new `start.elf` can't be tried before it's used (tryboot is p1's own feature), the same as on every Pi running Raspberry Pi OS, where it is overwritten in place. Bad blocks in the running slot itself have no way back: the firmware has no boot counter, so a slot that no longer starts is tried again until the card is flashed (#58).
* **An app crash on a trial boot**: `launch.sh` doesn't roll MirrorDash back when `rauc-bootloader is-update-trial` says this is the trial boot of a new OS: it keeps failing, `/health` never answers, mark-good gives up and the mirror goes back to the old OS with the app as it was. *Rationale*: on a trial boot the crash is the new OS's doing; the rollback downgraded the app for good, and when that failed too, Safe mode answered `/health` and got the broken OS kept.
* **What a trial boot must show**: after the internet, mark-good asks `/health?trial=1`, which answers 200 only when the app runs as itself (503 in Safe mode: with the venv link missing, `launch.sh` starts the image's copy, whose answer got a system kept that the app's own environment didn't start on) and the screen's page has been heard from since this start (`screen_loaded`), unless the screen is known to be off. *Rationale*: a system whose browser, compositor or GPU driver is broken had network and app and was kept, with a black mirror for good. The rule lives in the app, behind curl's own retries, so the image needs no polling script.
* **Smaller steps around the install**: `autoboot.txt` is swapped by writing the new text over the old where it lies (the same length, one sector) instead of a new file renamed over it, which on FAT is several writes with a moment where neither name is whole. The bundle downloads through `os-update.<build>.part`, which a try that broke leaves behind and the next continues with an HTTP `Range` request (`features/updates/download.py`); a file of another size than GitHub named is never installed. A nightly system install that fails is told on the bell and remembered until the next night (`os_install_failed`, in memory), when MirrorDash and the modules go first: the system goes first and one thing is done a night, so a build that failed every night (no room) kept everything else from updating. `failed_os_update` waits while the job says `restarting`: after `rauc install` the old system runs on for some seconds, and a check then counted a failed trial. The releases are asked for 100 at a time, cached for a minute.
* **Limits (p1)**: the trial boot proves the new kernel with the *old* `start.elf` in p1; `update-p1` then puts in the new one, which has never started this mirror. If it doesn't, the old p1 is still in its half of the card, but only a computer and `sfdisk -N 1` bring it back: a Pi 3 has no trial for p1.
* **Frozen in every image**: how a mirror installs an OS update can't change once an image is out: the sudo rule for `rauc install /storage/mirrordash/os-update.raucb`, `compatible=mirrordash-rpi`, the `verity` bundle format, the slot classes `rootfs` and `boot`, the certificate in the keyring, and the bundle name `mirrordash-os-v<version>-<YYYYMMDD-HHMM>.raucb` the app looks for. Changing one leaves the mirrors out there unable to install the update that would change it on them, so only reflashing helps; if one must change, the old way keeps working next to the new one until no older image is left. `tests/test_ab_updates.py::test_the_os_update_interface_stays_the_same` holds them.
* **Logs of failed updates**: The system log stays in RAM, so nothing is written to the SD card all day and it doesn't wear out (a journal kept on the card would write every few minutes, and a small write can cost a whole erase block). The price is that the log is gone after a restart, which is exactly when an update has failed. So `save-log` keeps a copy at that moment: a trial boot that fails (`mirrordash-save-trial-log`, before it restarts into the old slot), a failed `rauc install`, and an app update that `launch.sh` rolls back. The newest 5 are kept under `/storage/mirrordash/logs/`, listed under **Logs → Saved Logs**, and can be downloaded and deleted there. A kernel that doesn't start or finds no root runs no program, so nothing can be saved then; the admin page says the update didn't start.
* **Log times are UTC**: The app's log (ISO 8601 with `Z`, `main.py`), the system log in the Logs tab and the saved logs (`journalctl --utc -o short-iso`) and saved log file names all use UTC, so lines from different logs line up without a time zone or summer time in the way. Times written for people in the admin page (when a log was saved, until when developer logging is on) are local. A Pi has no clock battery: until NTP has set the time, every time is wrong whatever the zone.
* **Developer logging**: For working on a mirror, **Settings → Developer → Developer logging** keeps the whole system log on `/storage` across restarts: a drop-in in `/run` sets journald to `Storage=persistent` (after Pi OS's own `Storage=volatile`) and `/var/log/journal` is bind-mounted from `/storage/mirrordash/journal` (`mirrordash-dev-logging`, at boot and hourly). Off by default and off by itself after 7 days, so a forgotten switch doesn't wear the card for years; capped at 64 MB. The image's machine-id is `uninitialized`, so every start gets a new one and its own journal folder, which journald alone doesn't trim: the script deletes the oldest starts' folders beyond the cap, and the Logs tab reads them merged (`journalctl -m`). Whether it's on is a file on `/storage` holding when it turns off, so it works at boot before the app runs.

## 32. Sound and Hardware Video: a Lean GStreamer in the Image, Played Outside the Browser
> **In short:** The image has a small GStreamer for radio, TV and camera streams, played in a window of their own outside the browser, with the Pi's hardware decoder.

* **Decision**: The image carries GStreamer's base, ALSA and GL plugins and `gst-launch-1.0`. From the good and bad sets it carries only the plugins for radio, TV and camera streams (`step_media` in `configure_image.sh`): `video4linux2` (the Pi's H.264 decoder, `/dev/video10`), `adaptivedemux2` (HLS), `isomp4`, `audioparsers`, `mpg123`, `soup` (HTTP), `icydemux` (Icecast radio), `videoparsersbad` (`h264parse`), `waylandsink`, `faad` (AAC) and `autodetect` (`autoaudiosink`, without which WebKit's web process crashed on any `<audio>` or `<video>`). They are copied out of the .debs, with the libraries they need installed by name. The build fails if any of them doesn't load. A module plays media by starting `gst-launch-1.0` (for example `playbin3 uri=…`) as user pi, with `WAYLAND_DISPLAY=wayland-0` and `waylandsink fullscreen=true` for video and `alsasink` for sound; the video covers the mirror while it plays.
* **Rationale**: Modules can't bring system packages: a module is a Python package on `/storage`, and the root is read-only and replaced on every OS update. So what modules need for media has to be in the image, and it has to be small, since every MB is in every OS update. The full good and bad sets plus libav came to 277 MB, mostly unrelated libraries: plugins-bad pulls in ONNX runtime, oneDNN, LAPACK and GTK 3, and libav pulls in x265 and libavfilter. The chosen set is about 12 MB (13 packages and 2.4 MB of plugins), and `faad` decodes AAC instead of libav. Tested on a Pi 3B (2026-10-19), with only these plugins, an SVT live stream played on the hardware decoder at 50 fps, 1080p included (fullscreen: [MEASUREMENTS.md](MEASUREMENTS.md#video-on-a-pi-3)), at 30–50 % CPU; Sveriges Radio played at about 8 %. In Cog the same stream ran at 3–5 fps with both cores full. WebKit decoded it in software: its web process runs in a bwrap sandbox that most likely hides `/dev/video10` (unproven; the sandbox stays, it guards the mirror against harmful pages). WebKit also blocks sound that starts without a tap, and a mirror has no one to tap.
* **Measured**: fullscreen against a window, video inside the page, the sources and sound, and the other compositors are in [MEASUREMENTS.md](MEASUREMENTS.md#video-on-a-pi-3).
* **Where this leaves video (2026-10-20)**: a TV module should play fullscreen in its own GStreamer process, with the screen switched to 50 Hz while it plays. Optionally it plays in a window over the module's card (a labwc window rule), with the screen at 1920×1080@50 and the other modules holding still while it plays (or the screen switched to 1280×720@50). A window that stays smooth while the rest of the mirror updates needs WebKit 2.52+ (video in the page, the decoder in the sandbox) or a Pi 4/5. A heatsink is cheap headroom behind the glass: the Pi 3B idles at about 51 °C.
* **Video in the page on WPE 2.54 (2026-11-13)**: the sandbox no longer hides the decoder, but the video is painted only with `WEBKIT_GST_DMABUF_SINK_DISABLED=1`, and then it takes about 135–141 % CPU with about 25 late frames per 30 s, far above the limits of a TV module (60 %, one gap per 10 s), so "needs WebKit 2.52+" above does not hold for a Pi 3 ([MEASUREMENTS.md](MEASUREMENTS.md#video-in-the-page-and-in-an-own-window-wpe-254-2026-11-13)).
* **Limits**: Streams with DRM (TV4, Netflix) can't play. Copied files aren't in dpkg's database: they are refreshed when an image is built, not by apt, which never runs on a mirror anyway.

## 33. Modules Update Once a Minute While a Video Plays
> **In short:** While a video plays, the other modules' updates are held and sent once a minute, so the Pi keeps up with the video.

* **Decision**: A module that plays a video wraps the playback in `async with self.video_is_playing():` (injected like `fetch`). While any module plays, the websocket manager (`screen.py`) holds the other modules' updates and sends the latest of each on every whole minute, and at once when the last video stops; the playing module's own updates go out as usual. The page (`js/kiosk/core.js`) hears `{"type": "video_is_playing"}` (and the state in `hello`), puts `data-video-is-playing` on `<html>` and on every module's host, fires the `mirrordash:video_is_playing` event, steps the carousels on the minute without their fade (one a minute at most; a slower one keeps its pace), and `modules.css` pauses every animation and transition inside the modules. Whether a module goes away meanwhile is its own choice, from the same attribute (`:host([data-video-is-playing]) { display: none; }` in its CSS). A module's own timers are its own: while the attribute is set, nothing on its card should change more than once a minute, on the minute (the clock hides its seconds and ticks on the minute).
* **Rationale**: Under labwc, every redraw of the page costs the Pi 3's GPU about one frame of a video window (#32, [MEASUREMENTS.md](MEASUREMENTS.md#video-on-a-pi-3)): the clock's seconds alone dropped 67 frames in 90 s at 1080p50, 11 without them. Gathering every change on the same moment gives one short hitch a minute, which the owner accepted, without switching the screen to 720p. The name says when and why a module should adapt, so it means nothing else (not the screen being off, which #29 covers). Rewriting the page's `setInterval` and `requestAnimationFrame` for the modules was rejected: hidden, and it breaks modules in ways their authors can't see. Modules that ignore the signal cost a few frames, not a broken page.

## 34. A Module's Video Window: the Core Places It, the Module Plays It
> **In short:** A module plays a video in its own player; the core only puts the player's window where the card marks it.

* **Decision**: The core only gives a video its place; the player and what it plays belong to the module. A module wraps its own player in `async with self.video_window(fullscreen=False, hz=None) as window:` (injected like `fetch`). The card marks where the video goes with an element carrying `data-video-window`; the core asks the mirror's own page for its place (`{"type": "video_window"}` over the websocket; only a loopback client's answer counts), writes a labwc window rule for the app id `window.app_id` (`mirrordash-video`) into `~/.config/labwc/rc.xml` at that place, reloads labwc (`SIGHUP`), switches the screen to `hz` when the current resolution has that rate (50 for European TV), and holds `video_is_playing` (#33). When the block ends, also by an error or a cancel, everything is put back. One video window at a time; a second waits. The OS image gives the libraries: the lean GStreamer of #32 and its Python bindings (`python3-gi` and the GStreamer typelibs, about 3 MB), so a player runs on the system's Python (`/usr/bin/python3 -I`), which has them; the app's own Python (uv's, in the venv) doesn't.
* **Rationale**: Only the core may write the system's files and change the screen's mode, and only the page knows where the card is, so the place follows the layout like any module's. What to play and how (sources, playlists, YouTube) changes with the sources and ships with the module that knows them. A first version played the video in the core too and was split this way on the owner's call: the core stays small, and a second video module brings its own player.
* **For a module's player**: a small GStreamer player in Python, not `gst-launch-1.0` (what works and why: [MEASUREMENTS.md](MEASUREMENTS.md#a-modules-video-player)).
* **Limits**: The window's place is taken when the block starts; a card that moves while it plays leaves the video where it was. A carousel that hides the card doesn't hide the video. vc4 rotates planes only 0°/180°, so on a portrait mirror the window is composited like any other (#32).
* **Measured (2026-11-13)**: an own `waylandsink` window takes 22–26 % CPU at 720p50 beside the live page, but drops frames in the page's repaint spikes (1.5–2.6 gaps per 10 s, over the limit of one); fullscreen (direct scanout) and a 25 fps window had 0 gaps. A labwc window rule worked in a nested labwc only, not yet in the real session ([MEASUREMENTS.md](MEASUREMENTS.md#video-in-the-page-and-in-an-own-window-wpe-254-2026-11-13)).

## 35. Matter: a Node.js Sidecar That Runs the Screen Through /api/v1
> **In short:** The mirror is a Matter device (its screen an on/off light), run by a small Node.js program that talks to `/api/v1`.

* **Decision**: The mirror is a Matter device: its screen is an on/off light (`OnOffLightDevice`), nothing else. The node is `matter/index.mjs`, a small matter.js program installed in the image at `/opt/mirrordash-matter` (`step_matter`, Debian's `nodejs`, `npm ci` from the pinned lock file, then npm removed) and run as `mirrordash-matter.service` (user pi). It only talks to `/api/v1` (#24) on localhost: `GET /status` every 2 s for the screen's state, `POST /screen` when a home app turns it on or off. It is paired over the network (mDNS, the mirror is already on Wi-Fi), without Bluetooth. The core runs it from `features/matter`: turning Matter on makes the pairing codes once per mirror (random passcode outside the spec's forbidden ones, random discriminator, and the serial number and UniqueID `mirrordash-<8 hex>`, which a pairing reset makes anew as the spec asks, in `config["matter"]`), and on every start a new token, of which only the hash is kept (`config["matter"]["token_hash"]`, accepted by `require_api_token` beside the API card's), written with the codes to `~/.mirrordash/matter.env` (0600) for the unit's `EnvironmentFile`; then `sudo systemctl restart mirrordash-matter`. The unit isn't enabled: `/etc` is a RAM overlay (#5), so the core starts it at its own start when the config says so, like SSH. The node keeps its fabrics in `~/.mirrordash/matter/` and writes `pairing.json` (QR payload, manual code, commissioned) there, which the admin page's Matter card shows (QR drawn by the same `qrcode.js` as the Wi-Fi setup).
* **Rationale**: matter.js was the only library that can be a device (not only a controller) and complete pairing over IP with Apple, Google, Alexa, SmartThings and Home Assistant; the Python ones couldn't (CircuitMatter doesn't finish commissioning, `chip-core` only controls). A sidecar on the public API keeps Node out of the core and gives it no more power than a Home Assistant token. Its own token means a new API token doesn't unpair anything, and a token made anew at each start never has to survive a restore. The files sit next to `data/`, not in it, so a backup carries neither the pairing keys nor the token.
* **Limits**: Uncertified (test vendor `0xFFF1`, product `0x8000`): the apps warn, and Google Home needs a Developer Console project with those IDs (user guide). A change on the mirror reaches the apps up to 2 s late (polling; a push from the event bus is the upgrade). It costs about 90 MB in the image (Node.js about 70, matter.js trimmed to its ES modules about 20) and about 100 MB of RAM while on (measured on the Pi 3B, 2026-10-12). The node is updated with the OS image, not with app updates. Brightness and the sensors (occupancy, temperature, lux) would be more endpoints on the same node; left out until asked for.
* **Watch** (2026-11-06): the node runs on Debian trixie's Node.js 20 (20.19.2), which upstream stopped supporting on 2026-04-30; Debian still ships its security fixes for trixie, alone. matter.js 0.17.9 asks for Node >= 20.19 (`matter/package.json`). When a matter.js release asks for a newer Node, trixie can't give it: the same corner WPE was in (#56). Then: a Node from forky or NodeSource in the image, or the node held at its last matter.js that runs on 20.

## 36. The App's Root Rights: Fixed Commands, a udev Rule and polkit
> **In short:** The app runs as `pi`; every root action is one fixed sudo command, a udev rule or a polkit rule, and a helper that takes input checks it itself.

* **Decision**: The app runs as `pi`, and every root action it needs is either a sudo rule for one fixed command (`scripts/image/rootfs/etc/sudoers.d/`), a file the `video` group may write (the backlight, `90-mirrordash-backlight.rules`), or a polkit rule (NetworkManager, `50-mirrordash-networkmanager.rules`, so `nmcli` runs as pi). Where a command needs input, a root-owned helper takes it and checks it: `mirrordash-pi-password` reads one crypt hash on stdin and sets only pi's password; `mirrordash-gpio-overlays` takes a fixed vocabulary. A `*` may only end a sudo rule (`tests/test_configure_image.py::test_sudo_rules_give_no_way_to_root`).
* **Rationale**: Modules run in the app's process, so whatever the app may do as root, any installed module may too. A bare `chpasswd` let it set root's password, and the `*` in `tee /sys/class/backlight/*/brightness` matches spaces, so tee could be handed any file; `sudo nmcli *` could read any file as root (an import, a certificate path). The fixed rules make the sudo list the real boundary it looks like.
* **Limits**: A module still had everything pi has: the owner's settings, the network, the admin password's hash (until #41: each module now runs as a user of its own). The admin page marks official modules and warns before others (#26). The build removes Pi OS's own `010_pi-nopasswd` (`pi ALL=(ALL) NOPASSWD: ALL`) and takes pi out of the `sudo` group; with them left in, every rule here was moot. Where a sandbox would have to go: #38.

## 37. The Mirror Stands Still Between Updates; a Dark Screen Draws Nothing
> **In short:** MirrorDash's own modules stand still between updates and a dark screen draws nothing; endless motion is the owner's call, discouraged and always possible to turn off.

* **Decision**: Motion that never ends is strongly advised against, not forbidden: the cost is the owner's to weigh, and the owner decides. MirrorDash's own modules stand still between updates: a list that doesn't fit steps, one item slides up (a short `transition`), then it stands still for a few seconds (the news module since 1.2.1). A module that does keep moving (falling snow, a smooth ticker) says so and lets the owner turn the motion off or down in its settings. `mirrordash-sdk validate` warns hard about an `infinite` CSS animation or a `requestAnimationFrame` loop, and mildly about `infinite` with `steps()`; it never refuses. Endless motion also costs video: while a video plays the core pauses every CSS animation in the modules (`modules.css`, #33), but not a module's own JavaScript, and each redraw a script causes costs the video a frame (#33's measurement). The core has no pause for a dark screen: it isn't needed.
* **Rationale**: Measured on a Pi 3B at 1080p (2026-10-23): the news module's endless scroll (`linear infinite`, under a `mask-image` fade) made WebKit draw 60 frames a second all day. The compositor thread took 17 % of a core, labwc 13 %, cog 6 %, a kernel thread waited on page flips (load ~1.6 on an idle CPU), the CPU stayed at full clock and the Pi sat at 66 °C; with the scroll stepping instead, 54 °C. A smooth scroll with `steps(N)`, one whole pixel per step, no mask (the fades as still gradients on top) and `will-change: transform` drew only when it had moved a pixel: 28 flips a second at 28 px/s, about a quarter of the cost (WebKit 7 %, labwc 2 %, cog 3 %), but never free. A still page draws nothing. With the screen off the output is disabled (`wlr-randr --off`), labwc asks for no frames and WebKit drew nothing even under the endless scroll (0 % and 0 flips), so pausing animations for a dark screen would save nothing; a module's own timers keep running, at no measurable cost.

## 38. Locking Modules Down: Where the Boundary Has to Be
> **In short:** The analysis behind #41: a module can only be kept from the core, its secrets and the system by a process and a user of its own.

* **Decision** (2026-10-24, built as #41): in the core's process every limit is voluntary, since a module can undo any check written in Python next to it; only the kernel holds a line, so a module runs in another process as another user, and the screen gets a CSP (#41).
* **Weighed**: one module host for all modules (built first, then a user per instance inside it); a systemd unit per module with `DynamicUser=` (30+ MB each, #41); an iframe per card (isolates its script, but breaks the shadow-root design of #21 and costs a document each); requiring built wheels at install (stops builds only, not what a wheel holds). The module API stayed as it was: the host injects the same helpers, so modules kept their source.

## 39. Backups: Encrypted Ones Carry the Logins, and a New Mirror Can Start From One
> **In short:** A backup is a zip: a plain one holds no secrets; one with a password is encrypted and also holds the logins and Wi-Fi, so a new mirror can start from it.

* **Decision**: A backup is a zip. Without a password it holds no secrets: the config without `admin_auth`, no `pi_password.hash`, no Wi-Fi. With a password the whole file is encrypted with `openssl enc -aes-256-cbc -pbkdf2 -iter 600000` (the password in the environment, never on the command line) and also holds the admin password, the pi password and the saved Wi-Fi networks with their passwords (`wifi.json`, read with `nmcli -s`, which polkit's `settings.modify.system` allows). A restore takes the backup's admin password when it has one. Never in a backup, either way: `sessions.json` (a login cookie must not work on another mirror), `config.json.bak` and `config.json.broken-*` (they hold what a plain backup leaves out). Modules are restored into the next A/B venv (#16). The Wi-Fi setup page restores an encrypted backup too, while the mirror has no admin password (the same rule as the rest of that page): it joins a network from the backup first, since the modules come from GitHub, then restores.
* **Rationale**: Setting a mirror up again (a new card, a second mirror) should be one step. ZIP's own encryption (ZipCrypto) breaks with a known-plaintext attack, and a backup's layout is known, so it couldn't carry Wi-Fi passwords in plain text. openssl is in the image already, so no dependency. Before an admin password exists, anyone near the mirror could set it up anyway, so restoring from the setup page opens nothing new.
* **Limits**: CBC without a MAC: a changed file fails as a broken zip rather than being detected (upgrade: openssl's AEAD modes). Backups from before this (ZipCrypto) can't be read; no compatibility before 1.0.

## 40. A Module's Own Routes: Under /api/modules/<instance>, Nowhere Else
> **In short:** A module's own HTTP routes are served only under `/api/modules/<instance>/`, forwarded to its process; the module checks its callers itself.

* **Decision**: A module that sets `self.router` (a FastAPI `APIRouter`) is served at `/api/modules/<instance>/...` by one ASGI app mounted there (`module_routes` in `features/modules/api_proxy.py`), which looks the running instance up on every request. The module gets the path as `config["api_path"]`. The core puts no login in front: the module checks its callers itself.
* **Rationale**: Modules talk to devices on the home network (an ESP32 posting a reading, a phone shortcut flipping a relay), and a fixed prefix means a module can't add or shadow a route of the core, the way `app.add_api_route` from inside the process could. Looking the instance up per request needs nothing on a reload, and a disabled module is a 404. An `APIRouter` is what the module host of #38 step 1 can serve over its socket too, so modules keep their source when the sandbox comes.
* **Limits**: The routes run in the module host (#41): the core sends each call over its socket and the host runs it through a FastAPI app around the router. HTTP only (no WebSockets), 1 MB in, 4 MB out, 30 s. GPIO: the host's user may open `/dev/gpiochip*`, I²C and SPI (#41); the pins the core's overlays hold (buttons, PIR) stay busy in the kernel.

## 41. Modules Run Apart From the Core, Each as a User of Its Own
> **In short:** Every module instance runs in a sandboxed module host, in a process of its own as a user of its own, and reaches the core only over its own connection.

* **Decision**: Every module instance runs in the module host (`features/modules/host.py`, `forkserver.py`, `mirrordash-modules.service`), in a process of its own as a user of its own (uid 70100 and up), never in the core's process. The unit's main process is a forkserver; its first fork, the control process (the unit's user `mirrordash-mod`), answers the core's connection on the unix socket (`/run/mirrordash-modules/host.sock`, through the group `mirrordash-mod`, which pi is in): the users, the site's steps and the sandbox's checks. To start an instance the core (`client.py`) makes two socket pairs and passes one end of each over the second connection (`host.sock.fds`); the forkserver gives them to the instance's new process, so **its connection is who it is**: the core sends it its own settings only (`config["modules"][instance]` and `globals`, never the rest of config.json), the screen going on or off, hardware events and calls to `/api/modules/<instance>/`, and takes from it its HTML (placed by the core: position, carousel), its GPIO requests, its public events (`event_bus.publish(..., public=True)`: the core passes them to every instance, never to its own subscribers, only named `<its package>.…`, 64 kB and 20 a second at most; a plain publish stays in the instance's process) and its log lines (under `mirrordash.modules.<instance>`, whatever name it gives), checked as input from outside, whatever instance a message names. A changed setting restarts that instance alone (a move on the screen none); the cards of the others are sent again to the reloaded screen. The protocol is in host.py's docstring. The core never imports a module: schema, icon and translations are read as files (`package_dir`, which finds a package without running it), and the upgrade check imports the modules in the host. When the core goes (a restart, an update) the instances' connections close and they stop, the control process exits and with it the forkserver; systemd starts it again with the venv there is now. Off a mirror (development, the SDK's `start`) the core starts the host as its own child: the same processes, as the developer's user, without the sandbox.
* **The sandbox** (the unit): the system read-only, its own folder writable (`/storage/mirrordash/modules`: data_dir and cache_dir), the core's data dir (0700 and InaccessiblePaths), its logs and the SSH and Wi-Fi keys out of sight, no D-Bus, NoNewPrivileges, only the system calls of `@system-service`, and of the capabilities only `CAP_SETUID CAP_SETGID CAP_CHOWN` (ambient), which only the forkserver keeps (below). Devices: I²C, SPI and sound playback only (DevicePolicy=closed; the unit's user is in i2c, spi and audio, and the instances' processes keep those groups). Of sound, a module plays but never records: a microphone's capture node (`pcmC*D*c`, a USB microphone or webcam plugged in at any time) is root's alone (`72-mirrordash-sound.rules`, before `73-seat-late.rules` so logind gives pi no ACL on it either), and the self-check counts one a module can open; the cards are allowed by class (`char-alsa`), not by node, since nothing fixes their numbers (on the Pi 3B HDMI is card 0, the jack card 1), and of the I²C buses only the header's, `i2c-1` (a udev rule gives the others to root: one is the screen's DDC/CI, brightness and power; ddcutil runs through sudo). No GPIO chip and no gpiomem: a chip is every one of its lines, the SD card's and the core's too, since the Pi's pin control isn't strict and a line can be taken from I²C or the SD card, and gpiomem maps the registers (the Pi kernels have no gpio-aggregator to give out a part of a chip). A module asks for pins instead (`await self.gpio([27], output=True)`, `features/hardware/gpio.py`): the core requests exactly those lines with the kernel's v2 ioctl, if they are free header pins (GPIO 2–27, not a Hardware tab device's, not I²C's while an I²C device is set up), and sends the request's file descriptor over the instance's own descriptor socket (SOCK_SEQPACKET, SCM_RIGHTS: a stream drops it). That descriptor drives those lines and no other; the instance releases them when its run_loop ends. Network (written as addresses and systemd's own names only: it skips a word it doesn't know, like `localnet`, with a mere warning, and the first image left the home network and loopback open that way; `test_ip_filters_name_only_what_systemd_knows`): IPAddressDeny of the home network, of the mirror itself (127.0.0.0/8: the core's routes that trust loopback) and of IPv6 (a device at home can have a global address); IPAddressAllow of systemd-resolved's stub (127.0.0.53: why resolved is in the image, as the router is usually the DNS server) and of the addresses the owner typed in settings marked `"format": "lan-url"`, each to its own instance's user: the core runs `mirrordash-module-network <uid>=<address> ...` through sudo at every start and every 10 minutes; it lets through only the modules' users and home-network addresses, opens their union to the unit (IPAddressAllow) and keeps each to its user with nftables (`meta skuid <uid> ip daddr <address> accept`, then those addresses refused to the host's other users `with icmpx admin-prohibited`: a plain reject reads as "refused", which the self-check counts as reached). Never the mirror itself, whatever was typed (its own LAN address or `mirrordash.local` would open nginx, SSH and Matter to the module): a first rule refuses the modules' users every address the kernel calls local (`fib daddr type local`, every interface, a DHCP change included) but resolved's stub, checked in a network namespace. MemoryMax (30 %, no swap) and CPUWeight, so a runaway module can't take the core and the screen with it; the Pi's firmware turns the memory controller off (`cgroup_disable=memory`), so the image's cmdline.txt turns it on again (`cgroup_enable=memory`). At the limit the kernel kills one process (`OOMPolicy=continue`), an instance's first (`oom_score_adj` 500); the core starts it again and, after `CRASH_LIMIT` (3) deaths in a row each within `CRASH_WINDOW` (5 min) of its start, leaves it off with the Dashboard's *Start Modules Again*, naming it, while the others run on. Fixed uids (960, 70000 and up): `/storage` outlives the OS image. The core (pi) reads and writes the host's folder only for backups, and follows no symlink there: one the host put in would have pi copy the core's data into the backup, or delete and write in it on a restore.
* **Fail closed** (2026-10-27): systemd starts the unit with a mere warning when the kernel lacks what a directive needs (cgroup BPF, the memory controller, namespaces) or a newer systemd no longer knows one, so the self-check (`sandbox_checks`, as a module's user; on a mirror also that `memory.max` holds in the unit's cgroup) runs before any instance does: the control process answers the core's `uids` only once it ran, with what it found open, and refuses every instance while anything is. The core then starts none, stops those running and says so on the Dashboard (*Modules stopped for safety*), until a core restart finds it closed. A false alarm costs the modules, not the mirror; an open sandbox would cost the owner's home network. Checked before it ships: `systemd-analyze verify` in the image build fails on any directive the image's systemd ignores (`build_image.sh`), and CI runs `scripts/sandbox-check` (the real unit under Debian's systemd, arm64) on every push.
* **The screen** (`mirrordash-screen`, #56): it may reach the mirror and the internet, not the home network. The page gets a CSP: pictures and video from anywhere, but `connect-src 'self'` (no fetch or WebSocket elsewhere), no frames, forms or plugins, and only scripts with the page's nonce (new each load). core.js gives it to a card's `<script>`s only if its module may run them (`scripts_allowed`: one in the core's venv, the image's clock or a developer's, or one whose site folder's name is in config's `module_scripts`: put there when it is installed from `OFFICIAL_OWNER`'s GitHub, taken out when one of that name comes from anywhere else or it is uninstalled, and switched by the owner in its settings); another card's scripts are removed, and its `onerror=`, `javascript:` or `<iframe srcdoc>` don't run (tested in WebKit). *Rationale*: a script in the page reaches every card (a closed shadow root doesn't stop it: it can patch `attachShadow` or read the WebSocket), so it could send what the calendar or Home Assistant shows to the internet; `frame-src 'none'` because a frame of a page of this site's runs its scripts with the page in reach. Iframes per card would have isolated even the allowed ones, for about 2 MB a card on the Pi 3B (measured, nine cards) and a layout that has to measure each card; the owner's yes was chosen instead. Whether a module is MirrorDash's own comes from the install target, never from where its folder says it came from (`direct_url.json`, Project-URL): those are the module's own to write. The routes the OS calls (`/admin/auto-update`, `/api/wifi/changed`) want the core's `local-token` (in its data dir, new at every start) besides loopback: a module's card runs JS on loopback too. The page and its WebSocket are the mirror's own (`on_screen`: loopback, which the kiosk reaches without nginx; through nginx uvicorn sees the real address, the rightmost of `X-Forwarded-For`); another browser gets a redirect to the admin page. So a card's script never runs in a browser logged in to the admin page, and the two keep one origin without a port or hostname of their own: the kiosk has no admin session to use, and the token covers the loopback routes. Off a mirror the developer's browser is loopback too.
* **The admin page**: what a module supplies is its author's text. Schema titles, descriptions and option labels are escaped; keys and names that reach ids and JS are only `[A-Za-z0-9_-]` (`SAFE_NAME`, `SAFE_KEY`; an entry point or instance with another name is left out); icon.svg becomes a `data:` URL drawn as a CSS mask. All three ran a module's script in the logged-in admin page before. A module route's answer gets `Content-Security-Policy: sandbox` and no `Set-Cookie`, `Service-Worker-Allowed` (a service worker over the screen's whole site) or `Clear-Site-Data`, and the call reaches it without the owner's `Cookie`.
* **Rationale**: In one process every limit is voluntary (#38); a process and a user let the kernel hold the line, between the core and the modules and between the modules. Not a Python of its own per module (34 MB and 4 s each on a Pi 3B, measured) nor a systemd unit each ([MEASUREMENTS.md](MEASUREMENTS.md#a-systemd-unit-per-instance)), least of all on a 512 MB Pi 3 A+: the forkserver has the core's code, fastapi and the venv imported and `gc.freeze()`d, so a fork shares it (about 9 MB of its own in the real unit, against 34 MB, so three to four times less: the nine instances on the test mirror use 92 MB more than one process, see Limits; a fork in the experiment before, which used little of what it inherited, had 2 MB). Keeping the module API as it was (the instance's process injects the same helpers) means no module had to change, except Home Assistant marking its URL `lan-url`.
* **The module site**: modules aren't installed in the core's venv. They live in `/storage/mirrordash/modules/site`, a link the host switches between `site_a` and `site_b` like the core's venv (#16). Each of those holds only links, one per module (`site_b/mirrordash-news → ../pkgs/mirrordash-news_3`), written by the control process alone; each module is installed in a new folder of its own in `pkgs` with its dependencies (`uv pip install --target pkgs/<name>_<n>`, `--no-cache`, then `compileall`), in a process of its own as that module's user (one per module and where it comes from, 70002–70099, kept in `package_uids.json` by `package_user`: a module of an installed one's name from another GitHub owner or PyPI built as the installed one's user before, so it could change that code and fail on purpose, and the code kept its scripts on the screen; checks and cleaning run as the folder's owner; the folder is that user's, readable by all, and its `HOME`, with uv's `--no-config`: uv and git read their config from `HOME`, and in the unit's shared `/tmp` another module had planted an index and a git `insteadOf` for the next install, `scripts/sandbox-check`). So a package's build backend, the files its wheel holds and its `.pth` reach that module's folder and process only: never another module's code, the links, the core, the forkserver or another module's process. The core asks for each step (`ModuleHost.packages`: prepare the next site with the active one's links or none, `pip` one module at a time (install into a new folder, linked in only if uv succeeded and the module claims no name another module has, a module in the core's venv too (the image's clock, which the site shadows) unless it is a newer version of that package; uninstall takes the link out), `check` the modules import from their folders, each as its user, commit or revert); a folder no site links to any more (an older version, an uninstalled module, a failed install) is emptied by its user and removed at the next prepare. The core only reads the modules' files, and only those that really lie in a module's folder or on sys.path (`module_file`: a link put there to the core's data isn't followed): entry points through `importlib.metadata.distributions(path=…)`, a package's folder through `PathFinder`, in the entry point's own folder first (neither runs a `.pth`). An instance's process adds its module's folder alone, after the core's own packages (`site.addsitedir` in `ModuleLoader.start_modules`, only there: it runs the folder's `.pth` files), since `--target` installs every dependency again and a module's copy mustn't shadow the core's. *Rationale*: in one shared site (until 0.9.4) any module's install could change the others' code, its `.pth` ran in every module's process, and a package of a name another module imported replaced that one's for both; `--only-binary` would only have stopped the builds (a wheel's files and `.pth` go where they like) and ruled out modules whose dependencies have no wheel for the Pi. The price: a dependency two modules share is on the card twice (`babel`, about 30 MB), and a mirror from before had to install its modules again (no migration before 1.0). A new Python (#16) gets an empty site built for it in the same step as its venv, and both are switched in together; launch.sh's fallback to venv_old switches back to the old site when the two venvs' Pythons differ (the old site is untouched until the next module change). Local modules restored from a backup go to `modules/local`, where the host can build them. Off a mirror the same, with the site in the developer's `~/.mirrordash/module-data` (a module installed into the venv by hand is found there too). The host checks its own limits when the core connects (`sandbox_checks`, as the self-check's user: what systemd only warns about when the kernel can't filter: the mirror's ports 80 and 8000, the router, the folders it mustn't read, the devices besides the header's I2C bus; and what a user per instance needs: another module's data, writing the site, capabilities left over) and logs an error that shows under Logs when one is open. *Logs → Diagnostics* asks it again (`diagnose`), with what systemd knows of it (memory, restarts, lan-url addresses) and each instance's GPIO lines, and offers it all with the logs, versions, `rauc status` and `systemd-analyze security` as one download, to find a fault without SSH. It needs no right the app doesn't have; the settings aren't in the download. The host answers for itself, so it finds a kernel, unit or mode that doesn't hold, not a module that took the control process over. A `lan-url` setting's default is only a placeholder in the form: saving it unchanged opens nothing.
* **A user per instance** (built and checked 2026-10-25 after an analysis by experiment: a container running it as systemd would with `setpriv`, measured on the Pi, then the real unit under systemd in a container, `scripts/sandbox-check`). The forkserver (`forkserver.py`) runs one thread, imports only the core's code (never the module site's: a package there would run with its capabilities), `gc.freeze()`s it, sets `PR_SET_DUMPABLE` 0 and only forks, on a request from the control process it checks (a kind, a uid of that kind's range, an instance's safe name). A child: every descriptor but stdio and its own sockets closed (a fork inherits the forkserver's), `setgroups` to the unit's groups but `mirrordash-mod` (i2c and spi stay), `setresgid`/`setresuid` to its uid, **its capabilities cleared by hand** (`PR_CAP_AMBIENT_CLEAR_ALL` and `capset` to zero, then checked in `/proc/self/status`: changing from one non-root uid to another keeps them, and without the clearing a module became uid 0 again in the experiment), `PR_SET_PDEATHSIG` after the change (which clears it), dumpable again (non-dumpable, its own `/proc` files are root's) to raise its `oom_score_adj` to 500, no `pycache_prefix` and no bytecode written (the unit's prefix is the forkserver's own; the site's process compiles the site), `HOME` its data folder and `TMPDIR` its cache folder. The forkserver can't signal it (another uid, EPERM without `CAP_KILL`): an instance stops when the core closes its connection, and a thread in it ends the process `STOP_GRACE_SECONDS` (5 s) later, for a loop that never lets it read the close. Its users: one per installed module (70002–70099, uv and its build in its own folder: the module site, above), the self-check's (70001, `probe_main`, which looks at the sandbox as a module would: also another module's data, writing the site or a module's folder and capabilities left over), and one per instance from 70100, kept in `uids.json` in the host's folder and never given to another instance (its data may still be there). Files: the host's folder and its `data` and `cache` 2771 (others may pass, not list; set by mirrordash-hydrate.sh as root, as the sandbox refuses a setgid mode), the site's folders of links and `pkgs` the unit's user's and readable by all (`take_module_site_folders` at the forkserver's start, which takes back what an older shared site left in them), a module's folder its user's and readable by all (made by the forkserver before that user's first step in it, `o+rX` set while it still owns it: after the `chown` it would need `CAP_FOWNER`), an instance's data and cache folders its uid's in the group mirrordash-mod (setgid from their parent), so pi still reads and restores them through the group and other modules can't; what pi restored belongs to pi, so the forkserver gives the folder back to the instance (by file descriptor: `O_NOFOLLOW`, no link followed, a hard-linked file left alone) before it starts it. Checked under the real unit and on a Pi 3B: [MEASUREMENTS.md](MEASUREMENTS.md#the-module-sandbox). On an OS image without the capabilities no module runs (they would run as the unit's user beside the forkserver), and the host says to install the system update. 
* **Limits**: Modules still share the unit: its memory limit (one can use it up before the kernel picks it), its `/tmp` and `/dev/shm` (sticky, each user's own files, 16 MB each), the internet and their pins (one can take a line another wanted, first come). `/tmp` and `/dev/shm` are RAM and, with no swap, a file there can't be reclaimed: measured under systemd (2026-10-26) with `PrivateTmp=yes`, a module that left 130 MB in `/tmp` of a 150 MB unit and exited had the next module that wanted 40 MB killed instead, until the unit restarted; a file in the host's `/dev/shm` (outside PrivateTmp, and RemoveIPC removes only the unit's own user's) outlived the unit, its memory moved to `system.slice`, outside MemoryMax, until a reboot. So the unit has both of its own (`TemporaryFileSystem=`, 16 MB each, gone with the unit; `scripts/sandbox-check` writes 20 MB to each): no module of seven uses either (their `TMPDIR` is their cache folder on the card), and the site's `TMPDIR` is the module's folder, as uv unpacks a package there (32 MB was too little for the calendar's `babel`, measured). What a module sends the core is bounded, so a bad one can't take the core's memory or its log: a card over 512 kB isn't shown and a card reaches the screen at most every 0.5 s (the last one), log lines past 100 in 10 s are counted, not logged, and a module file the core reads (schema, translations, icon.svg) over 1 MB isn't read. Each module's user may have 256 processes and threads (`RLIMIT_NPROC`, forkserver `MAX_PROCESSES_PER_MODULE_USER`, only where it has a uid of its own), so a fork bomb stops there. A module's install can change its own folder (its earlier version too) and nothing else; all instances of a module run its one folder's code. What a module reads it can still send to the internet; the owner's choice of modules is the line there. The control process sees every instance's settings, as the core does. Memory: the test mirror's nine instances take 167 MB in the unit, about 92 MB more than one process; within a Pi 3B's 278 MB `MemoryMax`, and about five instances fit on a 512 MB Pi 3 A+ (30 %: 154 MB). ponytail: the measured way down is a process per module package instead of per instance (about 20 MB here; instances of one package would share a user). Where the memory goes, and what didn't help: [MEASUREMENTS.md](MEASUREMENTS.md#module-host-memory). **Backups**: unchanged by the users per instance, pi reaching the data through the group (above). The core walks the folder by file descriptors (backup/service.py `copy_out`, `_replace_in_module_folder`: `os.fwalk`, `O_NOFOLLOW` with `dir_fd`, `shutil.rmtree(dir_fd=)`), so a link swapped in while pi copies is never followed. Landlock (a process locking itself to its own folder without a user each) isn't in the Pi's kernel (rpi-v8 and rpi-2712 6.18, checked); nor Yama, which doesn't matter as the syscall filter already blocks ptrace (though not `/proc/<pid>/mem` between processes of one user, hence `PR_SET_DUMPABLE`). A module's card runs in the screen's page, so it can forge what the page reports (`video_window` places for other modules, the heartbeat app-watch reads); it can't reach more than the page itself does. A module can't use gpiod, gpiozero or RPi.GPIO; a change is one ioctl from the module's own process (microseconds), so a slow software PWM works with Python's jitter, but no fast protocol (WS2812). Real dimming would be a Hardware tab device on the kernel's pwm overlay. /storage has no quota, but ext4's reserve (5 %) is pi's too (`resgid=` in fstab), not the modules' user's: a module filling the card leaves the core room to save settings, though not for an OS update's download on a 16 GB card. The modules' folder is a file system of its own, in a sparse file on /storage (`modules.img`, made by mirrordash-hydrate.sh at the first start of an image: `mkfs.ext4` on the file, a quarter of /storage up to 8 GB, with what the folder held moved in; mounted over the folder with `loop,discard,nosuid,nodev` before the core and the host start, `discard` giving back what is deleted in it; growable later with `resize2fs`): a module that fills it gets "No space left" and the card keeps its room. The path stays, so backups don't change, and it works on mirrors that exist. When it doesn't mount, the modules run in the folder below it, without the limit. Not ext4 project quotas: they need `mkfs -O quota,project` (new cards only), a tool to set the limit (`quota` isn't in the image), and the files' owner can most likely move them to another project (`FS_IOC_FSSETXATTR`, allowed to the owner outside a user namespace; unverified), which a syscall filter can't tell apart from other ioctls. Nor a partition of its own: fixed for good, and only on new cards. Video players (#34) need Wayland, sound and the decoder: not in the sandbox, a permission to add with the first video module. A camera at home shows on a card through the module's own route, not from the page. Safe mode runs no modules (the host starts from the active venv), so a module can't be installed or updated there. The IP and device filters, the memory limit and the device groups hold on a Pi 3B (tested 2026-10-25). `ProcSubset=pid` hides the machine's `/proc` files (cpuinfo, meminfo, the kernel's settings) from the host; the host reads its route from `/proc/self/net`, which stays.

## 42. MQTT: the Mirror as a Home Assistant Device, and Modules That Expose Themselves
> **In short:** Over MQTT the mirror is a Home Assistant device, and a module can share values and take commands, when the owner allows it.

* **Decision** (built 2026-10-27, `features/mqtt`): the core keeps one connection to the owner's broker (the Settings tab's MQTT card) and is a Home Assistant device through device discovery. It partly reverses #24's "MQTT would mean a broker": most Home Assistant homes with Zigbee2MQTT have one, and only MQTT gives Home Assistant pushed events and entities without YAML. /api/v1 and Matter stay as they are.
* **What it gives**: through device discovery (`homeassistant/device/<mirror id>/config`, its entities under `components`, with `origin` and `availability`, sent again when `homeassistant/status` says `online` and whenever the settings or the hardware change) the mirror is one device: the screen, brightness, motion, the Hardware tab's climate and light sensors, the buttons (event: single, double, triple, long), the CPU temperature, and with the owner's yes a switch per module instance (on/off, through the admin page's own `set_instances_enabled`). What may be controlled is a `switch`/`number`; what may not, a `binary_sensor`/`sensor`, so Home Assistant shows no control that would be refused. Discovery has 32 platforms, among them `text`, `select`, `number`, `button`, `switch`, `notify`, `event` and `image`, but no `media_player` (home-assistant.io, checked 2026-10-27): a module playing video is told a URL through a `text` (255 characters at most, as far as known) or a script's `mqtt.publish`, never Home Assistant's media browser, which would need an integration of its own.
* **What another client on the broker can do** (measured 2026-10-27 against Mosquitto 2.1.2 in Docker, the mirror as aiomqtt 2.5.1 over MQTT 5, another logged-in user as Zigbee2MQTT): MQTT says nothing about who sent a message, so on a broker as Home Assistant's add-on is by default (logins, no ACL) any logged-in client can send the mirror a command, throw it off the broker by connecting with its client ID, and the mirror can write to any device's topics. A retained command is delivered again at every reconnect. With an ACL (the mirror writes `mirrordash/<id>/#` and its discovery, reads only its `…/set` topics; other clients only their own) and `use_username_as_clientid true` all of that was refused. What stayed: a client that must write discovery (Zigbee2MQTT, `homeassistant/+/+/+/config`) can add a made-up entity that claims the mirror's device; it can't make the mirror do anything. The mirror's own `MaximumPacketSize` (64 kB) had the broker drop a 1 MB command, and `retainHandling=2` on the subscription kept the retained one away. Home Assistant's own Mosquitto add-on (measured 2026-11-01, add-on 7.1.3 with Mosquitto 2.1.2 on a real mirror) doesn't apply the ACL to its logins: with its documented `customize` setup the mirror's user still read discovery it may only write and wrote outside its topics, as the add-on's auth plugin answers the ACL check before Mosquitto's own; and `use_username_as_clientid` in that folder opens a second listener on 1883, so the broker doesn't start.
* **Security, in layers**: (1) The broker: the mirror's own user and a client ID nobody else knows; the admin card shows ACL lines for a Mosquitto of the owner's own, and says that the add-on lets its logins through whatever an ACL says, so there only the card's choices hold. (2) The connection: MQTT 5, clean start (no session: nothing queued while the mirror was off is played later), `MaximumPacketSize`, `retainHandling=2`, a message with the retain flag dropped all the same, a last will so Home Assistant shows it offline, TLS with the broker's certificate checked as an option. (3) What is allowed: reading only, until the owner turns on control, per entity; a command is a type checked against its declaration (on/off, a number within its range, one of the options, text up to its length, a URL that is http(s)), at most a few a second, and never an admin action (install, restart, settings, backups); the screen and brightness go through the same functions as /api/v1. Every command is logged under Logs, by topic, as there is no sender to name. (4) The secrets: the broker password in config.json, out of a backup without a password like `admin_auth`. A signature or token in the payload was ruled out: Home Assistant's entities send plain values, so it would end discovery's point.
* **Where the client runs**: in the core, as /api/v1's peer. aiomqtt and paho-mqtt are pure Python (no memory-unsafe parsing), together about 750 kB and 1.5 MB of the core's memory beside what it imports already (measured), and every command is checked in the core in any case, where the screen's functions are. ponytail: a client of its own in the module host (another user, the broker's address opened like a lan-url) would keep a bug in the MQTT code from the core's secrets, for a protocol over the socket and about 9 MB.
* **Modules, if they want to**: a module declares what it exposes in `config_schema.json`, next to its settings, read as a file like the rest of it (the core never runs its code), so the admin page shows it before anything runs, like a phone shows an app's permissions:
  `"exposes": {"now_playing": {"type": "sensor"}, "play_url": {"type": "text", "format": "url", "maxLength": 255, "control": true}, "channel": {"type": "select", "options": ["SVT1", "SVT2"], "control": true}, "stop": {"type": "button", "control": true}}`
  Types: sensor, binary_sensor, event, text, select, number, button and switch; names `SAFE_KEY`, at most 32, a `title` of its own; what doesn't fit the rules (a name with `/` or `#`, an unknown type, a select without options, a number whose range isn't finite) is left out (`declarations`, and the SDK's validate says so). The instance sends `state {name, value}` over its own socket (its connection names it, whatever it says; checked against the declaration; the last value per entity goes out once a second) and gets `control {name, value}` only for what is declared with `control`, the owner allowed for that instance, and a value that fits; the instance's process calls the module's `on_control(name, value)`, and `self.expose(name, value)` sends. It never sees the broker or its password, and a control can only do what the module can in its sandbox. Each shared instance is a device of its own (`homeassistant/device/<mirror id>/<instance>/config`, under the mirror's id so one ACL line covers it, `via_device` the mirror). The owner's choices are in `config["mqtt"]["modules"]` (`{"<instance>": {"share": true, "control": ["channel"]}}`), not in the instance's settings: saving a module's form replaces those, and a change there would restart it; removing an instance removes its choice. The declaration isn't MQTT's: /api/v1 could serve the same entities with the same checks, and Matter later.
* **What else is kept closed** (from the security analysis of 2026-10-27, each with a test):
  * *A packet of any size*: paho reads whatever packet comes, up to 256 MB, whatever `MaximumPacketSize` the mirror asked for, so a broker that ignores it, or someone in between on plain MQTT, took a client to 230 MB (measured, a fake broker sending 200 MB). `guard_packet_size` ends the connection at a packet over 64 kB before reading it (32 MB, measured); it wraps paho's private `_sock_recv`, pinned in uv.lock, and `test_a_packet_over_the_limit_ends_the_connection_unread` fails if paho changes.
  * *The client ID*: a secret of its own (`client_id`, never shown), not the id every topic shows; on a broker without the ACL another client must guess it to throw the mirror off (scripts/mqtt-check: the visible id can't, the secret one can on an open broker, nothing on a locked one). A restore keeps this mirror's ids, never the backup's (two mirrors under one id would share their commands and throw each other off).
  * *Floods*: at most 100 waiting messages (`max_queued_incoming_messages`; aiomqtt's own line for each one it drops goes to a logger at ERROR), COMMAND_RATE commands a second, a refused one logged at most every 10 s with a count. Brightness (it writes the settings to the card) and modules on or off (each change reloads every module) are coalesced: the last brightness once a second, all waiting module changes in one save and one reload at most every 5 s.
  * *The log*: a topic is logged as `repr`, as a topic may hold a line break that would forge a line of the core's log.
  * *Left on the broker*: retained values stay there for any client to read; what a module no longer shared said is cleared (an empty retained message for each entity it declares, once a connection), a value it sent just before is dropped, and turning MQTT off clears every topic the mirror wrote.
  * *One command never ends the connection* (a module that went away meanwhile), and an error the bridge didn't expect ends that connection, not MQTT until the next restart.
  * The card checks the broker's name and the user and password (one line, bounded) at the trust boundary, never sends the password back to the page, and warns when there is no user (a broker that lets the mirror in without one lets anyone in). Its routes are the admin page's (login, SameSite=Strict, the Origin check).
* **Limits**: on Home Assistant's add-on, and on any broker without the card's ACL, any client on the broker can do what the owner allowed and fake the mirror's states and button presses for Home Assistant's automations (MQTT has no sender; the user guide says not to let a button unlock a door). Without TLS the mirror's MQTT password crosses the home network in plain text and a spoofed `homeassistant.local` gets it, so the guide asks for a login of the add-on, not a Home Assistant user (whose password opens Home Assistant). A module whose lan-url is the broker's host reaches the broker's port too (#41 opens an address, not a port); it still needs a login of its own. A client that may write discovery can still add a made-up entity to the mirror's device (above). TLS takes only a certificate a browser would trust (no CA upload; ponytail: a CA field on the card). A text holds 255 characters, Home Assistant's limit, and the check holds a script's `mqtt.publish` to the same, so a longer address (a signed stream) doesn't fit. No `media_player`.

## 43. The Settings Drawer's Preview: the Module Renders Its Own Sample Answers
> **In short:** The settings drawer shows the card as the unsaved form would draw it, rendered once from sample answers the module ships.

* **Decision**: A module's settings are a modal over nearly the whole screen: the settings on the left, the card on the right as the unsaved form would show it. Every change (debounced) posts the form to `/admin/panels/modules/preview/<module>`, which types and checks it as Save does (`_config_from_form`) and asks a process of the module to render it once (`ModuleHost.preview` → host `"preview"` → `preview.render_preview`): the instance's own, another instance's, or else the module's settings process (#48), so a module added a moment ago previews before it is saved. It is a throwaway object of the module's class (`throwaway.py`, shared with #48), whose `fetch`/`fetch_json` answer from the sample answers the module ships in `preview/fixtures.json` (`{"captured": "2026-11-02", "answers": {"*/api/states": "states.json"}}`, fnmatch on host + path). Its settings carry `preview: True` and a throwaway `data_dir`, so a module with a login of its own (Spotify) draws its sample answers instead of asking to log in. The dates in them move by the days since `captured`, so a forecast or a calendar stays current. A module without `preview/fixtures.json`, or whose process doesn't answer, shows the card the mirror shows now (`manager.latest_messages`), looked at again every 10 s; neither: "Not on the mirror yet".
* **Rationale**: The owner sees what a setting does before saving it, for every module and setting type, without the preview calling real services: no API quota or paid calls, no keys sent anywhere, and no home-network address (#41's lan-url) opened for a value nobody saved yet. The module draws the card itself, so the preview is the real card, and the sample answers are the module's own (often the data its tests use anyway). Lists fold to one line per item (`forms.py` `render_array_item`, the line filled in by `admin.js` `arrayItemSummary`) so a long list doesn't push the rest away.
* **Boundary**: The card is module HTML, so it never enters the admin page's DOM: it comes back as a page for the srcdoc of an iframe with `sandbox="allow-scripts"`, a page of no site, without the session cookie (SameSite=Strict), with a CSP in a meta tag (`connect-src 'none'`, only scripts with its nonce). The card goes into a shadow root as on the mirror (`core.js`); its own scripts run only if its module may run them on the mirror (`scripts_allowed`). The fonts are served with `Access-Control-Allow-Origin: *` for it (`FontFiles` in `app.py`). The throwaway object gets a scratch folder, an event bus and an `expose` that go nowhere, and `gpio`, `video_window` and `video_is_playing` that raise (a RuntimeError, as a pin the mirror holds does): a relay module can't switch from a preview. Nothing it renders reaches the screen or `latest_messages`.
* **Limits**: A module that fetches with its own HTTP client still goes out from a preview. Dates move by whole days, and only `2026-11-02` and `20261102T0800` forms (an epoch timestamp, as OpenWeatherMap's, doesn't move, so that provider has no samples). A Home Assistant entity that isn't among the samples answers a plain "on".

## 44. Files the Owner Uploads: a Setting Type the Core Takes, Shrunk on the Phone
> **In short:** A module's setting can take files (photos) the owner uploads; the phone shrinks them and the core keeps them in the instance's folder.

* **Decision**: A module declares `"format": "files"` with an `"accept"` in its config_schema.json; the settings drawer shows the files and an upload button, and the core takes each file on its admin routes (`features/modules/files.py`, login like every `/admin` route) into the instance's `cache/<instance>/files/<key>/`, where the module lists them. Nothing goes into config.json. The core takes one kind today: `FILE_KINDS["image"]` (a JPEG, 4 MB at most, its frame header at most 4096 px); an `accept` it doesn't know gets "not supported" in the drawer and is refused. The admin page shrinks an image on the phone before sending it (`admin.js` `shrinkImage`: `createImageBitmap` with the EXIF orientation, a canvas, a JPEG at 0.85, lower until it is under 3.5 MB) to the screen's longest side, which the core reads from wlr-randr's current mode (`video/window.py` `current_size`), within 1920 off a mirror and 3840 at most, and puts the file's date first in its name (`2026-07-14_IMG_1234.jpg`, from `lastModified`), so a slideshow sorting by name sorts by date taken. The name is otherwise the owner's, made safe (letters, digits, - and _, 100 at most, the kind's extension) and never replaces a file (`-2`, `-3`). With an image the page sends a 240 px copy from the same bitmap (~15 kB, at most 256 px and 64 kB), kept under the same name in `files/.thumbs/<key>/`, out of the module's way and removed with the photo; the field shows those (`?thumb=1`, the photo itself when there is none), the newest 30 first and 30 more a tap at a time.
* **Rationale**: A module can't take an upload itself: its routes share the admin page's origin, so the core sends their answers sandboxed (no form, no script, which could use the owner's session) and strips the cookie (a module can't tell the owner from a guest on the Wi-Fi), and they take 1 MB (#40). A setting type is the core's existing way to give modules something they can't safely build, as `lan-url` and `icon` are; built generic, with the kinds in one table, because a logo or a sound is the same problem. Shrinking on the phone sends a tenth of the data over the Pi 3's fragile Wi-Fi, decodes no 12-megapixel photo on the Pi, needs no imaging library, drops the EXIF (the GPS position) and fits the module route's 4 MB out, through which the module shows the photo on the screen. The cache because backups never copy it: hundreds of photos would make every backup huge, and the originals are on the phone. The small copies because 500 photos as thumbnails would otherwise fetch hundreds of MB over that Wi-Fi to scroll the field; made on the phone for the same reasons as the photo.
* **Boundary**: The core (pi) writes in a folder the instance's user owns once it has started (the forkserver gives it the folder and all in it, modes kept), so nothing there is trusted: each folder is opened with O_NOFOLLOW from the module folder down, a file is written under a temporary name with O_EXCL and linked in under a name that doesn't exist yet (a link the module planted there makes the next name be used, never followed), and a delete unlinks the name itself. `files/` and `files/<key>/` are 2775 and the files 0664: the instance isn't in pi's group (forkserver.py `switch_to_user`), so it reads them as other, at once; no other instance can, as the instance's own folder (0770) is closed to them.
* **Limits**: Nothing empties the cache today (fetch never prunes, the unit has no `CacheDirectory=`); any future pruning must skip `files/`. The core checks a JPEG's header, not the image (the logged-in owner is the only sender; Pillow on the Pi is the upgrade path). A screen changed later leaves earlier photos at the old size. A removed instance's folders stay on the card, as its data does.

## 45. Privacy Mode: Only the Modules Marked for It Stay on the Screen
> **In short:** Privacy mode hides every card except those marked *Shown in Privacy Mode*.

* **Decision**: Privacy mode (`features/power/privacy.py`) hides every card but those whose instance has the standard setting `show_in_privacy` (a placement key: changing it doesn't restart the module); with none marked, the boot screen's monogram (still, at half brightness, in the centre) or nothing, as `globals.privacy_shows` says. It's switched from the Settings tab, a button action (`privacy` in `BUTTON_ACTIONS`) and an MQTT switch beside the screen's (only when the owner lets Home Assistant control the screen), all through `set_privacy`, and saved as `config["privacy"]`, apart from `globals`, which the Settings tab saves whole from its form. The screen hears it in one message with the other screen-wide settings, `{"type": "screen", "privacy", "privacy_shows", "cards_over_photo"}`: right after `hello` on connecting (before any card, so a reloaded page never shows what is hidden), when the mode changes and when the settings are saved; core.js puts them on `<html>` and style.css does the rest.
* **Rationale**: Turning the screen off was already there (button, Matter, MQTT, `/api/v1/screen`) and is the most neutral a mirror can show; what guests shouldn't see is the calendar, the family's photos and the house's sensors, while the clock is fine. Marking what stays, not what goes, means a new module is hidden by default. "Something the owner chooses" is a module: the clock, or the photo module with a guest album. One message for the screen-wide settings means a changed setting reaches the screen without reloading the page (`cards_over_photo` used to come only with `/api/active-modules`, at load).
* **Limits**: The hidden cards stay in the page (`display: none`), which only the mirror's own screen loads (`on_screen`); the modules keep running and fetching. A carousel turns past its hidden slides (core.js `shownSlides`, since #46). No timer and no `/api/v1` endpoint: the owner chose the Settings tab, the button and Home Assistant.

## 46. A Module's Schedule: Shown on Some Days and Times
> **In short:** Every instance can have a schedule: shown only on the days and between the times the owner picks.

* **Decision**: Every instance has the standard setting `schedule` (`forms.py`), `{"days": ["mon", …], "from": "HH:MM", "to": "HH:MM"}`, in its own collapsible section beside *Other Standard Settings*. Blank times are midnight; `from` after `to` runs over midnight and belongs to the day it starts (Friday 22:00–02:00 shows on Saturday at 01:00); `to` is when it goes. No schedule saved, or one that doesn't read, shows the module; no day ticked hides it. The display power loop (`display_power.py`), which already reads the config every second on the owner's clock (`globals.timezone`, `local_now`), works out which instances are hidden (`scheduled_out`) and sends #45's screen message again when that changes, now with `scheduled_out`; core.js marks those cards `data-scheduled-out` and style.css hides them like privacy mode. A placement key: changing it doesn't restart the module. `validate_config` checks it (days of `DAYS`, `HH:MM` or blank).
* **Rationale**: The news in the morning, the calendar on weekdays: what is worth a glance depends on the time, and a second instance covers a second window, so one window per instance is enough. Worked out on the server, so the owner's time zone setting counts (as for the screen's schedule) and the page only follows a list; the screen message already reaches every open page at once and on connecting.
* **Limits**: Hidden, not stopped: the module keeps running and fetching, so it's current the moment it shows. A module hears it, though: the core tells each instance whose card a schedule or privacy mode hides or shows again (`hidden {on}`, and `hidden` in its start; `privacy.hidden_instances`, sent with every screen message by `broadcast_screen` and on every sync), and the module host calls the module's `on_shown(on)` at its start and whenever the card is on the screen or not, the screen being off counted too, so a radio stops when its card goes. A carousel's turn doesn't count: only what the server knows. ponytail: a paid API is called through the hours its card is hidden; upgrade: hold the instance's fetches like the screen being off does (`module_host.set_awake` per instance).

## 47. The Screen's Crash Guard: Modules Paused in Steps When the Page Keeps Crashing
> **In short:** When the mirror's page keeps crashing, the core pauses modules in steps until it stops, and says so on the Dashboard and, at the last step, on the screen.

* **Decision**: The page (`js/kiosk/core.js`) sends `{"type": "page", "id", "boot"}` each time its WebSocket opens: a random id made when the page loads, and the core start (`boot_id`) it last heard of, null when it just loaded. The connection manager (`screen.py`) counts another id than the last one's as a crash, unless the last page was from an earlier start of the core (it reloads itself on the new boot id) or the core asked for a reload within two minutes (`{"action": "reload"}`: a settings save, *Reload Screen*). A screen that systemd or the watch started again counts: that only happens when something is wrong. `modules/guard.py` keeps the crashes within ten minutes; two of them start the guard, and each crash within ten minutes of the last step takes the next: (1) pause the instance installed, updated or saved last (saves and installs are noted with their times; an install is matched to its instances by the package's name in what was installed, a PyPI name or a GitHub URL; a tie or nothing noted skips the step), (2) also every instance in Background or Foreground and those that played a video since the core started, (3) everything but the clock's instances, with a message at the screen's bottom edge in the mirror's language (the words come from the core in the screen message: the core has no translations of its own). The state is saved in the config (`screen_guard`): paused instances aren't started (`client.py`, beside the ones paused after crashing), and it outlasts a restart, since a restart would only start the loop again. The Dashboard's banner says what each step paused and when the screen crashed; *Show Again* lets them all go, and saving a paused instance's settings lets that one go (with none left the guard starts over).
* **Rationale**: A setting that crashes WebKit's renderer, such as a foreground module asking for more GPU memory than a Pi 3 has free (2026-11-04), crashes it again after every restart of the screen: without a guard the owner could only cut the power, which doesn't help either. The core can't tell which module did it (WebKit doesn't say), so it starts with the likely one, a change just made, then the GPU-heavy ones, then everything.
* **Limits**: A module that crashes the page without having been changed lately, and isn't full-screen or a video, is only caught at step 3. Ten minutes between crashes is the measure: a page that crashes less often is restarted each time but never paused. The screen's message is English and Swedish only.
* **Decision (a module update on trial)**: A module update is on trial for 15 minutes (`features/modules/trial.py`, config's `module_trial`, saved by `update_modules` before its restart), as an app update (#16) and a system update (#31) are. When it fails in that time, its version before is put back instead of anything being paused: for the module whose process died `CRASH_LIMIT` times in a row (`client.py`), or, when the guard's first step is due, for every module on trial (the guard can't tell which of them crashed the page), after which the guard starts over. Putting back is one link: an update goes into a new folder, and the site that isn't active still links the old one until the next change, so the host points the running site's link for that module back at it (`Control._site` "back") and the app restarts, as after any change of the modules. The other modules stay as they are, also after *Update All*. The version that failed counts as tried `UPDATE_TRIES` times, so the nightly update waits for a newer one; the buttons still install it. A module with no version before in the other site (a new install, or another change came in between) is paused as before. *Rationale*: pausing left an empty place on the mirror where a working module had been an hour earlier, until someone opened the admin page.

## 48. List and Search Settings: the Module Gives the Choices, Asked With the Unsaved Form
> **In short:** A setting can be a list or a search whose choices the module gives (schools, places): the admin page asks the module with the unsaved form, so the choices can follow the other fields.

* **Decision**: A setting with `"type": "object", "format": "list"` or `"search"` gets its choices from the module's `async def settings_list_<key>(self, item)` or `settings_search_<key>(self, item, query)`, named from the setting's key (`[a-z0-9_]`, so the name is always a valid one; `mirrordash-sdk validate` checks the key and the method). `item` is the other fields of the setting's list item, or the whole form for a setting outside a list; `self.config` is the unsaved form, so a key typed a moment ago works. The answer is `[{"id", "name", "detail"}]`, saved as `{"id", "name"}` (`{}` for none), so the form shows the name again without asking. A list is the browser's own `<select>` (a phone's own picker): `choices.js` loads it when the form opens and again when a field it may depend on changes (one in its own list item, or for a field outside any item, every list), keeping the saved choice when it's still there; a search is a text box whose suggestions (a listbox: mouse, arrow keys and Enter) are asked as the owner types (300 ms). Both take a list item's whole width. The route (`/admin/panels/modules/choices/<module>?field=…&query=…`) types and checks the form as Save does (`_config_from_form`), finds the field in the module's schema from its form name (`choice_field.py`: only a list or search setting of that schema passes) and asks a process of the module (`ModuleHost.choices` → host `"choices"` → `choices.py`), which makes a throwaway instance of the module (`throwaway.py`, as the preview does, but its fetch goes to the network and counts the screen as on) and calls the method. A `ValueError`'s text is shown under the field as it is ("Enter the API key first"); anything else is a generic error, the details in the log. When none of the module's instances runs (a module just added, not saved yet), the core starts its **settings process** (`settings_process.py`): a process of the module like an instance's, in the sandbox as a user of its own (`settings-<module>`, one per module, in the host's `uids.json`), never started with settings, stopped two minutes after it was last asked, when the modules reload (new code) and when the host goes. The preview (#43) uses it too. **The admin page is English only**: titles, descriptions and these errors are written in English; a module's `translations/` are for the mirror.
* **Rationale**: Choices that come from outside the module (a municipality's schools, a calendar, an entity) can't be an `enum` in a file the core reads without running the module. One method per field, named after it, says what it does without an `if field ==`, and the format in the schema says which box to draw before the module answers. Asking with the unsaved form lets a list follow the fields above it (the schools of the municipality just picked). The settings process because the owner picks the school while adding the module: an instance that isn't saved has no process. English only: the mirror is what the family sees every day and is translated; the admin page is opened now and then by whoever runs the mirror, and translating it would cost every module a translated schema for good.
* **Boundary**: The field's name comes from the browser and is matched against the schema; the module's answer is input from a module (at most 2000 choices, 200 characters a text, 300 an error, 15 s). The settings process gets no home-network address (#41's lan-url) and no settings start; its scratch folder goes when the call ends.
* **Limits**: A module that needs the home network for its choices (an address in a lan-url setting) can't reach it from the settings process before it is saved. A list keeps a saved choice the module no longer lists only while the list can't load; a loaded list without it falls back to "Choose…". ponytail: an instance an owner names `settings-<module>` would share the settings process's user and folders.

## 49. Rules on What the Owner Types: the Schema's Own Keywords, Checked by the Browser and on Save
> **In short:** A module's schema can say a setting is required, has a range, a length or a format; the browser points at a broken one in the form, and the save checks it again.

* **Decision**: The JSON Schema keywords modules already wrote and nothing read are the rules: `required` (on the schema, and on a list setting's `items`), `minimum`/`maximum`, `minLength`/`maxLength`, and `pattern` with `pattern_message` (the one keyword of our own: the words for the owner, as the browser's tooltip and in the save's error). The form gives them to the browser as its own attributes (`schema_form.html` `rules`: `required`, `min`, `max`, `minlength`, `maxlength`, `pattern` + `title`), so a broken one is pointed out at the field before anything is sent; a folded list item or section holding it opens (`admin.js`, the `invalid` event). The save checks them again (`setting_rules.py` `check_setting_rules`, from `_config_from_form` with `check_rules`) and answers with the first one broken, named by the setting's title and its list item ("Calendars #1: URL is required."). As the browser does, an empty value ("", or `{}` for a list or search setting) breaks only `required` (false and [] are values), and `pattern` matches the whole value (JSON Schema's matches anywhere in it; `^…$` works in both). A key the form didn't send isn't checked: the module uses its default.
* **Rationale**: Seven modules already marked settings required and six gave ranges, so these are the words module authors reach for, and they cost a module no code. The browser's own checks need no JavaScript of ours and work the same on a phone; the save's check counts, as the browser's can be skipped.
* **Boundary**: Only the instance being saved is checked, never the rest of the config (`validate_config` stays a check of shapes): an old saved value in another module that breaks a rule blocks no save. The preview (#43) and a list's choices (#48) don't check them, as they run on a form being filled in (a required school list must load while it is still empty).
* **Limits**: A pattern Python's `re` can't read passes on the server (the browser uses its own regex flavour). A list whose choices couldn't load is disabled and so skipped by the browser; the save's check still says it's missing. `settings_check_<key>` (a check only the module can make, such as trying an API key) waits until a module needs it. A rule on a field inside a nested object setting isn't checked on save.
## 50. A Setting Shown Only for a Choice: show_if
> **In short:** A setting can be shown only while another setting of its form has some values (`"show_if": {"source": ["immich"]}`), so a module with several sources shows only the chosen one's settings; hidden ones keep what is saved.

* **Decision**: `render_schema_form` (`forms.py` `_shown_if`) wraps a field with `show_if` in `<div class="show-if" data-show-if='{"<form name>": [values]}'>` (`display: contents`, so the field stays in the drawer's grid), hidden from the start when the saved value (or the default) doesn't match, so nothing flashes. `static/admin/show_if.js` follows the form on every change. Each key must name a field of the same schema level (others are left out); with several keys all must match; values compare as text. A hidden field is still sent with the form, so its value is saved as it was. The settings stay flat: no key moves.
* **Rationale**: Photos had one Source and the settings of all six sources in one list. Sections per service (#51, tried first) still showed four services beside the Source that picks one; showing only the chosen source's settings answers it. A nested `"type": "object"` per source would move the saved keys, and the core's other readers of a schema look only at its top level (a lan-url, #41, or a password, #39, inside it would be missed).
* **Limits**: `show_if.js` follows a dropdown, a text box or a switch (two inputs under one name, a hidden "false" and the checkbox: its value is whether it is ticked, `true` or `false` in the schema), in a list item too, naming a field of the same row (#54). A hidden field's value isn't cleared, and #49's rules still hold for it: one that breaks a rule is shown again when Save is pressed (admin.js's invalid handler), so the browser can point at it. ponytail: a rule that holds only for one choice (a key required only for its service) would need the rules to skip hidden fields.

## 51. Setting Groups: Flat Settings Drawn in a Collapsible Section
> **In short:** A module sorts its settings into sections with `"group": "<title>"` on each field; only the form changes, the settings are saved flat as before.

* **Decision**: `render_schema_form` (`forms.py`) draws the fields with the same `group` in one collapsible section (the `accordion` macro, the fields two by two inside as in the drawer), where the first of them is; the section is closed when the form opens. The field's form name and the saved key don't change. A field may have both a group and a `show_if` (#50).
* **Rationale**: Settings a module's owner seldom touches (advanced ones, one service's of several) out of the way without moving them. A nested `"type": "object"` draws the same section, but moves the saved keys and hides a lan-url (#41) or password (#39) inside it from the core's other readers of a schema.
* **Limits**: A section is never open by default. Groups work in a list item's row too (#54).

## 52. A Module Gets Its Schema's Defaults
> **In short:** A setting the owner never saved reaches the module as its schema's `default`, so a module reads `config["city"]` and writes each default once, in `config_schema.json`.

* **Decision**: When the core starts an instance (`client.py`'s sync), `features/modules/defaults.py` fills each setting missing from the saved ones with its `default`, in nested objects too. A `lan-url` never saved arrives as `""` (its default is a hint in the form, never an address the module may reach, #41); a list or search choice as `{}`, as a saved "none". A setting without a default stays missing. The preview and the settings process get the unsaved form, which holds every field already.
* **Rationale**: Each module wrote its defaults twice, in the schema and in `config.get("city", "Stockholm")`, and the two drifted. A setting a module update added was missing from every instance saved before it, which is why the second copy was needed.
* **Limits**: A setting saved empty (`""`) stays empty: only a missing one is filled.

## 53. The Type Picks a Setting's Box, the Format Changes It
> **In short:** Which box a setting gets follows its `type` and its `format` only: never its key's name, and a slider only with `"format": "slider"`.

* **Decision**: `forms.py`'s `WIDGET_RULES` reads the type, `enum` and `format`. Gone: a key named `api_key`, `password`, `token` or `secret` drawn as a password, `description`, `text`, `message` or `preamble` as a text box, `color` as a colour picker, and in a list item `color` as swatches and `icon` as a grid of sixteen icons (`format: color` gives the swatches there; `format: icon` the box that suggests every Lucide name, as everywhere else). `minimum` and `maximum` are rules on a number box (#49); `"format": "slider"` with both makes a slider. An `enum` without `enum_titles` shows its value with `_` as a space and a capital first (`open_meteo`: Open meteo), not in capitals. `mirrordash-sdk validate` warns about a key like `api_key` without `format: password`, an `enum` without titles and a keyword it doesn't know.
* **Rationale**: A module's author read a table of hidden rules: a field named `text` became a big box, adding a range to a number turned it into a slider. One rule (the type, changed by the format) is learnt once. A plain backup still leaves out a setting named like a secret without the format (`backup/secret_settings.py`): a safety net, not a way to draw it.

## 54. A List's Rows Are Drawn as the Form Is
> **In short:** The fields of a list setting's row get the same boxes as the form's own (a switch, a slider, a time, show_if, group), and a home address in a row opens to the module.

* **Decision**: `render_array_item` draws a row's fields with `render_schema_form` under the row's name (`modules[c][calendars][2]`), so every box, `show_if` (naming a field of the same row) and `group` work in a row; the list item's own macros (`sub_text`, `sub_select`, …) are gone, and a colour is one box everywhere (the swatches and the value as text, a `var()` too). Files still can't be in a row. `lan.py` reads the `lan-url`s in a list's rows and nested objects; a plain backup leaves out the secrets there too (`backup/secret_settings.py`, a restore putting this mirror's own back only into the same row). `admin.js`'s `reindexArrayContainer` moves a row's place in its names, ids, labels, Show buttons, swatches and show_if rules after a move or a removal (before, the swatches took the card's last field's id).
* **Rationale**: A module's author learnt two tables: a `boolean` in a row was a text box to type `true` into, a slider, a time or a home address there only text. One way of drawing a field is one thing to learn and fewer macros to keep.
* **Limits**: A row's fields show their descriptions now, so a row is taller. ponytail: a row's labels still point at ids made before a move only until it is reindexed, which every move and removal does.

## 55. A TV Turned Off and On With the Screen Over HDMI-CEC
> **In short:** When the screen turns off or on, a TV on the HDMI cable is told to as well, over HDMI-CEC, as its remote would; a TV showing another input is left alone. On by default, a switch on the Power tab. Not yet tried on a real TV.

* **Decision**: `DisplayPowerManager.set_state` (`features/power/display_power.py`) calls `set_tv_power` (`features/hardware/cec.py`) unless `system.display_control.cec` is false: before the HDMI output goes off, and in the background after it is back on. `set_tv_power` runs `cec-ctl` (v4l-utils, in the image by name) on the kernel's adapter (`/dev/cec0` from `vc4_hdmi`; the first with a physical address, for the Pi 4/5's two ports), as the playback device "MirrorDash", claimed again each time. It polls the TV (logical address 0) and stops there when nothing answers: a monitor. Off: it asks who is the active source (`<Request Active Source>`, a second for answers) and sends `<Standby>` to the TV only when the mirror is, or nobody says. On: `<Image View On>` and `<Active Source>`, unless the TV reports it is on (`<Give Device Power Status>`) while another device is the source. A screen without a physical address (a TV that drops its hotplug line in standby) only gets `<Image View On>`, from Unregistered, which the kernel allows for this. Every screen control goes through `set_state` (the schedule, presence, the button, the admin page, `/api/v1`, Matter, MQTT), so all of them reach the TV.
* **Rationale**: Turning the HDMI output off (`wlr-randr --off`, or DPMS with `wlopm`, which leave the same state in KMS: the CRTC off, no signal) puts a monitor in standby, but what a screen does without a signal is up to the screen, and many TVs show "No signal" for minutes or keep their panel lit. CEC's `<Standby>` is the TV's own off. Sent to the TV alone, never to everyone (15), which would turn a soundbar or receiver off too. The checks keep the mirror from turning off a TV someone watches on another input, or switching it to the mirror. Off waits for the TV before the signal goes, since a TV that switches inputs on its own would otherwise be showing another one, and be left on. cec-ctl was already in the image (a dependency) and handles claiming, retries and replies; the ioctls by hand would be ours to keep.
* **Measured** on a Pi 3B (2026-11-06): the adapter keeps its address and sends with the HDMI output off, by `wlr-randr` and by `wlopm` alike; the monitor there (Samsung S24D300) has no CEC, so the poll goes unanswered and a screen change waits 0.7 s for it, nothing else is sent. **Not yet tried on a TV**: the active-source and power-status answers are parsed as cec-ctl prints them, not as seen from one.

## 56. The Screen: WPE WebKit Rebuilt From Debian sid, Shown by a Launcher of Our Own
> **In short:** The mirror's page is shown by `mirrordash-screen`, about 80 lines of C on WPE WebKit's WPEPlatform API, instead of Cog. WPE comes from Menturan/mirrordash-wpe, which rebuilds Debian sid's package for trixie every time sid has a new one, because trixie's own WPE gets no security fixes. A walk-through for a new developer (the chain as a diagram, how to change and test the launcher, what to do when the build fails): `scripts/screen/README.md`.

* **Decision**: `Menturan/mirrordash-wpe` (its own repo) rebuilds the newest `wpewebkit` source from Debian sid for trixie arm64 on GitHub's free arm64 runner (`build.sh` in a trixie container: `dpkg-buildpackage -B`, no tests, docs or debug symbols, ccache kept between builds; a cold build takes about 2.5 hours). It turns off, with WebKit's public build options only, what the screen never uses (speech, spell checking, XSLT, PDF.js, accessibility, the libwpe API and the DRM and headless platforms), and takes exactly the symbols those remove off Debian's symbols list; the build stops if Debian's rules change under its edits, if WebKit stops knowing an option, or if any other symbol disappears. Before a release, `smoke-test.sh` compiles the launcher against the new packages and runs it in a headless labwc (it must draw and not crash): a WPE that breaks the launcher is never released, so the image never gets it. The release carries the .debs, `SHA256SUMS`, `DEPENDS.txt` and notes with Debian's changes since the last one (its security fixes); a weekly job starts a build when sid has a version without a release, and `MIRRORDASH_BUILD` in `build.yml` goes up when the build itself changes. The image's `step_screen` (`configure_image.sh`) installs the latest release's `libwpewebkit-2.0-1` (checked against `SHA256SUMS`), compiles `scripts/screen/mirrordash-screen.c` against it and removes the compiler; `build_image.sh` fails an image without the launcher or with another WPE (its version must carry `~mirrordash`). `screen-kiosk.service` runs it on labwc (`WPE_PLATFORM=wayland`) with the network rules #41 gives the screen. The launcher opens one fullscreen view with a black background and shows `loading.html`, which goes on to the mirror's page once the server answers. It exits on `web-process-terminated` (a renderer out of GPU memory, #15) and on the view's `close`, so systemd starts it again; it refuses every navigation off `http://localhost:8000/` and every new window (`decide-policy`), so a module's script can't send the mirror elsewhere; the page's console goes to the journal (`journalctl -u screen-kiosk`).
* **Rationale**: Debian marks wpewebkit unsupported from bookworm on (`security-support.deb13`): trixie keeps 2.48.3 and its open CVEs, and the screen shows pictures and video from anywhere, so the engine's own bugs are reachable. WPE 2.54 deprecated libwpe, the API Cog is built on, and Cog gets no releases past 0.18; Igalia's answer is that with WPEPlatform a launcher is a few lines, which it is. Weighed and dropped: WebKitGTK (supported in trixie, but GTK 4.18 gets no EGL on the Pi 3's vc4 and falls back to drawing on the CPU: 226 MB and ~20 % of a core against Cog's 101 MB and ~8 % then), Raspberry Pi's Chromium (~380 MB more and the heaviest on a 1 GB Pi 3), Firefox, Electron and QtWebEngine (bigger still), and staying on 2.48 (never fixed). Nobody ships a current WPE for Debian or the Pi (set-top boxes build their own), and sid's source builds on trixie unchanged.
* **Measured** on a Pi 3B with the same modules, the screen on, 10 minutes after start (2026-11-06): Cog on 2.48 211 MB (PSS of the screen's processes), ~10 % of a core, 13 MB CMA free; the launcher on 2.54 193 MB, ~8.6 %, 35 MB CMA free; the page looks the same.
* **A change of site while the screen is off aborts WPE 2.54**: `RELEASE_ASSERT(!priv->frameCallback)` in `WPEViewWayland.cpp:601` (like WebKit bug 298599, still in WebKit's main): the new web process hands a frame over while the compositor, with the output off, never answered the last one. `loading.html` from `file://` going on to `localhost` was such a change: 12 aborts in 12 starts with the screen turned off while loading. The launcher shows `loading.html` as if it came from `http://localhost:8000/` (`load_html`), so going on to the page is no change of site: 0 in 18, and a start with the screen off runs. Cog 2.48 was worse: it crashed about once a second for as long as the screen was off. A launcher started while the screen is off (a mirror booting outside its schedule) waits for a screen before it makes the view: a view made without one ties its frames to no display, never draws and so never shows, and stayed black when the screen came on (WebKit gives it a screen only when its window enters one); once made, it carries on through the screen going off and on.
* **The screen off stays `wlr-randr --off`**: DPMS (`wlopm --off`) leaves the same state in KMS (the CRTC off, no signal), but keeps the output in labwc's layout; it aborted WPE just the same and freed about 5 MB of CMA where `wlr-randr` frees 10. What a screen does without a signal is up to the screen; a TV is turned off over HDMI-CEC (#55).
* **Limits**: The packages are ours to keep: when sid's source stops building on trixie, the weekly job fails and the security fixes stop until someone fixes it. WPE has no debug symbols in the image: a crash's addresses are matched to the library's sections and the strings around them by hand. The smoke test draws on the CPU in a CI container: what only the Pi's GPU (vc4) shows is caught by an OS test version, not before the release.

## 57. Notifications: One Store, Fed by the Saved Logs, New Versions and the App's Own Events
> **In short:** What happens to the mirror that its owner should know (an update, a module that kept crashing, a power cut) is a notification in plain words: a bell on the admin page counts the unread ones, and while an error is unread the mirror says "Error: see the admin page". The system's own scripts never talk to the app: every saved log they leave becomes a notification.

* **Decision**: `mirrordash_core/notifications.py` keeps them in `notifications.json` in the data folder: the newest 50, read or not, each with a level (info, warning, error), its text, its time and the saved log that tells more. Three sources:
  1. **Saved logs** (`features/notifications/watch.py`): every new file in `/storage/mirrordash/logs` is one notification, its text and level from `KINDS` and `ERRORS` in `features/logs/saved.py` (an error needs the owner: safe mode, a system install or the firmware update that failed, a storage partition made anew, lost or left with errors (#58); a warning fixed itself). Looked for at start and once a minute. The first look on a mirror only remembers what is there.
  2. **New versions** (`features/notifications/versions.py`): at every start, MirrorDash's, the system's (its build stamp) and every module's version are held against the last start's; each that went up is "… updated to …". A version going down is a rollback, which has its saved log; a module installed for the first time isn't news.
  3. **The app's own events**: an update job that failed (`start_job(..., failure=)`), a module that couldn't be updated and stayed as it was (`update_modules`), a module stopped after crashing (`client.py`'s crash limit), a module update put back after it failed on trial (`trial.py`, #47), and the nightly update giving up on a version after three nights or waiting for Install Anyway (`auto_update`, `once=True`, so each is said once while it is kept).
  A power cut gets its saved log from `power-watch` (`mirrordash-power-watch.service`): a file on `/storage` says "running" from start to a proper shutdown, and a start that finds it still there saves a `power-lost` log. The screen hears of an unread error in its `hello` and in `{"type": "notices"}` when that changes, and shows its badge under Offline (`index.html`, `.system-badges`).
* **Rationale**: The scripts that know most (rollback, safe mode, Wi-Fi recovery, the app watch) run as root, often while the app is down, so they can't reach it; they already saved a log for each event, and the log is what the owner wants to download next. "Updated to" is said when the new version runs, not when it was installed, since an install that crashes is rolled back; comparing versions at start says it once for the buttons and the nightly update alike. One file for the history: it is a few kilobytes, written a few times a day, and lost history costs nothing (a broken file starts over), so no database. Not in a backup: it is this mirror's history.
* **Limits**: A saved log is seen up to a minute late. A notification marked `once` can be said again after 50 newer ones pushed it out. The power-lost log has only the start after the cut (the journal is in RAM), and a freeze the owner pulled the plug on looks the same as a power cut. An OS on trial counts as updated already; when its trial fails, the `os-trial` log says so right after.

## 58. A Damaged SD Card: the Newest Backup Is the Way Back
> **In short:** A power cut can't harm the system (#5, #16, #31) and a write to `/storage` is all or nothing (#12), but a card can still lose blocks. When the storage partition is past what `e2fsck -y` repairs, the mirror copies the newest backups off it, makes it anew and starts as a new mirror; one restore brings everything back. A weekly automatic backup makes sure there is a recent one, passwords included.

* **Decision (the weekly backup)**: The nightly run (`/admin/auto-update`, 03:30) first calls `features/backup/automatic.py`: when the newest automatic backup is a week old (less an hour) it builds the content, and writes `mirrordash_autobackup_<time>.mirror` only when the content's hash (`archive.content_hash`, in the manifest) differs from the last one's; otherwise it touches `.automatic-checked` so the next check is a week later (a check writes the content out to compare it). The newest two are kept, never pruning the one just written (a wrong clock can give it an older name); hand-made ones are never touched. Nothing is made while a job runs, and what a killed backup or restore left in the folder (`tmp*`, a day old: copies of the passwords) is removed first. The due check takes the time's distance either way, so a clock that went back more than a week doesn't stop them. It holds what an encrypted backup holds (the config with its secrets, `wifi.json`, `pi_password.hash`), unencrypted, mode 0600 in the core's 0700 data folder. It can be restored, not downloaded (`service.downloadable`: the route answers 403; the Backup list shows it as *Automatic*, without the download button). Nor can the copy a restore puts in `tmp_upload.mirror` (which can be one): it isn't listed and isn't downloadable. A restore needs no change: it keeps the backup's secrets where the backup has them (`_keep_this_mirrors_secrets` fills in only what is missing). A backup that fails is logged and never holds the nightly update back; the timer's curl waits up to 15 minutes for both.
* **Decision (the rescue)**: In `mirrordash-hydrate.sh`, on an image, when `e2fsck -p` gives up on the partition (exit 4 and up), `storage-rescue` (`/usr/local/lib/mirrordash/`) first copies the newest automatic and the newest hand-made backup that come out whole into a tmpfs with `debugfs -c` (reads without mounting, ignores the bitmaps; with the first superblock gone it tries the copies at 32768… for 4 KiB blocks). Whole means a plain file with something in it, at its full size, that starts as a zip (and ends as one, its central directory's end within the last 64 KiB) or with openssl's header; otherwise the one before it of the same kind is tried. A cleared inode (a block that reads back as zeros) lists with mode 0 and size 0, and the first version took that for a whole empty file: the newest "backup" came back empty and the whole one before it was never tried. Only then `e2fsck -y` runs: on an emulated mirror with the first two superblocks gone, `-y` took a later copy whose group descriptors were stale, cleared 121,200 inodes as garbage (the backups' with them), said errors were left, and the partition mounted with a root folder that refused every write ("Bad message"). So the partition is made anew when `-y` left errors and it doesn't mount, even after `udevadm settle`, or doesn't take a test write (the unit is ordered after `storage.mount`: with `nofail`, `local-fs.target` doesn't wait for it, and hydrate mustn't repair or format beside systemd's own fsck and mount; `mkfs.ext4` with one `-F` also refuses a partition in use). When it works after all, rescued backups that `-y` cleared or changed go back too; if `-y` cleared `config.json` (and its `.bak`) with what it couldn't read, the mirror starts as a new one, so it saves a `storage-lost` log and leaves the bell's mark like a rebuild, or the owner would never hear of it. When `-y` leaves errors (4 and up) but the partition works, it is kept (the settings are in it): not a repair, but a `storage-errors` log, once (while one is among the saved logs), saying to make a backup and replace the card. A partition systemd mounted but that takes no write (the kernel turned it read-only on an error, or its root folder broke) is unmounted and checked with `e2fsck -f -p`, since one the kernel didn't mark as having errors looks clean to `-p`; before, hydrate only checked a partition that wasn't mounted, and stopped on its first write. Rescued backups go back under a temporary name (`install`, synced, then renamed), and one that can't go back is only warned about: the mirror still starts. On an image the partition is always `/dev/mmcblk0p7`, in hydrate and in fstab, never found by its label: an old mirror's card in a USB reader carries the same label, and `e2fsck -y` or `mkfs` must never touch it. A rebuild whose mount fails after `mkfs` tries once more after `udevadm settle`, and the rescue's tmpfs is kept until the next start when `/storage` doesn't work, for a person to copy the backups off. A rebuild is `mkfs.ext4 -L mirrordash-data` on the device itself (not a link, which udev takes away and back for the new UUID), mounted through fstab, and the rescued files go to the app's backups folder (`/storage/mirrordash/data/data/backups`: `~/.mirrordash/data/backups`, where the Backup list finds them; until 2026-11-11 the rescue read and wrote `/storage/mirrordash/data/backups`, which the app never uses, so it found no backup) and the start's log is saved as `storage-rebuilt` at once, before anything else can fail; the rest of hydrate runs as on a first start (venv from `base_venv`, the modules' image, SSH keys). The log is shown red on the bell even on its first look (the rebuild took `notifications.json` with it; `watch.TOLD_ON_FIRST_LOOK`), but only when hydrate left `/run/mirrordash-storage-rebuilt` at this start: a `notifications.json` that broke later mustn't announce an old rebuild again, and the log's time can't tell (this early the clock still shows the image's date). Without a label (superblock gone) the partition is found as `mmcblk0p7`, the A/B layout's.
* **Rationale**: With a recent backup to restore, the backup is all that needs rescuing: settings, logins, Wi-Fi and the modules (the manifest reinstalls them) come back in one step, so the rescue reads two files instead of walking a broken tree. Unencrypted on the card, because the mirror knows no password (the admin password is a PBKDF2 hash) and the same secrets lie unencrypted beside it anyway (`system-connections`, `config.json`): whoever has the card owns the mirror (#28). Not downloadable, so they never leave the mirror in the clear; the owner makes a normal backup for a copy elsewhere. A password-protected backup is rescued as it is and asks for its password on restore; the automatic one beside it is the way back if that is forgotten. No "reformat?" button: the app, its login and the Wi-Fi all live on `/storage`, so with it gone there's no page to ask on that only the owner can reach. Only when `e2fsck` gave up, so a mount that fails for another reason (a slow card) never formats anything.
* **Decision (the boot partitions)**: The running slot's `cmdline.txt` and `config.txt` are written over in place, never replaced. A power cut must never leave either broken: no `root=` or no `auto_initramfs` is a boot loop on the only slot that boots. FAT has no journal, and replacing a file (raspi-config's two `sed -i`, or a synced new file moved over it) changes the folder and the allocation table in writes a card may persist in any order; replaying every state a cut can leave (`scripts/storage-check/boot-writes.sh`) found the one where the table frees the file's cluster while the folder still points at it: the firmware reads nothing and `fsck.fat` empties the file. Written in place with the same length, only the file's data sectors change. So the image ships `cfg80211.ieee80211_regdom=00` (the world's rules, as with none) and a country code is always two letters: `mirrordash-wifi-country` (instead of raspi-config) writes the line in place, refusing one without `root=`. The image ships an empty GPIO block of a fixed 2048 bytes last in `config.txt` (padded with empty lines, which the firmware skips): `mirrordash-gpio-overlays` keeps it that size and writes the file in place, so a cut inside the write can only garble the block, never the lines before it. A file of another length (a card from before, a block that doesn't fit) is still replaced, synced before and after the move, which leaves that one window open once. `rauc-bootloader`'s `prepare_boot` keeps the new slot's own block when the running one has none, and pads a running one from before to the fixed size, so after one OS update every mirror's block is written in place. The `mirrordash-bootslot` generator makes `/boot/firmware` wait for `systemd-fsck@` of its partition, so a FAT left dirty is checked (`fsck.vfat -a`) before use; `Wants=`, not fstab's `Requires=`, so a check that fails still mounts it as before. The helper's path is fixed in its text, never from the environment, as pi runs it as root.
* **Limits**: Nothing on the card survives a card that dies; the only copy elsewhere is one the owner downloaded. A backup bigger than half the RAM can't be rescued (the tmpfs), nor one in blocks that don't read; one that reads at its full size, starts and ends as a backup but is broken in the middle (a broken extent) fails only when restored, so the other rescued one is the fallback. Up to a week of changes is lost. The modules' data lives in `modules.img` and comes back only with the backup. Bad blocks in the running OS slot (boot or root partition) have no way back: the firmware has no boot counter and the tryboot flag dies with the power, so the mirror restarts into that slot until the card is flashed again (#31's A/B covers a bad update, not a bad card). The superblock copies are found only at their places for 4 KiB blocks (ponytail; `dumpe2fs -o` would read them).
* **Checked**: `scripts/storage-check` in CI on every push, `tests/test_hydrate.py`, and the built image in an emulated Pi 3B: [scripts/storage-check/README.md](scripts/storage-check/README.md).

## 59. Features Import One Way, Shared Code Imports No Feature
> **In short:** The shared code at the package root imports no feature, no two features import each other, and `app.py` connects what would otherwise point the wrong way. A test reads every import and fails on a new one against that.

* **Decision**: The core has three kinds of code. The shared code at the package root (#27) imports no feature. A feature imports the root and other features, but never one that imports it back. `app.py` puts the app together and may import everything: what would point from a lower part up to a feature, it connects at startup (`event_bus.subscribe("hardware.button", buttons.on_button)`, so `hardware` knows nothing of `power`; `module_host.on_state = mqtt_bridge.module_state`, so `modules` knows nothing of `mqtt`). What two features both need moves down to the root (`host.py`: disk usage and the installed OS version; `screen.py`: the screen's WebSocket hub) or to the feature that owns it (`features/modules/installed.py`, `features/wifi/network.py` `get_wifi_info`, `features/modules/trial.py` `UPDATE_TRIES`, `features/backup/setup_restore.py`: the restore on the Wi-Fi setup page is a backup route).
* **Rationale**: Measured on 2026-11-11, 14 of the 16 features and `system_settings.py` were one knot: 57 imports between features, 15 pairs importing each other, kept from failing at import time by about 105 imports inside functions. A change in one feature could break any other, and nothing showed which. After: 40 imports between features, one pair, 84 imports inside functions, and no cycle among the imports at the top of a file. A module's state doesn't go over the event bus because the bus forwards every core event to all modules; one hook on `ModuleHost` is the smaller thing.
* **The exception**: `modules` and `power` import each other, inside functions only (the crash guard and `ModuleHost` ask what the screen shows and hide instances; privacy mode and the screen schedule pause and start instances). They are one topic, what is on the screen and when, in two folders. Pulling them apart needs a third part both report to, which is more code than the eight imports it removes.
* **Limits**: The test sees pairs, not longer chains. One is left, held together by imports inside functions: `backup` → `mqtt` (a restored mirror keeps its MQTT ids) → `settings` (a setting changed from Home Assistant) → `updates` → `backup` (a backup before an update); `dashboard` is in it as well (`mqtt` reads the CPU temperature from it, and it asks `updates` for a new version). The root's `admin.py`, `notifications.py` and `screen.py` import each other inside functions too. `features/updates/service.py` (506 lines) and `features/mqtt/bridge.py` (527) were left whole: the tests replace names in them at about 100 places, and after a split those would silently replace nothing. Splitting them goes with changing how the tests fake the config.
* **Checked**: `tests/test_import_layers.py` reads every import in the package, also those inside functions. Its two lists of exceptions only shrink: a new import against the layers fails, and so does a listed one that is gone.

## 60. Root Over SSH by a Key File on the Boot Partition
> **In short:** The owner gets root on their own mirror for debugging by putting a public key on the first SD-card partition, which the app cannot write. No file, no root login. It is a developer feature with no admin page.

* **Decision**: sshd's drop-in `mirrordash-root.conf` lets `root` log in by key only, and reads root's keys from `/boot/autoboot/mirrordash-root-key.pub` (p1, AUTOBOOT, like `authorized_keys`: one key per line) instead of `~/.ssh`. There is no boot service: without the file sshd finds no key and root cannot log in. `pi`'s login is unchanged. `update-p1` (#31) copies the file into each renewed p1 and checks the copy before the MBR points at it. The drop-in is named after `mirrordash-hostkeys.conf` and its global keyword comes before the `Match` block, as sshd wants (the first value of a keyword wins, and a `Match` ends with its file). How to use it: [RELEASING.md](RELEASING.md#root-on-your-own-mirror).
* **Rationale**: The app runs as `pi`, and whatever `pi`, the admin page or a module can do, a compromised app can do. So root must come through a channel `pi` cannot write. The boot partitions are root-owned (vfat with fmask/dmask 0022, `pi` is not in group `disk`), and whoever holds the card already has root (#28), so the file gives an attacker nothing new. Not `sudo` for `pi`: that hands root to the app itself. Not a debug image: `pi` can install any bundle signed with the project key (#31), so a signed debug bundle would be installable on every mirror. Not an upload on the admin page: the admin page is the app. p1 and not p2/p3: those are per slot and overwritten by an OS update; p1 is shared by both slots and never written by RAUC. No banner and no setting: not for ordinary owners.
* **Limits**: A factory reset leaves the file (it is on the card, not in `/storage`); delete it before giving a mirror away. Anyone who can write the card can add a key, which they could do anyway.
* **Assumptions**: what the design relies on (`pi` cannot write `/boot/autoboot`: root-owned vfat mount, `pi` not in group `disk`, no sudo rule that writes there) is written in the header of [mirrordash-root.conf](scripts/image/rootfs/etc/ssh/sshd_config.d/mirrordash-root.conf), checked on a real mirror 2026-11-12.
* **Checked on a real mirror** (Pi 3B, `v0.16.0-os2`, 2026-11-13): root logs in with the key; sshd's `StrictModes` accepts the key file on vfat (the mount shows it root-owned, mode 0755); `sshd -T` for root gives `permitrootlogin without-password`, `passwordauthentication no`, `authenticationmethods publickey` and the file as `authorizedkeysfile`; root's password is locked (`passwd -S root` says `L`), and a password login or another key is refused with "Permission denied (publickey)"; `pi` still logs in with its password and can't write the file or the folder; without the file (same image, 2026-11-12) the key was refused. **Unverified**: that the file survives a real renewal of p1 (`update-p1`) on a mirror; `tests/test_ab_updates.py` covers it, and `tests/test_configure_image.py` checks the drop-in.
